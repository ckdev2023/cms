你现在负责处理“后端 Service 与 DTO 拆分和整理”。目标是降低后端类和方法的复杂度，让接口层、业务层、参数层更清晰，但不要扩散成大规模架构重写。

如需编写代码，必须同时遵守：

- `prompts/12_Cursor_代码规范与实现要求.prompt.md`
- `prompts/13_Cursor_输出汇报格式规范.prompt.md`
- `prompts/14_Cursor_提交前检查与收口.prompt.md`

## 一、适用范围

适用于：

- Service 过大、职责混杂
- Controller 过厚
- DTO 过多复用导致语义混乱
- 校验逻辑、业务逻辑、数据访问逻辑混在一起
- 同一模块用例边界不清晰

## 二、默认技术口径

- 后端基于 `NestJS + TypeScript + PostgreSQL`
- Controller 保持薄
- Service 按用例组织
- DTO 优先表达清晰的输入语义
- 保持当前项目目录风格一致

## 三、执行顺序

### 1. 先评估问题边界

请明确：

- 当前 Service / DTO 的主要问题是什么
- 本轮要解决哪些复杂度问题
- 本轮明确不改什么
- 是否涉及接口语义变化

### 2. 输出拆分方案

至少说明：

- 哪些逻辑保留在 Controller
- 哪些逻辑保留在核心 Service
- 哪些逻辑拆成辅助 Service / domain helper / util
- 哪些 DTO 需要拆分、重命名或单独建文件
- 拆分后如何提升可读性、测试性和复用性

### 3. 实施时请遵守

- 不把业务编排塞回 Controller
- 不把所有逻辑拆成过多碎片导致难追踪
- 创建 DTO 时名称必须表达场景语义
- 输入校验、权限判断、状态流转、数据访问职责要清晰
- 如接口字段或返回结构变化，必须同步上下游
- 如仅是内部重构，尽量保持外部行为不变

### 4. 重构重点检查

请重点关注：

- 方法职责是否更单一
- DTO 是否更贴合具体用例
- Service 之间调用关系是否清晰
- 错误处理和日志是否仍然明确
- 测试是否仍能覆盖关键业务逻辑

### 5. 必须补验证

至少完成：

- 关键 Service 逻辑测试
- 受影响接口的最小测试
- 至少一项类型检查或构建检查
- 如涉及 DTO 变化，补参数校验验证

### 6. 最终输出

请总结：

- 为什么要拆分
- 拆分了哪些 Service / DTO
- 哪些职责边界更清晰了
- 外部行为是否变化
- 测试与验证结果
- 是否还有遗留的大类 / 大方法

## 四、限制要求

- 不要顺手做大规模架构升级
- 不要只改目录结构，不解决职责混乱问题
- 不要遗漏 DTO 校验和测试同步
- 不要把内部重构伪装成功能增强

请用中文输出，优先保证职责清晰、行为稳定、测试可跟进。
