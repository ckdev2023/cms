你现在负责处理“前端页面拆分与重构”。目标是提升页面可读性、可维护性和复用性，但不能把重构做成无边界的大改。

如需编写代码，必须同时遵守：

- `prompts/12_Cursor_代码规范与实现要求.prompt.md`
- `prompts/13_Cursor_输出汇报格式规范.prompt.md`
- `prompts/14_Cursor_提交前检查与收口.prompt.md`

## 一、适用范围

适用于：

- 页面文件过长
- 单组件职责过多
- 列表、表单、详情、弹窗逻辑混杂
- 重复 UI 逻辑较多
- watch / computed / methods 过于混乱

## 二、默认技术口径

- 前端基于 `Vue 3 + TypeScript + Element Plus`
- 优先 Composition API
- 保持现有项目风格一致
- 优先小步重构，不做整站式重写

## 三、执行顺序

### 1. 先评估重构必要性

请明确：

- 当前页面有哪些可维护性问题
- 哪些问题最影响开发效率或稳定性
- 本轮重构目标是什么
- 本轮明确不重构什么

### 2. 输出拆分方案

至少说明：

- 哪些逻辑保留在页面层
- 哪些拆成子组件
- 哪些拆成 composable
- 哪些拆成 types / constants / utils / api 层
- 拆分后如何降低文件长度和复杂度

### 3. 实施时请遵守

- 页面层保留路由级编排和页面级状态
- 纯展示或局部交互优先拆为子组件
- 可复用业务逻辑优先拆为 composable
- 常量、枚举、表头、规则、默认值可抽离
- 避免把所有状态都下沉导致调用关系难追踪
- 避免为拆分而拆分，导致文件数量失控
- 先保持行为一致，再谈样式或结构优化

### 4. 重构重点检查

请重点关注：

- 表单校验是否仍然完整
- 弹窗开关、加载态、提交态是否稳定
- API 调用和错误提示是否仍然清晰
- 类型是否仍然准确
- 页面交互是否和重构前保持一致

### 5. 必须补验证

至少完成：

- 被拆分页面的关键交互测试或最小 smoke check
- 至少一项类型检查或构建检查
- 如提取了 composable，优先补其关键逻辑测试

### 6. 最终输出

请总结：

- 为什么要拆分
- 实际如何拆分
- 哪些文件变短了
- 哪些职责被隔离出来
- 测试与验证结果
- 是否还有待继续拆分的部分

## 四、限制要求

- 不要顺手改页面业务逻辑口径
- 不要一轮重构多个大页面，除非明确要求
- 不要只拆文件，不处理命名和职责问题
- 不要省略重构后的验证

请用中文输出，优先保证行为不变、结构更清晰、后续更易维护。
