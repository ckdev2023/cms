你现在开始编写或修改代码。无论开发哪个模块，都必须遵守以下代码规范与实现要求。若与当前任务 Prompt 一起使用，以本规范作为统一编码底线。

## 一、总体原则

1. 优先保证正确性，再考虑速度
2. 优先保证可读性，再考虑炫技写法
3. 优先最小闭环，不做过度设计
4. 改动尽量小而完整，避免大面积无关重构
5. 新增代码必须便于测试、便于排查、便于后续 AI 接手

## 二、可读性要求

- 命名要清晰，变量 / 函数 / 组件 / 类型名必须表达业务含义
- 禁止使用无意义命名，如 `a`、`temp1`、`data2`、`handleIt`
- 避免超过 3 层嵌套，优先早返回
- 一个函数尽量只做一件事
- 重复逻辑抽成公共函数、service、composable 或 util
- 魔法数字、魔法字符串要提取为常量或枚举
- 复杂判断要拆成具名布尔变量，提高可读性
- 保持同文件内代码顺序稳定，例如：类型 → 常量 → 主逻辑 → 辅助函数

## 三、注释与备注要求

- 注释重点写“为什么”，不要大量写“代码正在做什么”这种废话注释
- 对复杂业务规则、边界条件、性能取舍、兼容性处理，要写简短说明
- 公开函数、核心 service、复杂 composable、关键计算逻辑建议加简短注释
- TODO 必须带原因和后续方向，禁止只写 `TODO`
- 不要保留无意义的调试注释、注释掉的大段旧代码

## 四、文件与函数规模要求

- 单个函数建议不超过 60 行；超过 80 行应优先拆分
- 单个 Vue 页面 / TS 文件建议不超过 300 行；超过 400 行应优先拆分
- 单个组件职责不要过多；表单、列表、详情可拆子组件时优先拆分
- 单行代码建议不超过 120 字符，过长请换行
- 超过 5 个参数的函数应考虑改为对象参数

## 五、性能要求

- 避免明显的重复查询、重复计算、N+1 查询
- 列表接口优先分页，不要默认全量加载大数据
- 搜索和高频输入场景考虑防抖或节流
- 前端避免不必要的响应式层级和重复 watch
- 后端避免在循环中做昂贵查询或重复 I/O
- 数据库查询应关注索引命中和筛选字段设计
- 财务、文件、权限等关键路径优先保证稳定和可追踪，不做过早复杂优化

## 六、健壮性要求

- 所有外部输入都要做校验
- 错误处理要明确，不能直接吞错
- 关键操作要有清晰返回和错误提示
- 对删除、作废、金额修改、下载等高风险动作要保留保护逻辑
- 边界值、空值、重复提交、权限不足等场景要考虑清楚

## 七、前端要求

- Vue 组件优先使用清晰的 Composition API 结构
- 页面代码按“类型 / 常量 / 状态 / 计算属性 / 方法 / 生命周期”组织
- 表单校验、提交中状态、错误提示必须明确
- API 调用、状态管理、视图层逻辑尽量分层
- Element Plus 组件使用保持一致，不要同类页面风格差异过大

## 八、后端要求

- Controller 保持薄，业务逻辑尽量放到 Service
- Service 方法要围绕用例组织，不要堆成超大万能类
- DTO / 参数校验 / 返回结构保持清晰
- 数据访问逻辑集中管理，避免到处散落 SQL 或查询代码
- 日志记录要聚焦关键路径，不要输出过多噪音日志

## 九、测试要求

- 新增或修改业务逻辑时，必须补对应测试
- 优先补关键 service 测试，再补接口或前端交互测试
- 财务、文件、权限相关改动要更严格测试
- 如果暂时无法补测试，必须明确说明原因和风险，不可默默跳过

## 十、输出要求

每次完成代码修改后，请额外说明：

1. 如何满足了可读性要求
2. 哪些地方加了必要注释
3. 哪些性能风险已避免
4. 是否存在文件过长或函数过长风险
5. 本轮新增了哪些测试

请严格执行本规范，优先保证代码整洁、易读、稳定、可维护。
