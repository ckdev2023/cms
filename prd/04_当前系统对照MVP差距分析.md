# 当前系统对照 MVP 差距分析

## 1. 文档目的

本文用于把**当前已实现系统**与 `prd/01_第一阶段MVP_PRD_标准化办案底座.md` 做逐项对照，回答四个问题：

1. 当前系统已经做到什么程度
2. 哪些能力属于部分满足
3. 哪些能力仍明显缺失
4. 如果目标是后续做成可推广的 SaaS，优先应补哪些底座

本文只做**产品/架构层面的现状判断**，不涉及代码修改方案。

---

## 2. 总体结论

一句话结论：

> 当前系统已经具备较强的**内部办案后台**雏形，尤其在“客户中心 + 签证域 + 行政案件 + 财务 + 文件 + RBAC”方面已有较深实现；但如果按 `MVP` 文档要求把它定义成**可对外销售的 SaaS MVP**，目前仍只能算**部分满足**，还不是完整达标状态。

更准确地说：

- 对“单事务所内部使用的案件运营系统”而言：**完成度较高**
- 对“可市场化推广的 SaaS MVP”而言：**底层骨架还不够**

核心原因不是业务功能太少，而是**SaaS 必需的租户、组织、客户门户、套餐/试用、通用案件底座**还没有完整落地。

---

## 3. 五个维度结论总表

| 维度 | 结论 | 判断 |
| --- | --- | --- |
| 数据结构 | 客户、签证、行政案件、财务、文件、日志已经较完整，但缺 SaaS 多租户与通用案件骨架 | 部分满足 |
| 页面清单与页面关系 | 后台页面已经很多，客户中心也成型，但缺 SaaS 开通、组织管理、任务中心、模板中心、客户门户 | 部分满足 |
| 权限矩阵 | 已有 RBAC、角色、权限点、路由鉴权，基础不错；但缺租户级、客户级、套餐级权限层 | 部分满足 |
| 后台信息架构 | 已形成“工作台—客户中心—财务—文件—系统”的后台骨架，签证域最强 | 部分满足 |
| 客户中心信息架构 | 当前“客户中心”本质上是**内部员工客户中心**，不是客户自助门户 | 未满足 |

## 5. 分维度详细分析

### 5.1 数据结构：部分满足

### 已有能力

- 已有客户主档、个人/法人扩展信息、备注/跟进记录
- 已有签证案件主表、家属成员、材料项、材料模板、路径台账、导入批次
- 已有行政案件、任务、文件关联
- 已有财务主表：账单、收款、预收款
- 已有文件实体、访问日志、审计日志、登录日志
- 已有用户、角色、权限、团队

这说明系统在“**内部办案数据模型**”上不是空白，而是已经很接近实际事务所作业场景。

### 仍缺的关键结构

1. **多租户结构缺失**
   - 当前公共基类 `backend/src/common/entities/base.entity.ts` 只有审计字段，没有 `tenantId`
   - 客户、案件、文件、财务等核心表都看不到明确的租户隔离字段
   - `Team` 更像签证域的数据范围分组，不等于 SaaS 的租户/组织模型

2. **组织模型不完整**
   - MVP 要求里有“租户、组织、成员、试用开通、套餐控制”
   - 当前只有 `users / roles / permissions / teams`，缺 `tenants / organizations / offices / subscriptions`

3. **通用案件主表不足**
   - 当前更像“客户 + 签证案件 + 行政案件 + 税务合同”的并列模块
   - 还不是 `MVP` 里要求的“可承载多业务类型的统一案件引擎 + 模板实例化结构”

4. **模板层不够完整**
   - 现有材料模板偏签证域
   - 缺更通用的阶段模板、任务模板、资料项模板、业务包模板

5. **客户门户数据模型缺失**
   - 未见客户端账号、邀请链接、客户上传会话、外部协作者等实体

### 结论

当前数据结构更适合支撑“单事务所内部后台”，距离“SaaS MVP 数据底座”还差一层平台化抽象。

---

### 5.2 页面清单与页面关系：部分满足

### 已有页面

从 `frontend/src/router/routes.ts` 可以看到，当前后台已经具备：

- 登录页
- 工作台
- 客户列表 / 客户详情
- 签证工作台 / 提醒 / 案件登记 / 历史导入 / 行政补录
- 行政案件列表 / 详情
- 税务合同
- 财务（账单 / 收款 / 预收款）
- 文件中心
- 用户 / 角色 / 字典 / 审计日志 / 登录日志 / 导出日志

这说明“后台可操作页面”已经不是 MVP 草稿阶段，而是已有较强基础。

### 缺失页面

按 `prd/01` 的 MVP 页面清单，仍缺以下重要页面：

1. **试用开通 / 租户注册 / 组织初始化页面**
2. **组织与成员管理的 SaaS 化页面**（当前更像系统后台，不是租户自管理）
3. **统一案件列表 / 案件详情页**（当前仍偏模块分散）
4. **统一任务中心**
5. **统一沟通记录中心**
6. **模板配置中心**（而非仅签证材料模板）
7. **收费状态专页的案件运营视角整合**
8. **客户门户页面**（登录、进度查看、资料上传、补件反馈）
9. **套餐、订阅、试用到期、安全设置相关页面**

### 结论

后台页面很多，但“**内部系统页面**”和“**SaaS 产品页面**”之间还差一段距离。

---

### 5.3 权限矩阵：部分满足

### 已有能力

- 前后端都有统一权限码常量
- 已有 `users / roles / permissions`
- 路由权限、接口权限、角色种子都已经建立
- 审计日志也已经接入到多个关键操作

这部分说明系统的 **RBAC 基础是成立的**。

### 当前不足

1. **权限层级还是“内部员工系统”思路**
   - 现有角色主要是 `ADMIN / STAFF / FINANCE`
   - 与 MVP 目标中的“管理员 / 负责人 / 员工 / 财务 / 客户 / 外部协作者”还不完全对应

2. **缺租户级权限边界**
   - 当前更像全局系统用户
   - 未体现“一个事务所管理员不能看到另一个事务所数据”的平台层权限模型

3. **缺套餐控制层**
   - MVP 与 SaaS 路线要求基础版、专业版、增值包控制
   - 当前权限更多是功能权限，不是商业套餐权限

4. **数据范围控制仍偏局部**
   - 签证域已有 `mine/team/all` 数据范围，这是亮点
   - 但客户、财务、文件等模块还没有看到一致的平台级数据范围策略

### 结论

权限体系已经有良好起点，但还没升级为 SaaS 所需的“**租户隔离 + 角色矩阵 + 套餐门禁 + 外部用户权限**”四层结构。

---

### 5.4 后台信息架构：部分满足

### 当前优点

当前后台已经形成比较明确的信息架构：

- 工作台
- 客户中心
- 税务
- 财务
- 文件
- 系统设置

其中客户中心内部又整合了：

- 客户列表
- 在留提醒
- 签证工作台
- 签证案件登记
- 行政案件并列入口

从内部使用角度看，这个方向是合理的，而且贴近事务所日常操作。

### 当前问题

1. **签证域过强，通用案件域偏弱**
   - 现在最成熟的是签证域，不是通用案件底座

2. **客户中心承担过多“后台办案中心”职责**
   - 对内部员工很方便
   - 但对 SaaS 产品化来说，后续会需要拆成更清晰的“客户 / 案件 / 任务 / 模板 / 协同”几个中心

3. **缺 SaaS 运营后台层**
   - 缺租户管理、试用管理、套餐管理、订阅管理、开通引导

4. **缺模板与通知中心**
   - 这是从“自己用”走向“卖给别人用”时非常关键的一层

### 结论

后台 IA 已适合内部落地，但还没有完全转成“标准 SaaS 产品 IA”。

---

### 5.5 客户中心信息架构：未满足

这里最容易产生误判。

当前系统里虽然有 `CustomerCenterLayout`，但它本质是：

> **给内部员工使用的客户中心整合后台**

而不是 SaaS 语义里的：

> **给客户本人登录使用的客户门户 / Client Portal**

### 当前缺失点

- 没有客户端账号体系
- 没有客户端登录入口
- 没有客户端可见的案件进度页
- 没有客户端资料上传与补件反馈页
- 没有客户通知确认、消息查看、历史上传记录
- 没有客户与内部员工的前后台权限边界

### 结论

如果按 MVP 文档中“后续可做成 SaaS 并推广市场”的标准，这一块应判断为**未满足**。

---

## 6. 最需要优先改进的地方

如果目标是“尽量少返工地走向 SaaS MVP”，建议优先级如下：

### P0：必须先补的底层

1. 多租户与组织模型
2. 租户级数据隔离
3. 组织成员与角色模型重构
4. 客户门户最小闭环
5. 套餐 / 试用 / 订阅基础结构

### P1：把内部系统升级成可复制产品

1. 通用案件主表与统一案件视图
2. 统一任务中心
3. 通用模板中心（阶段 / 任务 / 资料项）
4. 通知中心
5. SaaS 化开通与初始化流程

### P2：再做深做强

1. 更多业务包模板
2. 外部协作者权限
3. 更细的数据范围控制
4. 更强的经营分析与自动化

---

## 7. 最终判断

### 如果问题是：当前系统是否已经满足“内部办案系统”

回答是：**大体满足，而且签证域做得已经比较深。**

### 如果问题是：当前系统是否已经满足 `prd/01` 定义的“可市场化 SaaS MVP”

回答是：**还没有完全满足，目前属于“内部系统较成熟，SaaS 底座不足”的阶段。**

### 最关键的改进方向

不是先继续堆签证功能，而是先补：

- 租户
- 组织
- 通用案件
- 客户门户
- 套餐/试用

只有把这几层补上，这个系统才会从“自用后台”真正变成“可卖的 SaaS 产品”。
