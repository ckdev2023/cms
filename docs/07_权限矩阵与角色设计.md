# 事务所管理系统权限矩阵与角色设计

## 1. 文档目标

本文用于明确系统的一期角色设计和权限控制方式。

本项目是内部小型系统，因此权限设计以“简单够用”为原则，不做过度复杂的层级和数据隔离。

## 2. 权限设计原则

一期建议遵循以下原则：

1. 先按角色控制
2. 先做到菜单、页面、关键按钮三级
3. 后端接口必须做最终权限校验
4. 一个用户可以拥有多个角色
5. 后续如有需要，再增加更细的数据权限

## 3. 一期建议角色

### 3.1 管理员

适用场景：系统负责人、管理人员。

建议权限：

- 可访问全部模块
- 可管理用户和角色
- 可查看日志
- 可处理敏感操作

### 3.2 业务员工

适用场景：日常处理客户、案件、税务资料的员工。

建议权限：

- 可访问客户中心
- 可处理行政书士事务和税理士相关业务
- 可上传和查看文件
- 默认不可管理系统配置
- 默认不可直接处理财务核心操作

### 3.3 财务人员

适用场景：负责请款、收款、预收款登记的人员。

建议权限：

- 可访问财务中心
- 可查看客户基础资料
- 可登记收款、处理预收款
- 可查看财务相关日志

### 3.4 审批人员（可选）

适用场景：需要处理简单审批的主管或负责人。

建议权限：

- 可查看审批中心
- 可审批本人负责范围内的申请
- 不必单独成为固定岗位，可以由管理员或主管兼任

## 4. 权限控制层次

### 4.1 菜单权限

控制用户是否能看到某个模块入口。

例如：

- 是否显示财务中心
- 是否显示系统设置
- 是否显示日志中心

### 4.2 页面权限

控制用户是否能进入某个页面。

例如：

- 客户详情页
- 收款登记页
- 用户管理页

### 4.3 关键按钮权限

控制用户是否能执行关键操作。

例如：

- 删除
- 作废
- 导出
- 审批通过
- 停用账号

### 5.3 操作审计与导出（Phase B）

与 **`docs/35_PhaseB_操作审计与导出口径.md`** 对齐的 **最小闭环**：

| 操作 | 权限码 | 说明 |
| --- | --- | --- |
| 查看操作/登录/导出日志列表 | `log:list` | 与「日志中心」一致 |
| 导出操作审计 CSV | `log:list` | `GET /logs/audit/export.csv`；服务端写入 `export_logs`（`AUDIT_LOG_CSV`）；**不**单独拆「仅导出」权限 |

**原则**：业务数据批量导出若后续立项，须 **另文** 定义字段范围、脱敏与 `export_type`，并回写 `docs/35` / 本节。

## 6. 推荐的数据可见范围

为了避免系统过于复杂，一期建议采用较简单的数据可见策略：

### 6.1 客户与业务数据

- 管理员：可见全部
- 业务员工：默认可见全部客户和业务数据
- 如后续管理需要，再增加“仅本人负责客户”模式

### 6.2 财务数据

- 管理员：可见全部
- 财务人员：可见全部财务数据
- 业务员工：默认不显示核心金额操作页，只保留必要摘要

### 6.3 系统与日志数据

- 管理员：可见全部
- 非管理员：默认不可见系统设置和完整日志
- 操作日志、登录日志、**导出日志**（`export_logs`）的列表查询在后端均使用同一权限码 `log:list`（`PermissionCodes.LOG_LIST`），与 Phase B 口径文档 `docs/35_PhaseB_操作审计与导出口径.md` 一致；触发写入导出日志的附件下载/预览接口仍受 `file:download` 约束。

## 7. 推荐权限编码

为便于后端和前端统一，建议使用权限编码。

### 7.1 菜单权限编码示例

- `dashboard:view`
- `customer:view`
- `admin_case:view`
- `tax:view`
- `finance:view`
- `file:view`
- `approval:view`
- `log:view`
- `system:view`

### 7.2 操作权限编码示例

- `customer:create`
- `customer:update`
- `customer:delete`
- `invoice:create`
- `payment:create`
- `deposit:operate`
- `file:upload`
- `file:delete`
- `approval:submit`
- `approval:approve`
- `user:manage`

## 8. 实现建议

结合现有数据库设计，建议使用以下表实现：

- `users`
- `roles`
- `permissions`
- `user_roles`
- `role_permissions`

实现上建议：

1. 登录后返回当前用户角色和权限编码
2. 前端根据权限控制菜单和按钮显示
3. 后端对关键接口再次校验权限

## 9. 一期不建议做的复杂权限

为了控制开发成本，一期不建议做：

- 复杂组织架构权限
- 很细的字段级权限
- 多级审批链路权限
- 高度灵活的自定义权限编排

这些都可以在系统真正跑起来后，再按实际管理需要补充。

## 10. 结论

本项目权限设计重点不是“做细”，而是“做稳、做简单、做可用”。

一期最重要的是：

- 管理员和普通角色有明显区分
- 财务操作有独立控制
- 系统设置和日志只给少数人
- 删除、审批、收款等关键动作有权限限制

一句话总结：**先做简单清晰的角色权限，再按实际使用情况逐步细化。**
