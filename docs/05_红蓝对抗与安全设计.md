# 事务所管理系统基础安全与风险控制

## 1. 文档目标

本项目是内部使用的小型管理系统，不需要设计成重型安全体系。

本文件的目标不是做复杂红蓝对抗，而是明确：

- 哪些基础安全必须要有
- 哪些风险要避免
- 上线前最少要检查什么

## 2. 安全设计原则

本系统安全建设遵循以下原则：

1. 不过度设计
2. 先满足内部使用场景
3. 重点防误操作、越权和数据丢失
4. 安全措施不能影响员工正常使用效率

## 3. 需要重点保护的内容

虽然系统不大，但以下信息仍然需要保护：

- 客户基础资料
- 行政案件信息
- 税务合同和月次资料
- 收款和预收款记录
- 上传的客户文件
- 员工操作记录

## 4. 一期建议保留的基础安全能力

### 4.1 账号登录

- 员工使用账号密码登录
- 离职或停用账号可立即禁用
- 密码支持修改
- 登录失败记录日志

不建议一期做太复杂的认证能力，例如双因素认证、单点登录等，除非公司已有统一要求。

### 4.2 基础角色权限

建议一期先采用简单角色：

- 管理员
- 普通员工
- 财务人员（如需要）

控制范围建议先做到：

- 菜单权限
- 页面权限
- 关键按钮权限

不建议一期就做很复杂的字段级、行级、组织级权限。

### 4.3 操作日志

以下操作建议记录日志：

- 登录
- 新建客户
- 修改客户
- 删除或作废记录
- 财务登记
- 文件上传 / 删除

日志只要能满足“出了问题知道是谁做的”即可。

### 4.4 删除保护

- 删除操作必须二次确认
- 关键数据建议采用软删除
- 财务记录不建议直接删除，可改为作废或冲正

### 4.5 数据备份

- 数据库定期备份
- 文件目录定期备份
- 至少要验证备份能恢复

### 4.6 可以后置的复杂安全项

以下内容不是一期必须项，可放到二期或三期：

- 双因素认证（2FA）
- 单点登录（SSO）
- 字段级、行级、组织级复杂权限模型
- 自动化安全扫描平台、WAF、SIEM、SOC 类建设
- 全量文件病毒扫描、OCR、电子签章平台集成
- 完整审批流中的双人复核、多级会签和复杂回退
- 自动化渗透测试、攻防演练平台接入

判断原则：如果某能力上线成本高、需要专人维护、且不会显著提升一期业务交付效率，就可以先排后。

## 5. 主要风险与应对

### 5.1 越权查看

风险：普通员工看到不该看的页面或金额。

建议：

- 后端接口做权限校验
- 财务页面与普通业务页面区分
- 敏感按钮仅管理员/财务可见

### 5.2 误删除和误修改

风险：员工误删客户、误改金额、误覆盖文件。

建议：

- 删除二次确认
- 关键表做软删除
- 财务操作留日志
- 文件删除可保留回收区或删除记录

### 5.3 财务重复登记

风险：同一笔收款重复录入，导致账目混乱。

建议：

- 收款登记时显示关联请款和余额
- 提交按钮防重复点击
- 财务记录支持作废，不直接物理删除

### 5.4 文件误操作

风险：文件丢失、覆盖、误删、误上传到错误客户。

建议：

- 上传时显示所属客户
- 文件列表显示上传人和时间
- 删除留记录

### 5.5 数据丢失

风险：服务器故障或人为操作导致数据找不回。

建议：

- 数据库备份
- 文件备份
- 恢复流程至少演练一次

## 6. 上线前最少检查清单

上线前建议至少确认以下事项：

1. 账号登录正常
2. 停用账号无法登录
3. 管理员和普通员工权限有区别
4. 删除操作有确认提示
5. 财务登记有日志
6. 文件上传和删除可追踪
7. 数据库备份已配置
8. 文件备份已配置

## 7. 简化版红蓝对抗理解

如果仍保留“红蓝对抗”这个概念，在本项目里可以做轻量理解：

- 红方关注：误操作、越权、错账、误删、文件丢失
- 蓝方应对：权限、确认、日志、备份、恢复

不需要扩展成复杂安全体系。

## 8. 架构师建议

对这个项目来说，安全重点不是“做多先进”，而是“做得刚刚好”：

- 不影响员工使用
- 能防常见内部问题
- 出问题能追溯
- 数据能找回来

一句话总结：**做基础安全，不做过度安全。**
