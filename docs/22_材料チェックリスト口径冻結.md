## 1. 背景与前置依赖

### 1.1 P0 现状

- `visa_cases.material_status` 为手工维护的摘要字段，枚举值 `NOT_RECEIVED | PARTIAL | COMPLETE`。
- 案件日志（`notes` 扩表）中 `submitted_items` / `missing_items` 为自由文本，不结构化。
- 客户需求（`docs/客户需求.md` §5）明确要求逐项勾选：护照是否已收/已扫描、在留卡是否已收/已扫描、住民票是否已提交、纳税资料是否已提交等。
- PRD（`docs/签证客户中心_PRD_开发版.md` §六 模块 4）将材料状态定位为 checklist 展示。

### 1.2 P1 目标

在 P0 摘要字段基础上，补齐：

- **材料模板**：按签证案件类型预定义通用材料项，减少每案手动录入。
- **案件材料实例**：建案时从模板实例化，支持逐项勾选与补件追踪。
- **家属维度**：部分材料项按家属成员归属，实现"每个成员材料情况"的需求。
- **摘要派生**：基于 checklist 完成度向操作员建议 `material_status`，但 P1 不强制自动写入。

### 1.3 前置依赖

| 依赖 | 说明 |
|------|------|
| P0 全部 S 任务已通过验收 | 确保 `visa_cases`、`visa_case_family_members`、`notes` 扩表、权限/路由/种子数据等基础已稳定 |
| `MaterialStatus` 枚举已冻结 | `NOT_RECEIVED / PARTIAL / COMPLETE`，见 `docs/17_业务口径冻结确认表.md` §1.4 |

## 2. 核心决策：模板 + 案件实例二层模型

### 2.1 结论

**采用「全局模板 + 案件实例」二层模型。**

| 层 | 说明 |
|----|------|
| **模板层**（`material_templates` + `material_template_items`） | 系统级，按案件类型预定义材料分组与材料项。管理者可维护模板。 |
| **实例层**（`visa_case_material_items`） | 案件级，从模板实例化后独立存在。支持逐项勾选、补件标记与自由新增。 |

### 2.2 模板层设计

- 一个模板对应一个 `case_type`（签证案件类型），如"工作签"、"高度人才"、"家族签"等。
- 模板内材料项按 `group_name`（分组名）+ `sort_order` 排列。
- 模板不与具体案件绑定；模板变更不回溯已实例化的案件材料（快照隔离）。
- 如某 `case_type` 无对应模板，建案时实例层为空，操作员手动逐项添加。

### 2.3 实例层设计

- 从模板批量实例化须基于当前案件 `case_type`。**默认何时自动实例化、已有实例时如何按新类型替换**，以 §7 **R9** 与**附录 B** 为准。
- 操作员仍可在材料清单 Tab 主动触发「从模板初始化」（与 `POST /visa-cases/:id/materials/initialize` 等接口幂等语义一致）。
- 实例化后，材料项与模板脱钩——模板后续增删不影响已创建的案件材料项。
- 操作员可在实例层自由新增额外材料项（`template_item_id IS NULL`）。
- 操作员可在实例层标记"不适用"（`is_applicable = false`）来屏蔽模板预设项，而非物理删除。

### 2.4 决策理由

| 备选方案 | 优点 | 缺点 | 结论 |
|----------|------|------|------|
| 纯自由录入（无模板） | 灵活 | 每案手动输入重复度高，容易遗漏；不同操作员命名不一致 | ❌ 否决 |
| 纯模板绑定（无实例脱钩） | 统一管理 | 模板变更影响历史案件；无法做个案定制 | ❌ 否决 |
| **模板 + 实例（快照隔离）** | 标准化与灵活性兼顾；模板变更不破坏历史数据 | 需两层表 | ✅ 采纳 |

**结论**：✅ 冻结。

## 3. 家属维度归属

### 3.1 结论

**材料项支持「案件级」与「成员级」两种归属，通过可选的 `visa_case_family_member_id` 区分。**

| 归属 | 条件 | 示例 |
|------|------|------|
| 案件级 | `visa_case_family_member_id IS NULL` | 申请书正本、手续费入金证明、公司相关书类 |
| 成员级 | `visa_case_family_member_id IS NOT NULL` | 护照复印件、在留卡复印件、住民票、纳税证明 |

### 3.2 实例化规则

- 模板项可标记 `scope = CASE | MEMBER`。
- `CASE` 项：实例化时创建一条（案件级）。
- `MEMBER` 项：实例化时按当前案件已挂载的每个家属成员（含主申请人）各创建一条。
  - 若建案时尚未挂载家属，仅为主申请人（或当前客户上下文）创建一条。
  - 后续新增家属时，可触发"补充实例化"——为新成员追加尚未存在的 `MEMBER` 项。
- 操作员手动新增的额外材料项，自行选择归属（案件级或指定某成员）。

### 3.3 展示规则

- 案件级材料在 checklist 顶部以独立分组展示。
- 成员级材料按家属成员分组展示（主申请人排首位）。
- 标记"不适用"的项默认折叠/隐藏，可展开查看。

### 3.4 家属解绑影响

- 解绑家属时，该成员名下的材料项不物理删除，状态保留可查。
- 前端对已解绑成员的材料项标注"（已解绑）"提示，不允许继续编辑勾选状态。

**结论**：✅ 冻结。

## 4. 与既有 material_status 的并存规则

### 4.1 结论

**P1 阶段 `visa_cases.material_status` 与 checklist 并存；checklist 提供建议值，操作员确认后手动同步。**

### 4.2 派生逻辑（建议值）

根据案件材料实例的勾选情况，系统计算建议的 `material_status`：

| 条件 | 建议值 |
|------|--------|
| 全部适用项均 `is_collected = true` | `COMPLETE` |
| 至少一项 `is_collected = true`，但未全部完成 | `PARTIAL` |
| 无任何 `is_collected = true`（或无材料项） | `NOT_RECEIVED` |

- "不适用"项（`is_applicable = false`）不参与计算。
- "成员级"项中已解绑成员的项不参与计算。

### 4.3 同步方式

- 前端在 checklist 区块展示"建议材料状态：XX"提示。
- 提供"同步到案件"按钮，点击后将建议值写入 `visa_cases.material_status`。
- 操作员也可忽略建议，继续手动在案件编辑中设置 `material_status`。
- P1 不做自动写入（避免操作员对手工流程的信任断裂）。

### 4.4 演进路径

| 阶段 | 行为 |
|------|------|
| P0（当前） | `material_status` 纯手工维护，无 checklist |
| P1（本轮） | checklist + 建议值 + 手动同步按钮 |
| P2（后续） | 可选"自动派生模式"——checklist 变更时自动写入 `material_status`，案件编辑中该字段变为只读 |

**结论**：✅ 冻结。

## 5. 枚举定义

### 5.1 新增枚举

| 枚举 | 值 | 说明 |
|------|----|------|
| `MaterialItemScope` | `CASE`, `MEMBER` | 模板项/实例项的归属维度 |
| `MaterialItemStatus` | `NOT_COLLECTED`, `COLLECTED`, `NOT_APPLICABLE` | 材料项收集状态 |

### 5.2 复用枚举

| 枚举 | 说明 |
|------|------|
| `MaterialStatus`（`NOT_RECEIVED / PARTIAL / COMPLETE`） | 案件摘要字段继续使用，不变更 |

### 5.3 决策说明

- `MaterialItemStatus` 采用三值而非布尔 `is_collected`，是为了在单字段上同时表达"已收集 / 未收集 / 不适用"三种状态，简化查询与统计。
- 实际存储时 entity 使用 `itemStatus: MaterialItemStatus` 单字段，不再拆分 `is_collected` + `is_applicable` 两个布尔列。

**结论**：✅ 冻结。

## 6. 逻辑表结构草案

> 以下为 P1-S1b 建表参考，具体列名与索引在 S1b 落地时确定。

### 6.1 `material_templates`（材料模板）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | uuid PK | |
| `case_type` | varchar(100) | 对应签证案件类型（如 WORK / FAMILY / PR …），唯一约束 |
| `display_name` | varchar(200) | 模板显示名称（如"工作签 通用材料清单"） |
| `is_active` | boolean | 是否启用，停用后新建案件不再引用 |
| `created_at` / `updated_at` | timestamptz | |

### 6.2 `material_template_items`（模板材料项）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | uuid PK | |
| `template_id` | uuid FK → `material_templates` | |
| `group_name` | varchar(100) | 分组名（如"基本書類"、"身分関係書類"、"収入関係書類"） |
| `item_name` | varchar(200) | 材料名（如"パスポートコピー"、"在留カードコピー"） |
| `scope` | varchar(20) | `CASE` / `MEMBER` |
| `sort_order` | int | 组内排序 |
| `is_required` | boolean | 是否必需项（影响建议值计算权重，P1 暂不区分必需/可选权重，预留字段） |
| `created_at` / `updated_at` | timestamptz | |

### 6.3 `visa_case_material_items`（案件材料实例）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | uuid PK | |
| `visa_case_id` | uuid FK → `visa_cases` | |
| `template_item_id` | uuid FK → `material_template_items`, nullable | 为空时表示手动新增项 |
| `visa_case_family_member_id` | uuid FK → `visa_case_family_members`, nullable | 为空时表示案件级 |
| `group_name` | varchar(100) | 实例化时从模板快照；手动项由操作员填写 |
| `item_name` | varchar(200) | 实例化时从模板快照；手动项由操作员填写 |
| `item_status` | varchar(30) | `NOT_COLLECTED` / `COLLECTED` / `NOT_APPLICABLE` |
| `sort_order` | int | |
| `remark` | text, nullable | 备注（如"2026/03/20 提出済み"） |
| `collected_at` | timestamptz, nullable | 标记已收集的时间戳 |
| `created_by` | uuid FK → `users`, nullable | |
| `created_at` / `updated_at` | timestamptz | |

**索引草案**：
- `visa_case_id`（案件下全部材料查询）
- `visa_case_id` + `visa_case_family_member_id`（成员维度查询）
- `visa_case_id` + `item_status`（统计与建议值计算）

## 7. 业务规则与约束

| # | 规则 | 说明 |
|---|------|------|
| R1 | 一个 `case_type` 最多一个活跃模板 | `material_templates` 上 `case_type` + `is_active = true` 唯一 |
| R2 | 实例化后模板脱钩 | 模板项增删不回溯已创建的案件材料实例 |
| R3 | 手动项无 `template_item_id` | 操作员可自由新增，不绑定模板 |
| R4 | 成员级补充实例化 | 新增家属时，自动为该成员补充 `MEMBER` scope 的模板项实例（如模板存在） |
| R5 | 解绑家属不删除材料 | 材料项保留；前端标注"已解绑"并禁止编辑 |
| R6 | 有材料项的案件不物理删除 | 与 P0 案件删除约束一致 |
| R7 | 建议值不自动写入 | P1 仅展示建议 + 手动同步按钮 |
| R8 | `NOT_APPLICABLE` 不参与建议值计算 | 标记"不适用"的项从分子分母中排除 |
| R9 | `case_type` 确定后的材料实例化策略 | **（2026-04-06 修订，详见附录 B）** **新建案件**保存成功后，若材料实例条数为 0 且存在对应活跃模板，服务端**自动**执行与 `POST .../materials/initialize` **幂等语义一致**的实例化（**已实现**：`VisaCaseService.create` 内联调用）。**编辑案件修改 `case_type`** 时：若实例条数为 0，产品上与新建案一致应自动套模板；若已有实例行，**不得静默**清空或覆盖，须显式确认后的替换流程——该编辑路径的服务端与前台闭环**另行任务**交付，**冻结文档不宣称当前已实现**。模板内容变更（非案件 `case_type` 变更）仍不回溯既有实例（与 R2 一致）。 |

| 权限码 | 说明 |
|--------|------|
| `materialTemplate:manage` | 模板 CRUD（仅管理者） |

## 9. 前端展示边界

### 9.1 P1 范围内

- 客户详情 → 签证域 → 选中案件 → "材料清单" 区块。
- 展示按分组和成员维度的 checklist 列表，支持逐项勾选、标注不适用、添加备注。
- 显示完成统计（如"12/15 已收集"）与建议 `material_status`。
- 提供"同步到案件"按钮。
- 提供"新增材料项"入口（手动添加模板外的项）。

### 9.2 系统管理

- 在系统管理菜单下新增"材料模板"子页面，供管理者维护模板与模板项。
- 模板编辑支持分组拖拽排序与 scope（CASE/MEMBER）标记。

### 9.3 不在 P1 范围

- 材料项与案件日志的自动联动（如勾选"已收集"时自动生成一条日志）→ P2 评估。
- Checklist 与案件状态流转的自动联动（如全部收齐自动推进状态）→ P2 评估。
- 材料项的文件上传关联（checklist 项关联具体附件）→ P2 评估。

## 附录 A：`FilePathType` 与 GAP / 业务用语对照（资料路径索引层）

> **用途**：`customer_file_paths.path_type`（`FilePathType`）是**技术枚举**，用于列表筛选与统计；`docs/GAP_ANALYSIS.md` 等需求文档中的「主申路径 / 案件路径 / 家属路径 / 客户档案路径」是**业务叙事**，二者不是 1:1 新增枚举关系。录入时按下表映射到现有 `FilePathType` 即可，避免为同一物理文件夹重复增加枚举值。

| GAP / 业务表述（示例） | 推荐 `FilePathType` | 说明 |
|------------------------|---------------------|------|
| **客户档案路径**（与客户主档绑定、不强调具体案件） | `PERSONAL_DOCUMENT` 或 `OTHER` | 客户级路径（`visa_case_id` 可空）时优先 `PERSONAL_DOCUMENT`；跨案件共用的扫描根目录可用 `OTHER` 并在 `remark` 说明。 |
| **案件路径**（某签证案件材料根目录） | `CASE_DOCUMENT` | 案件级路径（`visa_case_id` 非空）时表示本案共享材料目录。 |
| **主申请人路径**（主申人个人资料子目录） | `PERSONAL_DOCUMENT` | 技术上仍是「个人资料」语义；是否在 UI 标成「主申」依赖 `visa_case_family_members.is_primary` 或操作习惯，不单独占枚举。 |
| **家属路径**（配偶/子女等成员子目录） | `PERSONAL_DOCUMENT` | 同上，成员维度由 `visa_case_id` + 台账备注或所关联家属记录上下文区分，不单开枚举。 |
| **证书 / 合同 / 其他扫描** | `CERTIFICATE` / `CONTRACT` / `OTHER` | 与材料性质强相关时使用；与是否主申/家属无冲突。 |

**录入建议**：优先保证 `file_path` 可复制、可检索；`path_type` 取上表其一即可满足统计与筛选；细粒度「谁的主目录」放在备注或所挂载案件/成员上下文中维护。

## 附录 B：案件 `case_type` 变更与建案时的材料实例化策略（相对原 R9 的补充）

> **用途**：冻结初期 R9 表述为「`case_type` 变更不重新实例化」，意图是**避免案件类型一改就静默清空**既有勾选与备注，造成数据丢失与操作员不信任。随着产品流程收敛（希望保存案件后默认出现与签证类型匹配的完整材料列表），需在**不违背「禁止静默覆盖」**的前提下，对 R9 作**补充与例外**说明；实施以本附录与 §7 R9 为准。

### B.1 原 R9 冻结意图（保留）

- **要防止的行为**：案件 `case_type` 变更时，系统在后台**不经确认**删除或整体替换 `visa_case_material_items`，导致已记录的收集状态、备注、手工行丢失。
- **允许的兜底**：操作员在材料清单 Tab 主动触发「从模板初始化」等**显式动作**（与既有 `POST .../materials/initialize` 幂等语义配合），不视为「静默」。

### B.2 现行产品策略（对原 R9 的补充）

| 场景 | 期望行为 | 说明 |
|------|----------|------|
| **新建案件保存成功** | 若该案尚无材料实例行，**自动**按保存时的 `case_type` 对应活跃模板实例化（含 `CASE` / `MEMBER` 展开规则，与 R4 等一致）。 | **服务端已实现**（建案持久化成功后内联 `initialize`）；减少依赖「记得先打开材料 Tab 再初始化」；与简单视图、标准详情页同源列表展示一致。 |
| **编辑案件：修改 `case_type` 并保存** | **无实例行**：与新建案相同，**自动**按新类型模板实例化。**已有实例行**：**不**自动替换；前端须展示风险说明，操作员**确认**后调用**显式替换**能力（例如专用接口或带强制确认参数的初始化），按**新** `case_type` 模板重建实例层。 | 产品策略与「防静默覆盖」一致；**服务端对「保存编辑且变更 `case_type`」的自动/确认替换尚未与本行同步交付**，实现前操作员仍依赖材料 Tab 的「从模板初始化」等显式动作。 |
| **仅模板内容变更**（`case_type` 未变） | 仍遵循 **R2**：已实例化案件**不**因模板编辑而回溯变更。 | 与 R9 修订不冲突。 |

### B.3 与接口语义的关系（实现指引）

- 既有 **`POST /visa-cases/:id/materials/initialize`** 若约定为「已有实例则跳过」的幂等初始化，则**单独**的「确认后替换」应通过**显式契约**表达（例如独立路由名、或请求体 `replaceExisting: true` 等，以 P1-S1c / OpenAPI 落地为准），**禁止**仅靠普通案件 `PATCH` 在后台顺带清空材料表。
- 替换成功后，前端应刷新材料清单 Tab、简单视图材料卡等依赖 `GET .../materials` 的界面，保证展示与实例表一致。

### B.4 验收口径提示

- **简单视图与标准详情页**：材料块行数与内容与同一 `GET .../visa-cases/:id/materials` 一致；差异来自**实例表数据**，而非另一套缩略规则。
- **手工追加项**（`template_item_id` 为空）在**显式替换**后是否保留，由实现与产品在接口契约中写明（默认策略倾向：**替换以模板为准，手工行不保证保留**，须在确认文案中提示）。

**结论**：原 R9「不自动重实例化」在**禁止静默重置**意义上仍然成立；**允许**在**空清单**时自动实例化，以及在**有清单**时经**显式确认**后按新类型替换。✅ 作为对冻结文档的修订与实施依据采纳。
