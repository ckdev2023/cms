# 并行开发与分支 Worktree 策略

## 1. 文档目标

本文件用于说明如何在保证稳定性的前提下，通过多分支、多 worktree、多窗口方式并行推进开发，并最终稳定合并到 `release`。

## 2. 推荐分支模型

建议采用简单模型：

- `release`：当前可集成、可回归、可演示的稳定分支
- `feature/*`：各模块功能分支
- `hotfix/*`：紧急修复分支

不建议一开始引入过重的 Git Flow 流程，避免流程成本高于项目收益。

## 3. 推荐 worktree 使用方式

建议每个并行任务独立一个 worktree，例如：

- `cms-release`：release 稳定环境
- `cms-auth`：登录 / 用户 / 角色
- `cms-customer`：客户中心
- `cms-tax-finance`：税务 / 财务
- `cms-file`：文件上传下载预览

这样可以同时在多个窗口中推进，不必等待一个窗口完全结束再做下一个。

## 4. 适合并行的任务拆分

建议按模块拆分，而不是按零散页面拆分。

推荐并行方式：

1. 窗口 A：项目骨架、登录、权限、公共组件
2. 窗口 B：客户中心 + 行政书士模块
3. 窗口 C：税理士模块 + 财务模块
4. 窗口 D：文件中心、上传下载、预览
5. 窗口 E：单元测试、接口整理、文档同步

前提是先冻结接口规范、数据库主结构和公共组件边界。

## 5. 并行开发的前置条件

在并行前，必须先稳定以下内容：

- 技术栈固定
- 数据库主表结构初版确定
- API 命名风格确定
- 公共布局、鉴权、请求封装确定
- 公共枚举和字典规则确定

如果这些还不稳定，就不适合全面并行。

## 6. 冲突控制原则

为了减少冲突，建议执行以下规则：

- 一个模块尽量由一个分支主改
- 公共文件先指定负责人
- 接口变更必须先同步文档
- 不要多人同时改同一个路由、菜单、类型定义文件
- 公共组件改动要先说明影响范围

## 7. 与 Cursor / Augment 并行协作建议

可以同时使用多个工具，但要明确边界：

- 一个窗口专注公共骨架和架构
- 一个窗口专注页面和交互
- 一个窗口专注接口和后端实现
- 一个窗口专注测试、回归和文档

核心原则是：**同一时间不要让多个窗口无序改同一批文件。**

## 8. 合并到 release 的建议流程

建议每个功能分支按以下顺序合并：

1. 完成本模块开发
2. 补齐本模块单元测试
3. 自测通过
4. 与 release 做一次同步或 rebase
5. 提交合并请求或人工 review
6. 合并到 release 后立即做一次最小回归

不建议直接把未验证的功能堆到 `release`。

## 9. 质量门禁建议

每个分支合并前至少通过以下检查：

- 前端类型检查通过
- 前端单元测试通过
- 后端单元测试通过
- 关键 API 自测通过
- 关键页面手工 smoke check 通过
- 文档或接口变更已同步

## 10. 速度与稳定的平衡方法

建议采用以下原则：

- 开发时并行，合并时收敛
- 小步提交，小步合并
- 优先模块内闭环，不追求一次做很大
- 公共骨架改动尽量集中处理
- `release` 只保留“当前可演示、可回归”的版本

## 11. 推荐节奏

建议节奏如下：

- 每天同步一次各分支状态
- 每 1~2 天合并一批小功能到 `release`
- 每次合并后做一次基础回归
- 每完成一个主模块做一次可演示版本

一句话总结：**可以多窗口并行，但前提是先冻结公共边界；功能分支快开发，release 分支稳集成。**
