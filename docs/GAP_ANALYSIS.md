# 客户中心业务定位与一期边界说明

> 本文梳理客户中心的本质定位、核心对象、业务流程与一期边界，便于产品与开发对齐口径。

---

## 一、客户中心的本质定位

你们这个「客户中心」，本质上不是普通的客户通讯录，也不是单纯的 CRM，而是：

**以客户主档为基础，以签证案件为核心，以家属关系、材料状态、跟进记录、到期提醒、资料路径为重点的内部业务管理系统。**

也就是说，它要解决的不只是「客户是谁」，而是：

- 客户现在办什么业务
- 是谁在负责
- 主申请人是谁
- 有没有家属一起办理
- 材料交到哪一步
- 上次来干了什么
- 下次该跟进什么
- 资料在本地服务器哪个路径

---

## 二、客户中心要解决的核心问题

你们现在的业务痛点主要有 **5** 个。

### 1. 客户信息分散

客户信息散落在：

- 微信
- LINE
- Excel
- 员工个人记忆

导致：

- 查找困难
- 交接困难
- 容易遗漏

### 2. 业务进度不透明

一个客户到底：

- 现在办的是哪种签证
- 到了哪个阶段
- 缺什么材料
- 什么时候到期

如果没有系统，很难统一掌握。

### 3. 家庭型案件复杂

很多客户不是「一个人一件事」，而是：

- 主申请人
- 配偶
- 子女 1 / 子女 2 / 子女 3

而且家族签还分两种情况：

- 主申请人在你们公司办理
- 主申请人不在你们公司办理，但家属在你们公司办理

所以不能只用「一个客户 = 一个业务」来理解。

### 4. 跟进记录容易断

你们很需要知道：

- 客户这次来交了什么
- 这次沟通说了什么
- 还缺什么
- 下次谁跟
- 什么时候跟

否则换一个同事就接不上。

### 5. 材料与扫描件管理不顺

现在扫描件在本地服务器里，按客户建档保存。系统里如果不能快速定位路径，员工查资料会很慢。

---

## 三、客户中心的业务核心对象

你们这个系统里，真正重要的对象不是只有「客户」，而是 **5** 类核心对象。

### 1. 客户

客户是基础主档，分为两类：

- 个人客户
- 法人客户

客户主档用于统一记录：

- 编号
- 姓名 / 公司名
- 联系方式
- 微信 / LINE
- 负责人
- 状态

这是所有业务的入口。

### 2. 主申请人

主申请人通常是签证案件的核心发起人。

主申请人可能办理：

- 工作签
- 高度人才
- 经营管理签
- 永住申请
- 归化申请

主申请人不一定总是「只有他自己」，很多情况下还会带家属。

### 3. 家属成员

家属成员通常包括：

- 配偶
- 子女
- 父母
- 其他家属

在你们当前设计中，个人客户已经支持：

- 是否为家族成员
- 家族关系
- 主客户关联

这是对的，但在真实业务里还要进一步表达「这个家属签是内部主申请人还是外部主申请人」。

### 4. 签证案件

签证案件才是业务真正流转的中心。

你们当前明确的业务范围主要有这 **6** 类：

- 工作签
- 高度人才
- 经营管理签
- 家族签
- 永住申请
- 归化申请

所以系统里不能只做「客户管理」，还必须做「案件管理」。

### 5. 跟进记录

客户主档上仍有「客户备注」（跟进 / 备忘 / 通用等类型），用于**轻量备忘**。

**与签证域并存时的产品口径**（以 `docs/21_签证客户中心P0验收与Rollout说明.md` §1.4 为准）：**带材料、下次动作、下次跟进时间等结构化要素的业务过程记录，须写在案件日志**（挂在 `visa_cases` 的 `notes`）；客户备注不升级为与案件日志同构的强制要求，避免双写。

## 四、客户中心的真实业务结构

你们最终业务逻辑应该这样理解。

### 结构一：客户主档是基础层

客户主档负责记录「这个人/公司是谁」。

例如：

- 张三
- 李四
- 某某株式会社

### 结构二：签证案件是业务层

签证案件负责记录「这个客户在办什么」。

例如：

- 张三：经营管理签
- 李四：家族签
- 王五：永住申请

### 结构三：家庭关系是关联层

家庭关系负责表达：

- 谁是主申请人
- 谁是附属家属
- 是什么关系
- 是否依附内部主申请人
- 是否依附外部主申请人

### 结构四：跟进记录是过程层（案件日志为主）

**签证案件**上的日志负责记录过程细节：

- 这次发生了什么
- 客户交了什么
- 还缺什么
- 下次要做什么

客户主档备注仅作补充备忘；**日常跟进以案件日志为权威**，与 `docs/21` 职责划分一致。

### 结构五：资料路径是索引层

资料路径负责把系统和本地服务器连接起来。

系统本身不存扫描件，但要知道：

- 资料放在哪里
- 员工如何快速复制路径打开

## 五、你们一期客户中心的核心业务流程

下面是更适合开发理解的流程。

### 场景 1：普通主申请人建档

例如张三来办理经营管理签。

**流程：**

1. 新建客户主档
2. 录入张三基本资料
3. 建立一个签证案件
4. 指定业务类型：经营管理签
5. 填写当前状态、到期时间、负责人
6. 记录资料路径
7. 后续持续写跟进记录

### 场景 2：主申请人 + 家属一起办理

例如张三办理经营管理签，同时配偶和 3 个孩子办理家族签。

**流程：**

1. 建立张三主档
2. 建立张三主案件
3. 录入配偶和孩子客户档案
4. 标记他们与张三的关系
5. 将他们关联为家属成员
6. 为家属建立家族签案件
7. 分别记录材料状态和跟进记录

**注意：** 不是「张三同时有工作签和家族签」，而是「张三是主申请人，家属的家族签依附张三」。

### 场景 3：外部主申请人型家族签

例如：主申请人的工作签不是你们做的，但他的妻子和孩子来你们这里办家族签。

**流程：**

1. 为配偶或子女建立客户主档
2. 建立家族签案件
3. 选择关联方式：外部主申请人
4. 录入外部主申请人信息（姓名、主签类型、到期日、与申请人关系）
5. 后续正常管理材料、跟进、提醒

这一点是你们业务里的特殊逻辑，必须明确进系统。

### 场景 4：客户来访 / 提交材料 / 补件

**流程：**

1. 打开客户详情页，进入**对应签证案件**上下文
2. **新增案件日志**（非客户备注），记录：
   - 本次来访
   - 提交了什么
   - 还缺什么
   - 下次动作
   - 下次跟进时间
3. 如有需要，更新材料状态
4. 如有需要，更新提醒

客户主档备注仅用于轻量备忘；口径见 `docs/21` §1.4。

### 场景 5：到期前提醒续签

**流程（与 `docs/21_签证客户中心P0验收与Rollout说明.md` 对齐）：**

1. **主路径（案件口径）**：以签证案件 `expire_date` 为主，结合案件状态与案件日志，聚合为四类提醒桶（补件、今日待跟进、7 日内到期、2 个月内到期）；业务人员日常从 **签证提醒页**（`/visa-reminders`）与 **签证工作台**（`/workbench/visa`）查看与跳转处理（权限与路由见 `docs/21` §3、§5、§15–§17）。
2. **并列路径（在留卡口径）**：个人客户主档上的 **在留期限**（`person_info.residence_expire_date`）仍在客户详情等界面维护与展示；与案件到期 **独立计算、互不替代**，保留接口 `GET /customers/residence-expiry-reminders`（见 `docs/21` §3.2、§6.4）。
3. 若需区分「在留卡到期」与「签证案件到期」的菜单/书签与实现对账，以 `docs/21` 为验收基线，并以 `docs/GAP_ANALYSIS_实现对照与差距清单.md` 记录与本文草稿字面差异。**勿将「仅主档在留日的旧独立列表页」当作当前唯一或默认入口** — 日常叙事以签证提醒与工作台为主。

**演进说明：** 叙事上已从「仅个人在留统一列表」转为 **案件级提醒为主、在留卡维度并存**；与上文「结构五：资料路径」等章节一致，后续增强仍围绕案件与主档两条线分别收口。

## 六、客户中心的一期业务边界

为了避免系统一开始太重，一期要明确边界。

### 一期必须做的

#### 1. 客户主档

- 个人 / 法人
- 基本信息
- 联系方式
- 负责人

#### 2. 个人签证补充信息

- 国籍
- 在留资格
- 到期日
- 家族关系
- 主客户关联

#### 3. 签证案件基础能力

至少能表达：

- 办什么业务
- 当前状态
- 到期时间
- 下次跟进时间
- 谁负责

#### 4. 家属关系

- 主申请人
- 配偶 / 子女 / 父母 / 其他
- 内部 / 外部主申请人关系

#### 5. 跟进日志（结构化字段落在案件日志）

- 时间
- 记录人
- 类型
- 内容
- 已提交
- 缺失
- 下一步动作
- 下次跟进

（客户主档备注不要求具备上述全部分段，**业务跟进须写案件日志** — `docs/21` §1.4。）

#### 6. 提醒

- **签证域（一期主路径）**：基于 `visa_cases` 的到期、下次跟进与补件等信号，输出四类提醒桶；入口为签证提醒列表与签证工作台（与 `docs/21` §1.1、§6.4、§9 一致）。
- **客户主档在留期限（并列口径）**：基于 `person_info.residence_expire_date` 的旧在留到期提醒接口与展示逻辑 **不**被新提醒替代，与案件级提醒 **并存**（见 `docs/21` §6.4）。

#### 7. 资料路径

- 客户档案路径
- 案件路径
- 主申请人路径
- 家属路径
- 复制路径

### 一期可以先不做的

1. **在线文件预览** — 先不做，第一阶段只做路径。
2. **文件上传** — 先不做。
3. **财务完整闭环** — 你当前文档里财务 Tab 也还是占位状态，这块可以后置。
4. **复杂权限** — 一期先用宽权限，后面再细化。当前文档也明确了一期默认较宽的数据可见性。

## 七、客户中心页面应该围绕什么来设计

如果从业务逻辑看，页面核心应该这样组织。

### 1. 客户列表页

- **作用：** 快速找到客户；快速判断谁急。
- **重点看：** 业务类型；当前状态；到期时间；下次跟进；负责人。

### 2. 新建客户 / 新建案件页

- **作用：** 高效录入主申请人、家属、案件。
- **重点：** 主申请人信息；家属动态添加；家族签模式选择；外部主申请人录入。

### 3. 客户详情页

这是核心页面，应该一页看清：

- 这个客户是谁
- 办什么业务
- 当前到哪一步
- 家属有哪些
- 材料缺什么
- 上次做了什么
- 下次要做什么
- 文件在哪

### 4. 案件日志录入

- **作用：** 高频、快速录入**案件**过程日志（结构化字段）；客户备注弹窗/区块仅作轻量备忘（`docs/21` §1.4）。

### 5. 签证提醒与工作台

- **作用：** 每天打开先看哪些**案件**待补件、待跟进、即将到期；可跳转客户详情签证域或全局案件登记册（`docs/21` §1.1、§5、§15）。
- **与在留卡口径的关系：** 在留卡到期与签证案件到期为两套提醒，侧边栏与主操作路径以 **签证提醒 + 工作台** 为主；在留卡汇总与 API 边界以 `docs/21` §6.4 为准。

## 八、你这个客户中心和「普通 CRM」的最大区别

这一点很重要，你后面和开发沟通时要说清楚。

**普通 CRM 更关注：**

- 销售线索
- 成交过程
- 商机阶段

**而你们这个系统更关注：**

1. **签证业务状态** — 不是「成交没成交」，而是材料准备中 / 已提交 / 审核中 / 需补件 / 已获批。
2. **家庭关系** — 不是单一客户，而是主申请人 + 家属结构。
3. **到期提醒** — 不是销售提醒，而是在留资格续签提醒。
4. **材料状态** — 不是合同附件，而是实际业务材料是否收齐。
5. **本地资料路径** — 不是云盘附件，而是本地服务器文件夹定位。
