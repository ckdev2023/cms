# 事务所管理系统数据库设计

## 1. 设计目标

数据库设计应支撑以下目标：

- 以客户为中心组织全业务数据
- 同时支持行政书士事务与税理士双业务线
- 支撑请款、收款、预收款闭环
- 支撑任务、审批、文件与日志审计
- 具备后续报表与 BI 扩展能力

推荐数据库：**PostgreSQL**。

## 2. 设计原则

1. 主业务表统一使用 UUID 或 BIGINT 作为主键
2. 所有关键业务表保留 `created_at`、`updated_at`
3. 关键表保留 `created_by`、`updated_by`
4. 默认使用软删除字段 `deleted_at`
5. 财务流水采用“流水表 + 汇总视图”模式，避免覆盖式修改
6. 文件采用“元数据入库，文件实体落 NAS/对象存储”模式

## 6. 数据一致性设计

### 6.1 财务一致性

- 收款与请款采用分配表关联，不直接覆盖余额
- 预收款采用流水计算余额，不手工直接改余额
- 金额调整需保留审批记录与日志

### 6.2 文件一致性

- 文件元数据写库成功后再确认实体文件存在
- 定期校验库内路径与 NAS 实体文件是否一致

### 6.3 删除一致性

- 业务主表默认软删除
- 软删除后关联列表默认不可见
- 审计日志独立保存，不随业务删除而删除

## 10. 设计评审与优化建议（基于当前代码实现）

本节基于后端 TypeORM Entity 与迁移文件的“真实落库结构”对本设计文档进行评审，结论与建议以 PostgreSQL 生产可运维为目标，优先覆盖一致性、性能与长期治理。

### 10.1 总体结论

1. **总体合理**：以 `customers` 为中心的领域拆分清晰；主表 UUID 主键 + `timestamptz` 审计字段符合中小规模内部管理系统的工程现实；签证域引入的部分唯一索引与数据范围维度（`teams`/`team_users`）体现了对“幂等 + 性能边界”的前置治理。
2. **需要补齐的核心点**集中在：文档与实现差异、关键唯一约束缺口、列表/时间序查询索引、日志类大表的分区与保留策略、状态枚举的约束化治理。

### 10.2 文档与实现差异（需对齐口径）

以下差异并非设计错误，但会影响评审、联调与运维排障的“单一事实来源”：

1. `customers` 实现已补充 `wechat_id`、`line_id`，建议在 `4.1 customers` 字段表中补齐。
2. `person_info` 实现已扩展家族成员与提醒相关字段：`is_family_member`、`family_relation`、`primary_customer_id`、`remind_days_before`，且 `residence_expire_date` 采用条件索引（`IDX_person_info_residence_expire_date`）。建议在 `4.3 person_info` 中补齐并说明业务含义与查询场景。
3. `notes` 实现已承载“客户备注 + 签证案件日志”双用途：通过 `visa_case_id` 是否为空区分，并新增 `log_type`、`submitted_items`、`missing_items`、`next_action`、`next_follow_up_at`。建议在 `3.1/4.x` 中说明此建模选择的适用边界与后续拆表预案（见 10.4.4）。
4. 签证域已落地表：`visa_cases`、`visa_case_family_members`、`visa_case_material_items`、`material_templates`、`material_template_items`、`customer_file_paths`、`visa_case_import_batches`、`admin_case_visa_supplement_batches` 等，建议在 `3.7` 之外补充“核心字段摘要与关键约束”便于排障与巡检。

### 10.3 关键表结构与约束评审（以风险优先）

#### 10.3.1 主键策略与 UUID 选择

- 现状：全局使用 `uuid_generate_v4()`（见初始迁移）作为主键默认值，工程一致性很好。
- 风险：UUID v4 对 B-Tree 索引局部性不友好，写入量增大后更易产生索引碎片与缓存命中下降。
- 建议：
  - 当前规模可维持不变；若未来出现写入热点或大表（如日志、notes、材料项）显著增长，可评估切换为 **UUID v7 / ULID** 或按表改用 **BIGINT**（仅对新表/新域逐步引入，避免一次性迁移大范围主键）。

#### 10.3.2 软删除与唯一约束的可复用性

- 现状：多数主表含 `deleted_at`（继承 `BaseEntity`）；部分唯一索引已按软删做了部分唯一（如 `visa_cases (customer_id, import_reference)`，`material_templates case_type + is_active`）。
- 关注点：`customers.customer_code`、`invoices.invoice_no`、`payments.payment_no` 等唯一约束不区分软删，意味着软删后不可复用编号。
- 建议：明确业务口径：
  - 若编号要求“全生命周期唯一”，保持现状。
  - 若允许复用（例如测试环境/导入回滚场景），可改为部分唯一索引：`WHERE deleted_at IS NULL`，并评估历史重复数据风险。

#### 10.3.3 财务一致性（账单/收款/分摊/押金）

优点：

- `payment_allocations` 支持多对多核销；押金采用 `deposit_transactions` 流水 + `deposit_accounts.balance` 汇总字段，具备可审计性。

主要缺口与建议：

1. **分摊去重约束**：建议对 `payment_allocations` 增加唯一约束，避免同一收款重复分配到同一账单造成重复核销。
   - 推荐（示例 DDL）：
     - `CREATE UNIQUE INDEX CONCURRENTLY uq_payment_allocations_payment_invoice ON payment_allocations (payment_id, invoice_id);`
2. **金额有效性约束**：为关键金额字段增加 `CHECK`，提前阻断负数或 0 的非法写入（能显著降低数据修复成本）。
   - 示例（上线风险更低的做法）：先 `NOT VALID`，再低峰期 `VALIDATE CONSTRAINT`：
     - `ALTER TABLE payment_allocations ADD CONSTRAINT chk_payment_allocations_amount_positive CHECK (allocated_amount > 0) NOT VALID;`
     - `ALTER TABLE payment_allocations VALIDATE CONSTRAINT chk_payment_allocations_amount_positive;`
3. **押金流水可追溯索引**：`deposit_transactions` 当前仅索引 `deposit_account_id`，建议补充按时间倒序查询的复合索引，便于“最近流水/对账”与减少排序开销：
   - `CREATE INDEX CONCURRENTLY idx_deposit_transactions_account_created_at ON deposit_transactions (deposit_account_id, created_at DESC);`
4. **业务一致性规则**（跨行约束）如“累计核销金额不得超过账单应收”“balance_after 必须等于上一笔余额 + amount”等，数据库层可用触发器实现，但会增加复杂度与锁风险。建议先在服务层强校验 + 审计，待需求稳定后再评估数据库触发器或批量对账任务。

#### 10.3.4 税务月次周期唯一性

- 现状：`tax_periods.period_ym` 未体现唯一约束。
- 风险：同一合同同一期间重复生成会导致统计口径与 UI 展示混乱，后续清理成本高。
- 建议：增加部分唯一约束（未软删行）：
  - `CREATE UNIQUE INDEX CONCURRENTLY uq_tax_periods_contract_period ON tax_periods (tax_contract_id, period_ym) WHERE deleted_at IS NULL;`

#### 10.3.5 签证域：家族签/材料 checklist/导入幂等

优点：

- 家族签：`visa_case_family_members` 通过“部分唯一索引（每案唯一主申）+ 联合唯一（同案同客户不重复）”约束得当。
- 导入：`visa_case_import_batches.content_sha256` 全表唯一 + `visa_cases.import_reference` 客户维度部分唯一，幂等链路清晰。
- 列表性能：`visa_cases` 对 `case_status / fee_status / material_status` 建立“仅未软删”的部分索引，符合成本与收益平衡。

建议补充：

1. **材料实例去重约束**：若业务规则为“同一案件同一成员同一模板项只允许一条实例”，建议增加唯一约束，防止重复实例化或并发操作造成脏数据：
   - `CREATE UNIQUE INDEX CONCURRENTLY uq_vcmi_case_member_template_item ON visa_case_material_items (visa_case_id, visa_case_family_member_id, template_item_id) WHERE template_item_id IS NOT NULL;`
2. **案件日志/备注的时间序索引**：`notes` 同时承担两类数据，建议补充两个常用读取模式的部分索引，降低列表页与提醒页的排序开销：
   - 客户备注列表：`CREATE INDEX CONCURRENTLY idx_notes_customer_created_at ON notes (customer_id, created_at DESC) WHERE visa_case_id IS NULL AND deleted_at IS NULL;`
   - 案件日志列表：`CREATE INDEX CONCURRENTLY idx_notes_visa_case_created_at ON notes (visa_case_id, created_at DESC) WHERE visa_case_id IS NOT NULL AND deleted_at IS NULL;`

### 10.4 性能与可运维治理建议（按优先级）

#### 10.4.1 P0（近期即可落地，低风险高收益）

1. 补齐关键唯一约束：`payment_allocations (payment_id, invoice_id)`、`tax_periods (tax_contract_id, period_ym)`、材料实例去重（如适用）。
2. 补齐时间序查询索引：`deposit_transactions (deposit_account_id, created_at desc)`、`notes` 两类列表的部分索引。
3. 对“枚举字符串列”逐步增加 `CHECK` 或改为 PostgreSQL ENUM（建议先从最关键的状态列开始，如 `customers.status`、`invoices.status`、`visa_cases.case_status`）。

#### 10.4.2 P1（规模上来后的治理项）

1. 大表分区与保留：建议对 `audit_logs`、`login_logs`、`export_logs`、`notes` 评估按月 RANGE 分区（以 `occurred_at/created_at` 为分区键），并制定保留周期与归档策略。
2. 模糊检索优化：若客户名称支持模糊搜索（`ILIKE '%xxx%'`），建议启用 `pg_trgm` 并建立 `GIN` 索引（注意：会增加写入成本，应以真实慢查询证据为准）。
3. UUID 写入局部性：评估 UUID v7/ULID 或关键大表改用 BIGINT（仅在确有写入压力时进行）。

#### 10.4.3 P2（高可靠与可恢复体系）

1. 明确 RPO/RTO：内部系统仍建议做到“可恢复优先”，至少具备可演练的恢复流程。
2. 备份策略（建议）：每日一次全量备份 + WAL 归档（PITR），并每月做一次恢复演练；重要版本发布前做快照与回滚预案。
3. 监控与告警（建议最小集）：连接数、慢查询、锁等待/死锁、复制延迟（如有）、磁盘使用率与表膨胀（bloat）、autovacuum/分析状态、关键业务表行数增长。

#### 10.4.4 关于 `notes` 复用承载“客户备注 + 案件日志”的边界

现状复用能减少表数量与开发成本，但需明确适用边界：

1. 如果两类数据的增长速度、权限口径、生命周期（保留/归档）出现显著差异，建议拆出 `visa_case_logs` 专表，避免单表成为“冷热混合 + 索引膨胀”的长期负担。
2. 若继续复用，必须依赖部分索引与约束来保证查询路径清晰（见 10.3.5、10.4.1）。

### 10.5 总 DBA 补充检查清单（容易遗漏但生产高频）

#### 10.5.1 PostgreSQL 初始化前置条件（强依赖）

1. `uuid_generate_v4()` 依赖扩展：生产库需启用 `uuid-ossp`，否则迁移会失败。若不允许启用该扩展，可改用 `pgcrypto` 的 `gen_random_uuid()` 并统一迁移默认值策略。
2. 时区口径：数据库会话时区与应用时区需统一（当前字段使用 `timestamptz`，建议应用层固定为 `Asia/Tokyo` 或 `UTC`，并在文档中明确）。
3. 字符集与排序规则：建议明确 `UTF-8`，并对“按名称排序/检索”场景提前确认 collation 口径，避免跨环境排序不一致。

#### 10.5.2 约束体系：哪些必须用数据库兜底

建议明确分层策略，避免“全靠应用代码”的长期漂移风险：

1. 必须数据库兜底：唯一键、外键、关键金额 `CHECK`、核心状态 `CHECK/ENUM`。
2. 可以应用兜底：跨行累计规则（如核销不超账单）、复杂状态机流转（先服务层校验 + 审计，必要时再引入触发器/存储过程）。
3. 软删除口径：需要统一说明“业务删除=软删除”，并明确哪些表允许物理清理（如日志归档后物理删除）。

#### 10.5.3 索引与查询：高频但文档常漏

1. 时间序列表（倒序分页）建议在文档中明确标准索引形态：`(fk_id, created_at desc)`，并对软删/空值字段优先用部分索引。
2. 审计查询常用路径：建议为 `audit_logs` 补充对象维度索引（示例）：
   - `CREATE INDEX CONCURRENTLY idx_audit_logs_target_time ON audit_logs (target_type, target_id, occurred_at DESC);`
3. 多态关联（`files.related_id/related_type`、`invoices.related_id/related_type`）无法用 FK 约束，至少需要：
   - 明确业务口径（允许为空、允许哪些类型）
   - 复合索引（示例）：`(related_type, related_id)`，并在数据修复手册中定义“孤儿记录”扫描 SQL

#### 10.5.4 大表治理：分区、保留、真空与膨胀

1. 需定义保留周期：`login_logs`、`audit_logs`、`export_logs`、`notes`（尤其 notes 复用）建议至少写清“保留多久、是否归档、谁触发清理”。
2. 分区策略建议写明触发阈值：当表行数/增长率达到一定量级再启用按月分区，避免过度设计；同时定义归档表/冷存储方案。
3. 运维侧必备：`autovacuum` 与 `ANALYZE` 观测指标、表膨胀（bloat）巡检与告警触发条件。

#### 10.5.5 变更与发布：迁移纪律与回滚

1. 明确迁移策略：避免手工改库，所有 DDL 经迁移落地；生产添加索引优先 `CONCURRENTLY`，避免长时间阻塞写入。
2. 高风险 DDL 需拆步：先加列/索引/约束 `NOT VALID`，上线后低峰期 `VALIDATE`；回滚策略需写清（尤其是删除列/改类型）。
3. 数据修复与审计闭环：对“修复脚本/回填脚本”要求写入 `audit_logs`，并保留执行人、范围与结果摘要。

#### 10.5.6 连接与事务安全阈值（建议默认）

为避免慢查询、长事务与锁等待对小团队生产库造成“雪崩式扩散”，建议在数据库与应用侧同时设置最小安全阈值（可按业务放宽，但不建议为空）。

1. 数据库侧建议参数（示例）：
   - `statement_timeout = '60s'`
   - `lock_timeout = '5s'`
   - `idle_in_transaction_session_timeout = '60s'`
   - `deadlock_timeout = '1s'`
2. 应用侧建议（原则）：
   - 连接池上限与数据库 `max_connections` 协调，预留运维与迁移连接余量。
   - 对“列表页/统计页/导出”按接口维度设置超时与分页上限，避免一次请求拖垮共享资源。

#### 10.5.7 日志与大表保留周期（建议默认）

建议将“保留多久、是否归档、谁触发清理”写成可执行口径，避免长期堆积导致性能退化与备份窗口失控：

1. 默认保留建议（可按合规要求调整）：
   - `login_logs`：保留 12 个月，超过部分归档或物理清理。
   - `export_logs`：保留 24 个月，便于追责与问题定位。
   - `audit_logs`：保留 24 个月（若涉及更高合规要求可更长），清理前需确保归档与对账。
   - `notes`：默认长期保留；若增长明显，按“客户备注/案件日志”分别设定归档与冷热分层策略。
2. 分区启用阈值建议（避免过度设计）：
   - 单表行数达到 1,000 万级或月增量达到 100 万级，优先评估按月 RANGE 分区（以 `occurred_at/created_at` 为键）。
   - 分区后必须配套“自动创建下月分区 + 归档/清理过期分区”的运维任务。

#### 10.5.8 `tax_periods.period_ym` 数据质量约束（避免脏数据）

`period_ym` 作为期间主标识，建议用数据库约束兜底，防止出现 `2026-3`、`2026/03`、`2026-13` 等脏值导致口径漂移：

1. 推荐约束（示例）：
   - `ALTER TABLE tax_periods ADD CONSTRAINT chk_tax_periods_period_ym_format CHECK (period_ym ~ '^\\d{4}-(0[1-9]|1[0-2])$') NOT VALID;`
   - `ALTER TABLE tax_periods VALIDATE CONSTRAINT chk_tax_periods_period_ym_format;`
2. 替代方案：改为 `period_month date`（保存月首日，如 `2026-03-01`）并配合唯一索引，统计更直接，但需要一次数据迁移与接口口径同步。

#### 10.5.9 多态关联“孤儿记录”巡检 SQL（模板）

`files` 与 `invoices` 的 `related_type/related_id` 属多态关联，无法用外键强约束，建议至少建立“可巡检”的孤儿扫描脚本模板，并纳入巡检/告警。

1. `files`（示例模板，需按业务映射补齐 join 对象）：

```sql
WITH candidates AS (
  SELECT id, related_type, related_id, created_at
  FROM files
  WHERE deleted_at IS NULL
    AND related_id IS NOT NULL
)
SELECT *
FROM (
  SELECT c.*, 'ADMIN(admin_cases)' AS expected_table
  FROM candidates c
  LEFT JOIN admin_cases ac ON c.related_type = 'ADMIN' AND c.related_id = ac.id
  WHERE c.related_type = 'ADMIN' AND ac.id IS NULL

  UNION ALL
  SELECT c.*, 'TAX(tax_contracts)' AS expected_table
  FROM candidates c
  LEFT JOIN tax_contracts tc ON c.related_type = 'TAX' AND c.related_id = tc.id
  WHERE c.related_type = 'TAX' AND tc.id IS NULL

  UNION ALL
  SELECT c.*, 'FINANCE(invoices/payments/...)' AS expected_table
  FROM candidates c
  WHERE c.related_type = 'FINANCE'
) t
ORDER BY created_at DESC;
```

2. `invoices`（示例模板，需按 `related_type` 的真实含义补齐）：

```sql
SELECT id, related_type, related_id, created_at
FROM invoices
WHERE deleted_at IS NULL
  AND related_id IS NOT NULL
  AND related_type IS NOT NULL;
```

建议在项目内明确 `related_type -> 允许的表` 映射表（即使只写在文档里），否则该字段会成为长期数据修复成本来源。
