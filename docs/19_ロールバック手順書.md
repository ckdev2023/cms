# ロールバック手順書

> **窓口**：F2  
> **作成日**：2026-03-20  
> **対象**：事務所管理システム 一期（P0）

---

## 1. ロールバック方針

### 1.1 基本原則

- ロールバックの判断基準：**本番デプロイ後にシステムが正常動作しない**、またはデータ破損の恐れがある場合
- 判断タイムリミット：デプロイ後 **30 分以内** に主要機能の動作確認が完了しなければロールバックを検討
- ロールバック実行者：管理者（サーバーアクセス権保有者）

### 1.2 ロールバック対象

| レベル | 内容 | 影響範囲 | 所要時間 |
|--------|------|---------|---------|
| L1 | バックエンドのみ巻き戻し | API のみ | 約 2 分 |
| L2 | フロントエンド + バックエンド巻き戻し | 全体 | 約 3 分 |
| L3 | L2 + データベース巻き戻し | 全体 + データ | 約 10-15 分 |

---

## 2. L1：バックエンドのみロールバック

**使用場面**：API エラーが発生しているが、フロントエンドは正常。DB スキーマ変更がないデプロイの場合。

```bash
# 1. 前回のリリーススナップショットを確認
ls -lt /opt/cms/releases/

# 2. バックエンドを前のバージョンに戻す
PREV_RELEASE="20260320_120000"  # 前回のタイムスタンプに置換
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/backend-dist/" \
    "/opt/cms/backend/dist/"

# 3. PM2 再起動
pm2 reload cms-backend

# 4. ヘルスチェック
sleep 3
curl -s http://127.0.0.1:3000/api/v1/health

# 5. 動作確認
pm2 logs cms-backend --lines 20
```

---

## 3. L2：フロントエンド + バックエンドロールバック

**使用場面**：フロントエンドとバックエンド両方に問題がある場合。

```bash
# 1. 前回のリリーススナップショットを確認
ls -lt /opt/cms/releases/
PREV_RELEASE="20260320_120000"  # 前回のタイムスタンプに置換

# 2. バックエンドを戻す
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/backend-dist/" \
    "/opt/cms/backend/dist/"

# 3. フロントエンドを戻す
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/frontend-dist/" \
    "/opt/cms/frontend/dist/"

# 4. PM2 再起動
pm2 reload cms-backend

# 5. Nginx リロード（キャッシュクリア）
sudo nginx -s reload

# 6. 動作確認
sleep 3
curl -s http://127.0.0.1:3000/api/v1/health
echo "ブラウザでフロントエンドの表示を確認してください"
```

## 4. L3：データベースを含む完全ロールバック

**使用場面**：マイグレーションがデータ破損を引き起こした、または DB スキーマ変更が原因で障害が発生した場合。

> ⚠️ **注意**：DB ロールバックを行うと、デプロイ後に入力されたデータは失われます。

### 4.1 方法A：マイグレーションの巻き戻し（推奨）

マイグレーションに `down()` メソッドが実装されている場合に使用可能。

```bash
# 1. アプリケーションを停止
pm2 stop cms-backend

# 2. マイグレーションを 1 つ巻き戻す（必要に応じて繰り返す）
cd /opt/cms/backend
npx typeorm migration:revert -d dist/data-source.js

# 3. コードを前バージョンに戻す（L2 の手順 2-3）
PREV_RELEASE="20260320_120000"
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/backend-dist/" \
    "/opt/cms/backend/dist/"
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/frontend-dist/" \
    "/opt/cms/frontend/dist/"

# 4. アプリケーションを再起動
pm2 start cms-backend

# 5. 動作確認
sleep 3
curl -s http://127.0.0.1:3000/api/v1/health
```

### 4.2 方法B：バックアップからの完全復元

マイグレーションの巻き戻しが不可能な場合、または破損が深刻な場合。

```bash
# 1. アプリケーションを停止
pm2 stop cms-backend

# 2. デプロイ前のバックアップを特定
ls -lt /data/backups/db/
BACKUP_FILE="/data/backups/db/jimusho_cms_20260320_020000.dump"

# 3. 本番 DB にリストア（要確認プロンプト）
/opt/cms/scripts/restore-db.sh "${BACKUP_FILE}" --target-db jimusho_cms

# 4. コードを前バージョンに戻す（L2 の手順 2-3）
PREV_RELEASE="20260320_120000"
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/backend-dist/" \
    "/opt/cms/backend/dist/"
rsync -a --delete \
    "/opt/cms/releases/${PREV_RELEASE}/frontend-dist/" \
    "/opt/cms/frontend/dist/"

# 5. アプリケーションを再起動
pm2 start cms-backend
sudo nginx -s reload

# 6. 動作確認
sleep 3
curl -s http://127.0.0.1:3000/api/v1/health
```

## 5. ファイルストレージのロールバック

**使用場面**：ファイルの削除や破損が発生した場合。

```bash
# NAS バックアップからの復元
rsync -avz \
    /mnt/nas/cms-backup/files/ \
    /data/cms-files/

# 特定ディレクトリのみ復元する場合
rsync -avz \
    /mnt/nas/cms-backup/files/CUSTOMER/2026/03/ \
    /data/cms-files/CUSTOMER/2026/03/
```

## 6. ロールバック後の対応

| # | 対応項目 | 説明 |
|---|---------|------|
| 1 | 原因調査 | PM2 ログ、Nginx ログ、PostgreSQL ログを確認 |
| 2 | 影響範囲の特定 | どの機能が影響を受けたか、データ損失の有無 |
| 3 | 修正対応 | バグ修正後、開発環境で再テスト |
| 4 | 再デプロイ | 修正確認後、通常のデプロイ手順で再デプロイ |
| 5 | 報告 | ロールバック理由、影響、対応内容を記録 |

## 7. 緊急連絡先・ログ場所

### 7.1 ログファイル一覧

| ログ | パス |
|------|------|
| PM2 アプリログ | `/var/log/cms/pm2-out.log` |
| PM2 エラーログ | `/var/log/cms/pm2-error.log` |
| Nginx アクセスログ | `/var/log/nginx/cms_access.log` |
| Nginx エラーログ | `/var/log/nginx/cms_error.log` |
| DB バックアップログ | `/var/log/cms/backup-db.log` |
| ファイルバックアップログ | `/var/log/cms/backup-files.log` |
| PostgreSQL ログ | `/var/log/postgresql/` |

### 7.2 よく使うコマンド

```bash
# PM2 ステータス
pm2 status
pm2 logs cms-backend --lines 50

# Nginx
sudo nginx -t
sudo systemctl status nginx
tail -f /var/log/nginx/cms_error.log

# PostgreSQL
sudo -u postgres psql -d jimusho_cms -c "SELECT count(*) FROM users;"

# ディスク使用量
df -h
du -sh /data/cms-files/
du -sh /data/backups/db/
```

## 8. デプロイ前バックアップ必須ルール

**毎回のデプロイ前に必ず実行**：

```bash
# 1. 手動で DB バックアップを取る
/opt/cms/scripts/backup-db.sh

# 2. バックアップ成功を確認
ls -lt /data/backups/db/ | head -3

# 3. デプロイ実行
./scripts/deploy.sh
```

> デプロイスクリプト（`deploy.sh`）は自動的にコードのリリーススナップショットを作成しますが、**DB バックアップは手動で事前に実行**してください。
