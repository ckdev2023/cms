# 事务所管理系统需求分析与开发说明

## 1. 文档目的

本文基于以下源文件整理：

- `事务所系统_完整开发规格书.docx`
- `系统详细功能说明.docx`

目标是将原始需求转化为便于开发、设计、排期和验收的 Markdown 开发文档。

## 2. 项目概述

该系统面向 **行政书士事务 + 税理士事务所**，用于统一管理客户、业务案件、税务服务、财务收支、内部任务审批、文件资料与操作日志。

系统核心设计原则：

1. **客户中心化**：`Customers` 为核心主表，绝大部分业务数据通过 `CustomerID` 关联。
2. **双业务一体化**：同时支持行政书士事务业务、税理士业务，且允许同一客户存在双业务关系。
3. **业务财务联动**：从客户资料、案件/合同，到请款、收款、预收款形成闭环。
4. **内部管理可追踪**：任务、审批、日志、文件归档统一管理。

## 3. 建设目标

### 3.1 业务目标

- 统一客户入口，避免客户信息分散
- 支持行政案件与税务顾问业务并行处理
- 提高请款、收款、预收款结算的可追踪性
- 建立事务所内部任务与审批流程
- 实现客户资料与业务文件统一归档
- 保证关键操作有日志留痕

### 3.2 管理目标

- 快速查看客户全貌
- 减少跨模块重复录入
- 提升案件与申报期限管理效率
- 提供后续报表、提醒、BI 分析扩展基础

| ------ | ------------------------------------------------ |
| 管理员 | 全部模块访问、用户管理、审批、日志查看、系统配置 |
| 员工   | 按授权访问客户、案件、税务、财务、文件、任务     |

### 5.1 建议补充的权限维度

- 财务数据是否对普通员工隐藏金额字段
- 删除、审批、导出、日志查看是否需要单独授权

## 6. 业务主流程

源文档给出的核心操作逻辑如下：

`客户 -> 行政/税务 -> 请款 -> 入金 -> 预收款 -> 任务 -> 备忘`

可整理为以下业务闭环：

1. 新建客户（个人/法人）
2. 选择服务类型（行政 / 税务 / 双业务）
3. 建立行政案件或税务顾问/申报事项
4. 记录业务进度、期限、提交资料、面谈记录
5. 生成请款记录
6. 登记收款与预收款
7. 进行预收款结算
8. 通过任务、备忘、文件持续跟进
9. 通过日志追踪关键操作

## 7. 功能需求拆解

### 7.1 客户管理模块

**核心目标**：建立统一客户主档，作为所有业务入口。

**明确功能**：

- 个人 / 法人客户注册
- 客户编码管理
- 基础信息维护
- 服务类型选择（行政 / 税务 / 双业务）
- 客户详情统一入口
- 客户查询与过滤

**关键字段**：

`CustomerID, CustomerCode, CustomerType, CustomerName, Phone, Email, Address, ServiceType`

**扩展子表**：

- `CompanyInfo`：法人信息
- `PersonInfo`：个人信息

**开发要点**：

- 客户详情页需聚合显示共通信息、法人/个人信息、相关案件、财务、任务、备忘、文件
- 同一客户必须支持挂接多个业务记录
- 需要提供快速跳转到行政、税务、财务等模块的入口

### 7.2 行政书士事务模块

**核心目标**：管理行政案件及在留资格相关业务。

**明确功能**：

- 行政案件管理
- 在留资格管理
- 面谈记录
- 提交资料管理
- 行政任务管理

**关键字段**：

`AdminCaseID, CustomerID, ApplicantName, ResidenceStatus, ExpireDate, Status`

**开发要点**：

- 案件需与客户直接关联
- 必须支持案件状态与到期日管理
- 面谈记录、提交资料应支持按客户/案件归档查看
- 建议预留状态流转字段，如“受理中/材料待补/已提交/完成”

### 7.3 税理士模块

**核心目标**：管理顾问合同、月次资料、月次业务和申报期限。

**明确功能**：

- 顾问合同管理
- 月次资料管理
- 月次业务进度管理
- 年末调整
- 申报期限管理

**关键对象**：

`MonthlyDocuments, MonthlyWork, TaxContracts`

**开发要点**：

- 需支持客户税务服务周期管理
- 月次资料与月次业务应有期间维度（年月）
- 应能清晰看到“资料是否到齐、月次是否完成、申报是否临期”
- 建议将“顾问合同”和“具体月次作业”拆成不同数据实体

### 7.4 财务模块

**核心目标**：形成从请款到收款、预收款结算的财务闭环。

**明确功能**：

- 请款管理
- 收款管理
- 预收款管理
- 预收款结算

**关键对象**：

- `Invoices`
- `Payments`
- `Deposits`

**开发要点**：

- `Payments` 通过 `InvoiceID` 关联请款记录
- `Deposits` 通过 `CustomerID` 维护客户预收余额
- 应支持客户维度查看应收、已收、预收余额
- 建议确认是否支持部分收款、超额收款、预收转抵、退款

### 7.5 事务所管理模块

**核心目标**：支持内部执行、申请审批和人员管理。

**明确功能**：

- 任务管理
- 内部申请 / 内部请款
- 审批
- 用户管理
- 操作日志

**关键对象**：

`Tasks, InternalClaims, Users, Logs`

**开发要点**：

- 任务应支持关联客户，也应支持纯内部任务
- 审批流程需确认发起人、审批人、状态、意见字段
- 用户管理至少应包含账号、角色、启停用状态

### 7.6 文件管理模块

**核心目标**：统一管理客户和业务文件，支持快速打开。

**明确功能**：

- 客户文件夹管理
- 行政 / 税务文件分离
- 文件路径保存与一键打开

**关键字段**：

`FilePath, CustomerID`

**开发要点**：

- 至少需要客户级文件夹、行政文件夹、税务文件夹三层概念
- 文档当前更偏“路径管理”，未明确是否做文件上传
- 若依赖 NAS，则需确认路径命名规则、权限映射、一键打开方式

### 7.7 日志系统

**核心目标**：实现审计追踪。

**明确功能**：

- 登录日志
- 操作记录
- 删除记录

**关键字段**：

`LogID, UserID, Action, DateTime`

**开发要点**：

- 建议增加 `TargetType, TargetID, BeforeValue, AfterValue` 等字段
- 删除操作建议采用“软删除 + 删除日志”模式

## 11. 红蓝对抗与异常场景需求

本章节从“红队攻击 / 滥用 / 误操作 / 流程绕过”与“蓝队防护 / 审计 / 恢复”两个视角补充需求，用于弥补原始需求文档在安全性、可追溯性和异常场景上的不足。

### 11.1 账号与认证安全

需补充以下要求：

- 明确登录方式：账号密码、是否支持单点登录、是否需要双因素认证
- 密码强度策略、重置策略、初始密码失效策略
- 连续登录失败锁定机制
- 会话超时、异地登录提醒、强制下线机制
- 离职或停用员工账号的回收流程

建议最少实现：

- 登录失败次数限制
- 会话超时自动退出
- 管理员可手动停用账号
- 登录成功 / 失败均写入日志

### 11.2 权限控制与越权防护

原文仅区分“管理员 / 员工”不足以支撑真实场景，建议权限设计至少拆为四层：

1. 模块权限：是否能进入某模块
2. 数据权限：能看全部客户还是仅看本人负责客户
3. 字段权限：能否看到金额、证件信息、在留资格等敏感字段
4. 操作权限：新增、编辑、删除、审批、导出、打印等动作是否允许

建议补充规则：

- 客户需支持“负责人 / 协同人 / 所属组”机制
- 财务数据对非财务角色可按字段脱敏或隐藏
- 审批、删除、批量导出、日志查看应单独授权
- 文件访问权限需跟随客户或案件权限继承

### 11.3 审计日志与追责能力

当前 `Logs` 表定义过于简略，建议扩展至少包含：

- `TargetType`：操作对象类型
- `TargetID`：操作对象 ID
- `ActionType`：新增、修改、删除、导出、审批、登录等
- `BeforeValue` / `AfterValue`：关键字段变更前后值
- `IPAddress` / `DeviceInfo`
- `Result`：成功 / 失败
- `OccurredAt`

建议按场景拆分日志：

- 登录日志
- 数据变更日志
- 删除日志
- 审批日志
- 文件下载 / 打开 / 导出日志
- 批量操作日志

### 11.4 删除、修改与恢复机制

需要防止误删、恶意删除和无痕篡改：

- 关键业务数据默认采用软删除
- 删除前需二次确认
- 财务记录不建议直接覆盖修改，应支持冲正 / 作废 / 重开
- 关键记录需保留版本历史或变更快照
- 回收站与恢复机制需明确适用范围和保留时长

建议重点保护对象：

- 客户主档
- 行政案件
- 税务月次记录
- 请款 / 收款 / 预收款记录
- 审批单据

### 11.5 财务异常场景控制

财务模块需补充异常与边界场景，否则容易出现账实不符：

- 一张请款单多次收款
- 部分收款
- 超额收款
- 预收款转抵
- 退款 / 冲销
- 重复入金
- 作废后重开
- 金额修改后的审批与留痕

建议补充财务状态机：

- 请款状态：待发送 / 已发送 / 部分收款 / 已收清 / 已作废
- 收款状态：已登记 / 已核销 / 已退款 / 已冲正
- 预收款状态：可用 / 已部分结算 / 已结清 / 已退款

### 11.6 文件与资料安全

文件管理目前更像“路径管理”，仍需补充安全要求：

- 明确是仅保存路径，还是支持上传、下载、预览
- 文件访问是否完全继承客户 / 案件权限
- 文件下载、预览、删除必须留痕
- 文件重名、覆盖、版本控制规则
- NAS 路径白名单与非法路径拦截
- 敏感资料是否需要水印或禁止批量导出

建议至少区分以下文件类别：

- 客户基础资料
- 行政案件资料
- 税务资料
- 财务附件
- 内部审批附件

### 11.7 审批防绕过设计

事务所管理模块中的申请与审批需避免流程被绕过：

- 发起人与审批人不能为同一人（如业务上确需允许，必须留痕并可配置）
- 审批流需定义：待审 / 已通过 / 已驳回 / 已撤回 / 已转审
- 审批通过后关键字段应锁定，若修改则需重新发起审批
- 审批意见、审批时间、审批人必须完整保留
- 禁止前端绕过审批直接修改最终状态

建议需审批的事项至少包括：

- 内部请款 / 申请
- 大额金额修改
- 关键客户资料删除
- 批量导出敏感数据

### 11.8 备份、容灾与恢复

原文仅写“自动备份（Server）”，不足以支撑上线。建议明确：

- 备份频率（如每日、每小时增量）
- 备份保留周期
- 数据库与 NAS 文件是否统一备份
- 恢复时间目标（RTO）
- 数据丢失容忍目标（RPO）
- 是否异地备份
- 是否定期做恢复演练

重点是保证：

- 数据库恢复后，文件索引与文件实体一致
- NAS 故障不会造成文件完全不可恢复
- 误删可在可接受时间内恢复

### 11.9 敏感信息保护与合规

本系统涉及大量敏感信息，应明确分类分级：

- 客户基础身份信息
- 国籍、在留资格等个人敏感信息
- 法人信息与企业编号
- 金额、收款、预收款等财务信息
- 申请材料、证件、报税资料

建议补充：

- 敏感字段脱敏展示规则
- 高敏信息导出审批
- 敏感数据最小可见原则
- 数据保留期限与销毁策略
- 离职员工权限与访问痕迹审计

### 11.10 并发、重复提交与误操作防护

需考虑多用户同时操作导致的数据冲突：

- 同一客户资料被多人同时修改
- 同一请款单被重复登记收款
- 同一审批单被重复提交
- 网络中断导致用户重复点击提交

建议实现：

- 乐观锁或更新时间戳校验
- 表单提交幂等控制
- 重复提交拦截
- 并发冲突提示与刷新机制

### 11.11 通知与提醒安全

若后续接入自动提醒和 Google 日历联动，需同时定义：

- 提醒触发条件
- 提醒接收对象
- 提醒失败后的重试策略
- 重复提醒去重规则
- 提醒内容是否包含敏感信息
- 站内消息、邮件、日历同步之间的权限边界

避免出现：

- 临期事项无人提醒
- 提醒发给无权限人员
- 重复提醒造成骚扰和误操作

### 11.12 导出、打印与报表风险控制

事务所系统通常存在大量导出与打印场景，建议补充：

- 谁可以导出客户清单、财务数据、行政资料、税务报表
- 是否对大批量导出设置阈值、审批或告警
- 导出、打印、预览是否必须留痕
- 报表口径是否统一定义
- 敏感导出是否带水印或标记导出人

### 11.13 高风险用例清单

建议在开发与测试阶段重点覆盖以下高风险场景：

1. 普通员工越权查看非本人客户资料
2. 非财务角色查看或导出全部金额数据
3. 同一请款记录被重复收款
4. 预收款被重复抵扣
5. 审批通过后关键数据被再次修改且无重新审批
6. 员工批量下载客户文件但日志无记录
7. 删除客户或财务记录后无法恢复
8. NAS 路径配置错误导致访问越界
9. 登录失败暴力尝试未被限制
10. 数据库恢复后与文件服务器状态不一致

## 14. 结论

该系统本质上是一个 **以客户为中心的事务所综合管理系统**，强调：

- 客户主档统一
- 行政与税务业务并行
- 财务闭环管理
- 文件与日志留痕
- 内部任务与审批协同

从开发角度看，当前文档已足以支撑 **信息架构设计、数据库初稿设计、模块拆分与页面原型设计**；但若进入正式编码阶段，仍需先补齐状态流转、权限细则、财务规则和审批规则。
