# 复杂安全项后置与测试质量策略

## 1. 文档目标

本文件用于说明：在追求“稳、质量高、速度快”的前提下，哪些复杂安全项可以后置，以及如何通过测试策略保证上线质量。

## 2. 安全建设分层建议

### 2.1 P0 一期必须做

- 账号登录与停用
- 基础角色权限
- 关键操作日志
- 删除确认与软删除
- 财务防重复提交
- 数据库与文件备份

### 2.2 P1 二期补充

- 敏感数据脱敏
- 文件版本管理
- 更多财务校验规则
- 更细的角色权限

### 2.3 P2 三期再考虑

- 双因素认证
- 单点登录
- 字段级 / 行级复杂权限
- 自动化攻防演练
- 安全监控平台和告警联动
- 在线 Office 安全审计

## 3. 红蓝审核下可后置的复杂项

如果按红蓝视角理解：

- 红方重点关注误操作、越权、错账、误删、文件丢失
- 蓝方先解决权限、日志、确认、备份、恢复

以下复杂项通常可以后置：

- 重型安全平台接入
- 复杂组织级权限模型
- 高成本自动化安全体系
- 完整多级审批安全闭环
- 文件内容级安全治理平台

原则是：先解决最常见、最影响业务的风险，再补高成本安全能力。

## 4. 测试策略总原则

建议采用“单元测试优先，关键链路补集成，发布前做最小回归”的策略。

目标不是一开始把测试做得非常重，而是让测试真正帮助你更快、更稳地合并代码。

测试与代码规范、JSDoc 门禁一起构成三道质量防线：

1. **代码规范**（`npm run lint`）— 拦截低级反模式和风格漂移。
2. **JSDoc 门禁**（`npm run jsdoc:check`）— 保证方法可理解性。
3. **单元测试**（`npm run test:frontend` / `npm run test:backend`）— 保护业务逻辑正确性。

三者统一收口到 `npm run verify`（详见 §7）。

## 5. 推荐测试层次

### 5.1 前端

- 使用 `Vitest` + `Vue Test Utils`
- 重点测表单校验、状态切换、权限按钮显示、文件上传交互

### 5.2 后端

- 使用 `Jest` + `@nestjs/testing`
- 重点测 service 层、权限判断、财务计算、导入校验、文件接口

### 5.3 集成与 smoke check

- 登录
- 客户新增 / 编辑
- 案件或税务月次主流程
- 财务登记
- 文件上传 / 下载 / 预览

## 6. 模块级测试重点

建议优先覆盖以下模块：

- `auth`：登录、停用账号、权限返回
- `customer`：新增、编辑、查询条件、重复校验
- `finance`：金额计算、重复提交、防误删、作废逻辑
- `file`：上传、权限、下载、删除日志、关联对象校验

这些模块一旦出错，业务影响最大。

## 7. 合并到 release 前的最小门禁

本仓库提供三层递进式校验入口，AI 和人工开发共用同一套（详见 `AGENTS.md` §4）：

| 命令 | 包含检查 | 适用场景 |
|------|----------|----------|
| `npm run verify:fast` | lint（含 JSDoc 存在性）+ type-check + JSDoc 质量检查 | 日常开发自查 |
| `npm run verify` | verify:fast + 前后端测试 | 功能完成、分支合并 |
| `npm run verify:full` | verify + 前后端构建 | CI 全量门禁、部署前 |

每个功能分支合并前至少确认：

1. **代码规范通过** — `npm run lint:frontend && npm run lint:backend` 无 error（规则详见 `docs/s05_style_rules.md`）。
2. **JSDoc 完整** — 新增/修改方法已按 `docs/s06_jsdoc_standard.md` 补齐注释（用途描述、`@param`、`@returns`、`@throws`），`npm run jsdoc:check` 通过。
3. **类型检查通过** — `npm run type-check:frontend && npm run type-check:backend` 无报错。
4. **本模块单元测试已补齐且通过** — `npm run test:frontend && npm run test:backend`。
5. **关键页面或接口已自测**。
6. **未引入明显的 TODO、假数据、临时开关**。
7. **文档、接口或字段变更已同步**。

最低要求：功能分支合并前必须通过 `npm run verify`。

## 8. 代码规范与 JSDoc 门禁

在测试策略之外，项目还通过以下门禁保障代码可维护性：

### 代码规范（详见 `docs/s05_style_rules.md`）

- 前后端共用一套分级 ESLint 规则：error 级阻断提交，warn 级渐进清理。
- 关键阻断项：`debugger`、`eval()`、`alert()`、`===` 强制、Vue `<script setup>` 块顺序、禁止直接修改 prop。
- 渐进清理项：`no-console`、导入排序、未使用变量、`no-explicit-any`、文件/函数长度守卫、危险注释。

### JSDoc 质量门禁（详见 `docs/s06_jsdoc_standard.md` + `docs/s07_jsdoc_gate_design.md`）

- **Layer 1**（ESLint `eslint-plugin-jsdoc`）：随 `npm run lint` 执行，检查函数/方法是否有 JSDoc 块、`@param`、`@returns` 及描述。
- **Layer 2**（`scripts/check-jsdoc.mjs`）：随 `npm run jsdoc:check` 执行，检查描述有效长度、空泛词拦截、`@throws` 覆盖。
- 两层均已集成到 `npm run verify:fast` 管道，新增或修改的方法若缺失 JSDoc 或内容不合格会被拦截。

## 9. 如何兼顾稳、快、质量高

建议采用以下做法：

- 公共基础先稳定，再并行开发
- 功能分支尽量小，避免超大分支
- 测试跟随模块一起交付，不要最后一起补
- release 分支只合并已通过 `npm run verify` 的功能
- 复杂安全项后置，不要拖慢 MVP 交付
- 代码规范和 JSDoc 跟随开发同步执行，不积累技术债

## 10. 推荐执行口径

当前项目最合理的做法是：

- 一期先做基础安全和核心业务闭环
- 二期再补更细权限和文件增强
- 三期再看复杂安全平台与在线协同编辑

一句话总结：**该快的地方靠并行和模块拆分提速；该稳的地方靠单元测试、代码规范、JSDoc 门禁和 release 集成控制质量。**
