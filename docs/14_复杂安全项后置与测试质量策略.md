# 复杂安全项后置与测试质量策略

## 1. 文档目标

本文件用于说明：在追求“稳、质量高、速度快”的前提下，哪些复杂安全项可以后置，以及如何通过测试策略保证上线质量。

## 2. 安全建设分层建议

### 2.1 P0 一期必须做

- 账号登录与停用
- 基础角色权限
- 关键操作日志
- 删除确认与软删除
- 财务防重复提交
- 数据库与文件备份

### 2.2 P1 二期补充

- 敏感数据脱敏
- 文件版本管理
- 更多财务校验规则
- 更细的角色权限

### 2.3 P2 三期再考虑

- 双因素认证
- 单点登录
- 字段级 / 行级复杂权限
- 自动化攻防演练
- 安全监控平台和告警联动
- 在线 Office 安全审计

## 3. 红蓝审核下可后置的复杂项

如果按红蓝视角理解：

- 红方重点关注误操作、越权、错账、误删、文件丢失
- 蓝方先解决权限、日志、确认、备份、恢复

以下复杂项通常可以后置：

- 重型安全平台接入
- 复杂组织级权限模型
- 高成本自动化安全体系
- 完整多级审批安全闭环
- 文件内容级安全治理平台

原则是：先解决最常见、最影响业务的风险，再补高成本安全能力。

## 4. 测试策略总原则

建议采用“单元测试优先，关键链路补集成，发布前做最小回归”的策略。

目标不是一开始把测试做得非常重，而是让测试真正帮助你更快、更稳地合并代码。

## 5. 推荐测试层次

### 5.1 前端

- 使用 `Vitest` + `Vue Test Utils`
- 重点测表单校验、状态切换、权限按钮显示、文件上传交互

### 5.2 后端

- 使用 `Jest` + `@nestjs/testing`
- 重点测 service 层、权限判断、财务计算、导入校验、文件接口

### 5.3 集成与 smoke check

- 登录
- 客户新增 / 编辑
- 案件或税务月次主流程
- 财务登记
- 文件上传 / 下载 / 预览

## 6. 模块级测试重点

建议优先覆盖以下模块：

- `auth`：登录、停用账号、权限返回
- `customer`：新增、编辑、查询条件、重复校验
- `finance`：金额计算、重复提交、防误删、作废逻辑
- `file`：上传、权限、下载、删除日志、关联对象校验

这些模块一旦出错，业务影响最大。

## 7. 合并到 release 前的最小门禁

每个功能分支合并前至少确认：

1. 本模块单元测试已补齐
2. 单元测试已通过
3. 关键页面或接口已自测
4. 未引入明显的 TODO、假数据、临时开关
5. 文档、接口或字段变更已同步

## 8. 如何兼顾稳、快、质量高

建议采用以下做法：

- 公共基础先稳定，再并行开发
- 功能分支尽量小，避免超大分支
- 测试跟随模块一起交付，不要最后一起补
- release 分支只合并已完成最小验证的功能
- 复杂安全项后置，不要拖慢 MVP 交付

## 9. 推荐执行口径

当前项目最合理的做法是：

- 一期先做基础安全和核心业务闭环
- 二期再补更细权限和文件增强
- 三期再看复杂安全平台与在线协同编辑

一句话总结：**该快的地方靠并行和模块拆分提速；该稳的地方靠单元测试、最小门禁和 release 集成控制质量。**
