# 后端架构评审与优化建议（含轻量红蓝视角）

## 1. 背景与评审范围

本评审面向当前仓库的后端实现（NestJS + TypeORM + PostgreSQL + 本地/共享目录文件存储），目标是判断现有架构是否符合项目定位，并给出与当前阶段相匹配的优化路线。重点覆盖：

- 模块边界与分层是否清晰
- API 契约、错误治理与写链路一致性
- 权限、审计与文件链路的风险控制
- 稳定性、可观测性与上线运维可控性
- 在“不过度设计”前提下的轻量红蓝对抗视角

评审约束遵循项目基线：**够用、简单、稳定、便于迭代**，不引入需要专职平台/安全团队长期维护的重型方案（见 [01_总体架构与实施规划.md](./01_总体架构与实施规划.md)、[05_红蓝对抗与安全设计.md](./05_红蓝对抗与安全设计.md)）。

## 2. 当前架构概览（基于代码事实）

### 2.1 应用形态与模块组织

- 当前后端是**单体应用 + 模块化代码组织**，由 `AppModule` 汇总装配 `auth/customer/admin-case/tax/finance/file/system/log/dashboard/visa-case` 等模块（[app.module.ts](../backend/src/app.module.ts)）。
- 全局 API 前缀为 `/api/v1`（[main.ts](../backend/src/main.ts)）。
- 这套形态与一期“内部轻量业务后台”的定位一致，适合快速交付和渐进迭代。

更准确地说，当前架构属于**实用型模块化单体**：

- 优点是目录与职责大体清晰，工程效率较高。
- 需要注意的是，它**还不是严格隔离的领域边界**；部分模块之间已存在直接引入与实体复用，例如客户域与签证域之间有跨模块依赖（[customer.module.ts](../backend/src/modules/customer/customer.module.ts)、[visa-case.module.ts](../backend/src/modules/visa-case/visa-case.module.ts)）。

这在当前阶段不构成必须重构的问题，但说明后续应控制跨域依赖继续扩散，避免模块名存在、边界却逐步失效。

### 2.2 已具备的基础治理能力

- 统一响应结构：全局 `TransformInterceptor` 将成功响应包装为 `{ code, message, data }`（[transform.interceptor.ts](../backend/src/common/interceptors/transform.interceptor.ts)）。
- 统一异常结构：`AllExceptionsFilter` 将异常统一映射为 `{ code, message, data: null }`（[http-exception.filter.ts](../backend/src/common/filters/http-exception.filter.ts)）。
- 全局参数校验：`ValidationPipe` 开启 `whitelist`、`forbidNonWhitelisted`、`transform`（[main.ts](../backend/src/main.ts)）。
- 审计日志：`LogModule` 通过全局审计拦截器为带 `@AuditAction()` 的接口补写审计日志（[log.module.ts](../backend/src/modules/log/log.module.ts)、[audit-log.interceptor.ts](../backend/src/modules/log/interceptors/audit-log.interceptor.ts)）。
- 认证授权：全局 JWT 守卫 + `PermissionGuard`，权限来源于 DB 中的 `user.roles.permissions`（[auth.module.ts](../backend/src/modules/auth/auth.module.ts)、[jwt.strategy.ts](../backend/src/modules/auth/strategies/jwt.strategy.ts)、[permission.guard.ts](../backend/src/modules/auth/guards/permission.guard.ts)）。
- 登录安全：已实现登录失败计数与临时锁定，具备基础爆破防护意识（[auth.service.ts](../backend/src/modules/auth/auth.service.ts)）。

### 2.3 已出现的工程化特征

- 幂等：存在基于 `x-idempotency-key` 的短 TTL 内存拦截器，并已在财务写接口使用（[idempotency.interceptor.ts](../backend/src/common/interceptors/idempotency.interceptor.ts)、[payment.controller.ts](../backend/src/modules/finance/payment.controller.ts)）。
- 事务：财务域已出现显式事务封装，说明关键写链路已具备一致性治理意识，但尚未在全域形成统一模式（[payment.service.ts](../backend/src/modules/finance/payment.service.ts)、[deposit.service.ts](../backend/src/modules/finance/deposit.service.ts)）。
- 文件能力：文件上传/下载/预览/软删除与访问日志均已落地，符合“数据库存元数据 + 文件目录存实体”的设计思路（[file.controller.ts](../backend/src/modules/file/file.controller.ts)、[file.service.ts](../backend/src/modules/file/file.service.ts)）。

## 3. 架构合理性结论（结论先行）

整体判断：**现有后端架构方向是合理的，且与项目定位基本匹配。**

主要依据如下：

- 单体 + 模块化符合一期快速交付和小团队维护成本控制目标。
- 全局校验、异常包装、统一响应、审计与权限控制已经形成基础治理骨架。
- 财务、文件、签证等复杂度较高的域已开始出现事务、幂等、数据范围等工程化实践，说明系统并非停留在纯 CRUD 水平。

但需要更准确地区分两类问题：

1. **架构形态本身没有大问题**：当前不需要向微服务、复杂权限平台或重型安全体系演进。
2. **实现细节与治理闭环仍有明显缺口**：风险主要来自不安全默认值、配置不一致、审计脱敏不足、缓存/幂等/日志治理不完整，以及跨模块依赖逐步扩散的趋势。

因此，本次优化重点不应是“推倒重来”，而应是：

- 修补高风险、低成本的安全与稳定性问题
- 收敛跨模块依赖与写链路治理方式
- 为后续规模增长预留轻量扩展点，而不是提前建设重型平台

## 4. 主要问题与改进建议（按优先级）

### P0（建议尽快处理：高风险、低成本、直接影响上线质量）

1) 缺少统一的生产配置 fail-fast 校验

- 现状：多个关键配置存在默认值回退，例如 `JWT_SECRET` 存在 `default-secret` 回退；数据库配置也存在较多默认值；启动阶段尚未见统一 schema 校验（[jwt.strategy.ts](../backend/src/modules/auth/strategies/jwt.strategy.ts)、[auth.module.ts](../backend/src/modules/auth/auth.module.ts)、[data-source.ts](../backend/src/data-source.ts)、[main.ts](../backend/src/main.ts)）。
- 风险：最危险的情况不是“启动失败”，而是“带着错误配置正常启动”，上线后表现为看似可用、实则安全性或可靠性不足。
- 建议：建立统一配置校验机制；至少对 `JWT_SECRET`、`DB_*`、`FILE_UPLOAD_DIR`、`CORS_ORIGIN` 做生产环境必填和合法性检查，不满足即启动失败。

2) JWT 允许从 URL 查询参数读取 token

- 现状：`extractJwtFromRequest` 支持 `?token=` 回退（[jwt.strategy.ts](../backend/src/modules/auth/strategies/jwt.strategy.ts)）。
- 风险：token 易出现在浏览器历史、代理日志、Referer 或误分享链接中；对内部系统同样是低成本高收益的攻击面。
- 建议：默认禁用 query token。若确有内网临时工具场景，必须通过显式环境变量开关启用，且需确认网关/日志不记录 query。

3) 文件上传临时目录与正式目录的配置来源不一致

- 现状：Controller 层临时目录直接读取 `process.env.FILE_UPLOAD_DIR || './uploads'`，而 Service 层通过 `ConfigService` 读取 `FILE_UPLOAD_DIR`（[file.controller.ts](../backend/src/modules/file/file.controller.ts)、[file.service.ts](../backend/src/modules/file/file.service.ts)）。
- 风险：会出现“临时文件写入 A 目录、正式搬运使用 B 目录”的隐性故障，也会误导运维对目录权限与容量的判断。
- 建议：统一通过 `ConfigService` 提供上传目录；Controller 不再直接读取 `process.env`。

4) 审计日志成功分支直接记录请求体，存在敏感信息落库风险

- 现状：审计拦截器成功分支将 `req.body` 作为 `afterValue` 写入（[audit-log.interceptor.ts](../backend/src/modules/log/interceptors/audit-log.interceptor.ts)）。
- 风险：随着业务演进，密码、证件号、银行信息、token 等字段可能被直接落入审计库，扩大泄露面，也增加合规风险。
- 建议：审计记录改为“最小必要信息”原则：默认不落全量 body，只保留关键字段、字段白名单或摘要；统一脱敏 `password/newPassword/token` 等高风险字段，并对超长内容做截断。

5) 轻量限流应纳入上线治理，但优先级需结合部署暴露面判断

- 现状：登录失败次数锁定已存在，但尚未见通用请求级限流或文件下载/导入等接口的轻量保护（[auth.service.ts](../backend/src/modules/auth/auth.service.ts)）。
- 风险：若系统可被公网或弱边界网络直接访问，登录、下载、导入接口易成为误刷或脚本压测入口；若系统仅在办公网/VPN 内使用，风险相对下降，但仍存在误操作打挂服务的可能。
- 建议：
  - **若部署面向公网/弱边界**：将登录、下载/预览、导入接口限流视为 P0。
  - **若仅办公网/VPN 内使用**：可排入 P1，但应在正式上线前完成，不建议长期缺失。

### P1（建议近期治理：提升可维护性、排障效率与后续扩展弹性）

1) 模块边界总体可用，但跨域依赖已有扩散迹象

- 现状：当前是实用型模块化单体，部分模块已存在直接引入对方模块、实体或服务的情况，尤其客户域与签证域之间耦合度较高（[customer.module.ts](../backend/src/modules/customer/customer.module.ts)、[visa-case.module.ts](../backend/src/modules/visa-case/visa-case.module.ts)）。
- 风险：短期不会立刻出问题，但若继续无约束扩散，后续会出现“模块很多、实际边界很弱”的维护困境，导致改一处牵动全局。
- 建议：
  - 先做一次跨模块依赖盘点，识别“必要依赖”和“便利性依赖”。
  - 对新增跨域依赖提高门槛，优先通过明确的查询服务、DTO 映射或受控导出能力复用，而不是随意共享内部实现。
  - 不必为了当前阶段引入复杂 DDD 分层，但应避免继续滑向“名义模块化”。

2) `PermissionGuard` 每请求加载用户角色权限，存在稳定 DB 热点

- 现状：每个受保护请求都会查询一次 `roles.permissions`（[permission.guard.ts](../backend/src/modules/auth/guards/permission.guard.ts)）。
- 风险：当前流量下或许可接受，但随着请求增长会形成稳定热点，也使权限变更生效策略缺少统一设计。
- 建议：
  - 第一阶段采用**单实例内存短 TTL 缓存**（例如 30–120 秒）。
  - 配合“角色/权限变更后主动失效缓存”的管理动作。
  - 仅在未来走多实例部署或确有共享缓存需求时，再引入 Redis；不建议当前阶段为了权限缓存而提前引入额外基础设施。

3) 错误码体系仍偏按 HTTP status 粗粒度映射

- 现状：`AllExceptionsFilter` 主要按 HTTP status 映射系统错误码（[http-exception.filter.ts](../backend/src/common/filters/http-exception.filter.ts)）。
- 问题：状态机非法迁移、幂等冲突、导入校验失败、业务规则冲突等场景会被压缩到少量错误码，导致前端提示粒度不足，排障过度依赖 message 文案。
- 建议：引入可选的业务异常基类（`code + message + httpStatus`），优先在财务、导入、权限等高价值域落地，而不是一开始全域重写异常体系。

4) 幂等实现目前是单机内存级，key 设计也偏粗

- 现状：幂等 key 由 `method:url:idempotencyKey` 组成，缓存与 pending 集合均为进程内存（[idempotency.interceptor.ts](../backend/src/common/interceptors/idempotency.interceptor.ts)）。
- 风险：
  - 多实例部署时天然失效。
  - `url` 受 query 参数顺序等影响，命中不稳定。
  - 未纳入 `userId` 或关键请求摘要，存在误碰撞空间。
- 建议：
  - 短期把 key 升级为 `userId + 路由模板 + idempotencyKey + body 摘要`。
  - 中期若需要多实例部署，再迁移到 Redis 或共享存储。
  - 不建议当前阶段为了少量接口幂等而直接建设重型分布式幂等平台。

5) 缺少 request-id 与更一致的结构化日志关联方式

- 现状：已有大量业务日志，但缺少贯穿一次请求的关联 ID，排查时仍偏依赖时间窗口与人工比对。
- 建议：
  - 优先在网关透传或应用层生成 request-id。
  - 首先打通 server log、error log、audit log 的检索关联。
  - 是否把 request-id 下发到响应体，可作为第二阶段增强，而非首批必须修改的接口契约。

### P2（中长期演进：在业务增长后收益更大）

1) 写链路一致性治理需要从“局部有意识”走向“可复用模式”

- 现状：财务域已出现显式事务封装，说明关键写操作已具备治理意识；但尚未看到覆盖全域的统一写链路模式。
- 建议：后续可逐步沉淀哪些场景必须事务、哪些场景允许最终一致、哪些场景应依赖唯一约束 + 幂等保护，不必追求全域统一事务框架。

2) 导入/批处理治理可逐步任务化

- 现状：签证导入已具备预览、冲突识别和逐行提交能力，但仍属于同步提交 + 结果汇总模式（[visa-case-import-commit.service.ts](../backend/src/modules/visa-case/visa-case-import-commit.service.ts)）。
- 建议：当导入规模或频率继续增长时，再演进为“异步任务 + 进度 + 可重试 + 操作审计”的任务化方案；当前阶段不必为少量导入能力预建通用任务平台。

3) 文件存储应预留抽象层，但不必立即替换现有目录方案

- 现状：本地目录/NAS + 数据库存元数据与项目定位匹配。
- 建议：先通过存储接口抽象屏蔽底层实现，未来如需接入对象存储再增加策略实现；病毒扫描、内容识别等能力可继续后置，不作为当前阶段门槛。

4) 审计体系可逐步从“能追溯”升级为“更易分析”

- 建议中长期统一审计事件模型，例如：动作、对象、对象 ID、关键字段摘要、操作结果、原因、request-id、操作者。目标是提升追责与排障效率，而不是把审计系统建设成独立平台。

## 5. 轻量红蓝对抗分析（结合当前实现的真实攻击面）

本项目不需要重型攻防体系，但可以保留“轻量红蓝视角”，帮助识别最具性价比的攻击面与防守闭环。

### 5.1 资产与最低安全目标

关键资产：

- 客户资料
- 案件/签证资料
- 税务合同与月次资料
- 财务记录
- 上传文件
- 登录日志与审计日志

最低安全目标：

- 不越权
- 可追溯
- 不因误操作或配置错误造成严重事故
- 不被轻易打挂
- 出问题时可恢复

### 5.2 红方路径与蓝方对策

1) 伪造或泄露登录态

- 红方路径：利用弱密钥/默认密钥伪造 token，或通过 `?token=` 链接、代理日志、浏览器历史泄露 token。
- 蓝方对策：生产环境强校验 `JWT_SECRET`，默认禁用 query token，明确 access token 有效期；必要时对财务作废、冲正等关键动作增加二次确认。

2) 越权访问（纵向或横向）

- 红方路径：扫描未正确声明权限的接口，或利用可猜测 ID 访问他人数据。
- 蓝方对策：
  - 核心业务接口，尤其写接口，应显式声明 `@Permissions()` 或显式声明 `@Public()`，避免“默认遗漏”。
  - 对财务、系统设置、日志、签证等敏感域加强权限码和审计覆盖。
  - 数据范围控制只在确有业务必要的域有限复用，避免仓促扩展成全域复杂行级权限系统；签证域的数据范围实现可作为模式参考，但不应直接泛化为全系统统一引擎。

3) 参数污染、校验绕过与动态查询滥用

- 红方路径：提交额外字段、类型混淆、超长字符串或危险排序字段，尝试绕过逻辑或拖垮查询。
- 蓝方对策：
  - 当前 `ValidationPipe` 的 `whitelist + forbidNonWhitelisted` 已具备基础防护。
  - 对排序字段、动态筛选字段、查询构造入口继续坚持白名单策略；文件模块中对 `sortBy` 的处理方式值得推广到其他域。

4) 文件链路攻击（上传/下载/预览）

- 红方路径：上传恶意脚本或带宏文档、利用 MIME/文件名编码做内容嗅探或响应头问题、反复刷下载拖垮 IO。
- 蓝方对策：
  - 当前扩展名白名单已存在，但未来若风险提高，可再补真实内容类型检测。
  - 下载/预览接口应结合部署边界决定是否立即加限流。
  - 网关层应保留 `X-Content-Type-Options: nosniff` 等基础响应头；现有 Nginx 配置已体现这一点，若切换网关应确保等价能力（[deploy/nginx/cms.conf](../deploy/nginx/cms.conf)）。
  - 下载、预览、删除已有访问日志，后续可把失败下载与异常峰值纳入告警维度。

5) 审计绕过与追责失败

- 红方路径：利用未声明 `@AuditAction()` 的关键接口进行操作，或在异常路径中制造审计空洞。
- 蓝方对策：
  - 建立“关键动作清单”，而不是要求所有接口都强制审计。
  - 对财务登记、文件删除、角色权限变更、导入提交等关键动作做测试/检查，确保存在权限码与审计动作。
  - 日志写入失败应可监控；审计内容坚持最小化与脱敏原则，避免为追责扩大敏感数据面。

## 6. 推荐的优化落地路线（分阶段）

### 6.1 立即可做（P0，低成本高收益）

- 建立统一配置校验：至少覆盖 `JWT_SECRET`、`DB_*`、`FILE_UPLOAD_DIR`、`CORS_ORIGIN`。
- 禁用 query token，必要时改为显式开关且默认关闭。
- 统一文件上传目录配置来源，移除 Controller 直接读 `process.env`。
- 审计日志脱敏：黑名单遮罩 + 白名单字段 + 最大长度限制。
- 结合部署暴露面决定是否立即对登录、下载/预览、导入接口加轻量限流；若面向公网或弱边界，则应立即处理。

### 6.2 近期治理（P1，提升可维护性与排障效率）

- 做一次跨模块依赖盘点，控制客户域、签证域等高耦合区域继续扩散。
- 权限缓存：先单实例内存 TTL，再视多实例部署情况决定是否引入 Redis。
- 引入业务异常基类，为核心域提供稳定错误码。
- 幂等增强：key 纳入 `userId / 路由模板 / body 摘要`。
- 打通 request-id 与结构化日志关联，优先提升日志检索与排障效率。

### 6.3 中长期（P2，面向增长的结构化演进）

- 逐步沉淀事务边界、一致性与唯一约束的使用模式。
- 导入/批处理任务化：异步队列、进度、重试、审计。
- 文件存储抽象：存储接口 + 本地目录/NAS/对象存储策略实现。
- 审计事件模型增强：动作、对象、摘要、结果、原因、request-id 的统一结构。

## 7. 验证与上线检查清单（建议纳入发布门禁）

- 安全配置
  - 生产环境 `JWT_SECRET` 不允许默认值且长度达标
  - `CORS_ORIGIN` 不允许错误放通，需与真实部署域名匹配
  - query token 默认关闭；如启用需确认网关与日志策略安全
- 权限与审计
  - 核心业务写接口显式声明权限或显式声明 `@Public()`
  - 财务登记、文件删除、角色权限变更、导入提交等关键动作具备权限码与审计动作
  - 审计内容已脱敏，避免敏感字段直接落库
- 稳定性
  - 登录、下载/预览、导入接口已根据部署暴露面配置限流或确认替代防护措施
  - 财务等关键写链路的事务边界已明确
  - 数据库备份与文件目录备份至少完成一次恢复演练
- 运维可控
  - 关键日志可按 request-id 或等价请求标识关联检索
  - 关键告警至少覆盖：审计写入失败、登录异常峰值、下载异常峰值、导入失败率
