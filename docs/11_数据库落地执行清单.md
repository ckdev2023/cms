# 事务所管理系统数据库落地执行清单

## 1. 文档目标

本文用于把数据库设计文档进一步拆成实际可执行步骤，帮助按顺序完成建库、建表、字典初始化和验收。

## 2. 落地目标

完成本清单后，应达到以下状态：

1. 数据库实例可连接
2. 核心业务表已建立
3. 角色权限和字典数据已初始化
4. 主键、外键、唯一约束和索引已设置
5. 迁移脚本可重复执行
6. 可以支撑登录、客户和主业务模块开发

## 3. 数据库落地原则

1. 先建基础表，再建业务表
2. 先建主表，再建明细表和日志表
3. 所有关键表统一时间字段和软删除策略
4. 枚举过多的状态优先沉淀为字典或统一常量
5. 一期以 PostgreSQL 为主路线，Access 只作为备选说明

## 4. 执行步骤

### 4.1 步骤 01：创建数据库与基础连接账号

目标：准备可供开发和测试使用的数据库实例。

具体操作：

- 创建开发库、测试库
- 创建应用连接账号
- 配置字符集、时区和基础访问权限
- 确认本地和服务器可连接

对应技能：

- PostgreSQL 基础管理
- 数据库账号权限管理
- 环境配置

产出物：

- 开发库
- 测试库
- 数据库连接信息模板

完成标准：应用可稳定连接开发库和测试库。

### 4.2 步骤 02：确定主键策略与公共字段规范

目标：统一所有表的基础结构风格。

具体操作：

- 确认主键采用 UUID 或 BIGINT
- 统一 `created_at`、`updated_at`、`deleted_at`
- 对关键表增加 `created_by`、`updated_by`
- 明确哪些表支持软删除，哪些表只允许作废或追加流水

对应技能：

- 数据建模
- 通用字段规范设计
- 审计字段设计

产出物：

- 主键规范说明
- 公共字段规范说明

完成标准：新表都能按统一模板扩展，不再反复讨论字段风格。

### 4.3 步骤 03：先落事务所管理基础表

目标：优先支持登录、用户和权限能力。

具体操作：

- 建立 `users`
- 建立 `roles`
- 建立 `permissions`
- 建立 `user_roles`
- 建立 `role_permissions`

对应技能：

- 权限模型理解
- 表关系设计
- 唯一约束设计

产出物：

- 用户与权限基础表
- 初始管理员角色与权限数据

完成标准：数据库层面已能支撑登录和 RBAC 基础能力。

### 4.4 步骤 04：落客户主档相关表

目标：建立客户中心数据基础。

具体操作：

- 建立 `customers`
- 建立 `company_info`
- 建立 `person_info`
- 建立 `customer_staff_relations`
- 建立 `notes`

对应技能：

- 主子表建模
- 客户数据建模
- 索引设计

产出物：

- 客户主档相关表
- 客户编号唯一规则

完成标准：客户、法人、个人和跟进记录都可独立落库。

### 4.5 步骤 05：落行政书士业务表

目标：支撑行政案件录入和跟进。

具体操作：

- 建立 `admin_cases`
- 建立 `admin_case_interviews`
- 建立 `admin_case_documents`
- 建立 `admin_case_tasks`
- 为客户、状态、到期日建立索引

对应技能：

- 业务表设计
- 日期类查询索引设计
- 关联对象建模

产出物：

- 行政书士业务表
- 关键索引

完成标准：行政案件主流程具备落库条件。

### 4.6 步骤 06：落税理士业务表

目标：支撑税务合同和月次管理。

具体操作：

- 建立 `tax_contracts`
- 建立 `tax_periods`
- 建立 `tax_monthly_documents`
- 建立 `tax_monthly_work_items`
- 为客户、期间、截止日、状态建立索引

对应技能：

- 合同与期间建模
- 状态字段设计
- 查询路径设计

产出物：

- 税务业务表
- 税务月次索引

完成标准：税务合同与月次数据可以稳定存储和查询。

### 4.7 步骤 07：落财务业务表

目标：支撑请款、收款和预收款闭环。

具体操作：

- 建立 `invoices`
- 建立 `invoice_items`
- 建立 `payments`
- 建立 `payment_allocations`
- 建立 `deposit_accounts`
- 建立 `deposit_transactions`
- 为编号、客户、状态、日期建立唯一约束和索引

对应技能：

- 财务流水模型设计
- 事务一致性设计
- 唯一约束设计
- 金额字段规范设计

产出物：

- 财务表结构
- 财务约束与索引清单

完成标准：财务登记具备防重复和可追踪基础。

### 4.8 步骤 08：落任务、审批与文件表

目标：补齐日常使用闭环。

具体操作：

- 建立 `tasks`
- 建立 `approvals`
- 建立 `approval_steps`
- 建立 `files`
- 建立 `file_access_logs`

对应技能：

- 任务与审批建模
- 文件元数据建模
- 审计关联设计

产出物：

- 任务审批表
- 文件与访问日志表

完成标准：系统可支撑任务、审批和文件的基础扩展。

### 4.9 步骤 09：落日志与审计表

目标：为关键操作留痕。

具体操作：

- 建立 `audit_logs`
- 建立 `login_logs`
- 建立 `export_logs`
- 明确日志保留字段和查询条件
- 对常用查询字段建立索引

对应技能：

- 审计日志设计
- 写多读多场景建模
- 索引优化基础

产出物：

- 日志表
- 日志字段说明

完成标准：关键操作具备数据库级留痕基础。

### 4.10 步骤 10：初始化字典、枚举与基础数据

目标：减少业务开发阶段的硬编码。

具体操作：

- 初始化角色数据
- 初始化权限编码数据
- 初始化客户类型、服务类型、案件状态、月次状态、财务状态等字典
- 初始化管理员账号和测试角色

对应技能：

- 初始化数据脚本编写
- 枚举设计
- 业务口径整理

产出物：

- 初始化 SQL 或脚本
- 基础字典数据

完成标准：系统启动后即可使用基础角色和状态数据。

### 4.11 步骤 11：补充索引、唯一约束和外键检查

目标：防止后续出现性能和脏数据问题。

具体操作：

- 检查客户编码、请款编号、收款编号唯一性
- 检查客户、合同、案件、收款分摊等表的外键关系
- 检查常用筛选字段是否建索引
- 检查软删除表的查询条件是否有配套索引策略

对应技能：

- 索引设计
- 外键约束设计
- 查询路径分析

产出物：

- 索引清单
- 约束检查清单

完成标准：核心业务表的唯一性、关联性和常用查询性能有基本保障。

### 4.12 步骤 12：建立迁移和版本管理机制

目标：让数据库结构变更可重复、可追踪。

具体操作：

- 约定迁移文件命名规范
- 区分建表迁移、修订迁移、初始化数据脚本
- 确认本地、测试、生产的迁移执行流程
- 约定禁止直接手改生产表结构

对应技能：

- 数据库迁移管理
- 发布流程设计
- 环境一致性控制

产出物：

- 迁移目录结构
- 迁移执行说明

完成标准：结构变化都能通过迁移脚本重复执行。

### 4.13 步骤 13：完成数据库落地验收

目标：确认数据库已能支撑业务开发和测试。

具体操作：

- 执行建表脚本验证
- 执行初始化数据验证
- 测试典型插入、更新、删除、查询场景
- 检查外键、唯一约束和软删除逻辑是否正常
- 检查备份导出是否可执行

对应技能：

- SQL 验证
- 数据库测试
- 问题排查
- 备份恢复基础

产出物：

- 数据库验收记录
- 数据库问题清单

完成标准：数据库进入“可开始批量开发业务接口”的状态。

## 5. 建议的建表顺序

推荐顺序如下：

1. `users` / `roles` / `permissions`
2. `user_roles` / `role_permissions`
3. `customers` / `company_info` / `person_info`
4. `notes` / `customer_staff_relations`
5. `admin_cases` 及相关子表
6. `tax_contracts` / `tax_periods` 及相关子表
7. `invoices` / `invoice_items`
8. `payments` / `payment_allocations`
9. `deposit_accounts` / `deposit_transactions`
10. `tasks` / `approvals` / `approval_steps`
11. `files` / `file_access_logs`
12. `audit_logs` / `login_logs` / `export_logs`

## 6. Access 备选说明

如果客户坚持 Access，建议只作为备选或过渡方案，并注意：

- 不要把复杂财务流水设计得过重
- 不要依赖高并发写入
- 尽量减少复杂外键和大规模日志写入压力
- 表命名和字段设计尽量保留未来迁移到 PostgreSQL 的兼容性

## 7. 数据库落地检查表

建议逐项确认：

1. 开发库和测试库可连接
2. 主表和子表创建成功
3. 初始化角色和字典成功
4. 关键编号唯一约束已生效
5. 外键关系无明显缺失
6. 常用查询索引已建立
7. 迁移脚本可重复执行
8. 备份方案已确认

## 8. 结论

数据库落地阶段最重要的不是“一次建得多复杂”，而是“先把核心结构建稳”。

一句话总结：**数据库先支撑登录、客户、业务、财务主流程，再逐步补细节和优化。**
