# 单人并行开发编排与依赖关系

## 1. 文档目标

本文用于把“一个人开发，但想多个窗口同时推进”的方式编排清楚，重点说明：

- 哪些事情可以同时进行
- 哪些事情必须等上一步完成
- 一个开发者如何借助 Cursor、Augment、多窗口或 worktree 提速

## 2. 先说结论

对于当前项目，最稳的方式不是所有模块一开始一起做，而是：

1. 先串行完成公共基础
2. 再并行推进互相独立的模块
3. 最后统一收口、联调、回归、上线准备

一句话理解：**先把地基打稳，再让多个窗口并行干不同的房间。**

## 3. 适合你的并行方式

你是一个人开发，所以这里的“并行”不是你本人同时写 4 份代码，而是：

- 你在一个主窗口控制主线
- 其他窗口交给 AI 或作为独立任务上下文
- 每个窗口只做边界清晰、文件冲突少的一块

分支和 worktree 只是手段，不是目的。

如果只是你自己在多个窗口看代码、写文档、跑测试，可以不强制每个窗口都独立分支。

如果你要让多个 AI 窗口同时改代码，**就强烈建议用独立 worktree 或独立分支**，避免互相覆盖。

## 4. 必须先串行完成的阶段

以下步骤建议必须先完成，再进入大规模并行：

### 4.1 串行阶段 S0

1. 冻结范围与角色
2. 确认技术栈与数据库
3. 初始化前后端项目
4. 建立数据库主表与枚举
5. 完成登录与用户角色
6. 搭建后台布局与菜单

### 4.2 为什么这 6 步先串行

因为这些内容决定了后面所有模块的公共边界：

- 技术栈不稳，后面会返工
- 数据库主表不稳，模块会反复改字段
- 登录权限不稳，页面和接口都不好定
- 后台壳子不稳，多个页面会重复返工

所以这 6 步不要并行乱开，先稳住。

## 5. 第一批可并行阶段

当前提步骤 1~6 完成后，可以开始第一批并行。

### 5.1 建议并行的任务

#### 窗口 A：客户中心

- 客户列表
- 新建 / 编辑
- 客户详情
- 基础查询和状态标签

#### 窗口 B：文件基础能力

- 文件表和文件元数据接口
- 上传 / 下载接口
- 图片 / PDF 预览
- 前端通用上传组件

#### 窗口 C：测试与公共整理

- 登录、用户、权限的单元测试
- 公共枚举、字典、类型整理
- API 文档同步

### 5.2 这批为什么能并行

因为它们的共享边界已经比较明确：

- 客户模块依赖基础登录和布局
- 文件基础能力更多是公共设施
- 测试和文档整理可以与业务页面开发并行

### 5.3 这一阶段不要并行做什么

先不要全面展开以下模块：

- 行政书士全模块
- 税理士全模块
- 财务全模块
- 工作台聚合页

原因是这些模块多数依赖客户主档、业务状态和关键字段口径先稳定下来。

## 6. 第二批可并行阶段

当前提是“客户中心主流程已稳定”后，可以进入第二批并行。

### 6.1 建议并行的任务

#### 窗口 A：行政书士模块

- 案件列表
- 新建 / 编辑 / 详情
- 跟进记录和到期日

#### 窗口 B：税理士模块

- 税务合同
- 月次任务
- 月次资料状态

#### 窗口 C：文件关联扩展

- 客户文件关联
- 行政案件文件关联
- 税务合同 / 月次文件关联
- 对应单元测试

### 6.2 这批为什么能并行

因为此时客户主档、公共布局、登录权限、上传基础能力都已经稳定，行政和税务两个模块可以分别推进。

## 7. 第三批可并行阶段

当前提是“行政 / 税务主流程的关键字段和状态已稳定”后，可以进入第三批并行。

### 7.1 建议并行的任务

#### 窗口 A：财务模块

- 请款
- 收款
- 预收款
- 作废 / 冲正逻辑

#### 窗口 B：工作台与提醒

- 待办卡片
- 到期提醒
- 财务提醒
- 最近上传文件或最近跟进

#### 窗口 C：权限、日志、删除保护补齐

- 按模块补按钮权限
- 删除确认与软删除
- 上传 / 下载 / 财务等关键日志
- 补模块测试

### 7.2 为什么财务和工作台不要太早做

因为它们依赖前面模块的数据：

- 财务通常依赖客户、案件、合同或业务状态
- 工作台依赖多个模块都先产生可汇总数据

## 8. 最后统一收口阶段

以下步骤建议不要并行乱做，而要集中收口：

1. 联调
2. 初始化数据
3. 试运行
4. 部署准备
5. 备份恢复验证

原因是这些工作天然跨模块，适合最后统一处理。

## 9. 依赖关系总表

| 任务 | 最早开始条件 | 可否并行 | 说明 |
| --- | --- | --- | --- |
| 冻结范围与角色 | 无 | 否 | 起点任务 |
| 确认技术栈与数据库 | 范围冻结后 | 否 | 不稳定会导致返工 |
| 初始化前后端项目 | 技术栈确定后 | 否 | 先把工程骨架搭好 |
| 建数据库主表与枚举 | 项目初始化后 | 部分可并行 | 可与接口草案整理轻度并行 |
| 登录与用户角色 | 基础表完成后 | 否 | 后续模块共同依赖 |
| 后台布局与菜单 | 登录与角色基础完成后 | 否 | 公共壳子先稳定 |
| 客户中心 | 1~6 完成后 | 是 | 第一优先业务模块 |
| 文件基础能力 | 4~6 完成后 | 是 | 可与客户中心并行 |
| 测试 / 枚举 / 文档整理 | 3~6 完成后 | 是 | 适合作为辅助并行窗口 |
| 行政书士模块 | 客户中心稳定后 | 是 | 可与税理士模块并行 |
| 税理士模块 | 客户中心稳定后 | 是 | 可与行政书士模块并行 |
| 文件关联扩展 | 客户 + 对应业务模块稳定后 | 是 | 逐模块补齐 |
| 财务模块 | 客户稳定且关键业务状态确定后 | 是 | 不建议太早启动 |
| 工作台与提醒 | 至少两个业务模块稳定后 | 是 | 依赖汇总数据 |
| 权限 / 日志 / 删除保护补齐 | 各模块初版完成后 | 是 | 可以边开发边补，但最终统一收口 |
| 联调 / 初始化数据 / 试运行 | 主要模块完成后 | 否 | 跨模块统一验证 |
| 部署 / 备份 / 上线准备 | 联调通过后 | 否 | 最后阶段 |

## 10. 单人开发的推荐窗口编排

推荐保留 4 个工作窗口即可：

### 10.1 主线窗口

只负责这些内容：

- 公共骨架
- 合并代码
- 公共类型
- 路由和菜单主入口
- 最终回归

### 10.2 业务窗口

一次只做一个主业务模块，例如：

- 客户中心
- 行政书士
- 税理士
- 财务

### 10.3 文件/公共能力窗口

适合放：

- 上传下载预览
- 公共组件
- 枚举和字典
- API 封装

### 10.4 测试与文档窗口

适合放：

- 单元测试
- 联调记录
- 文档同步
- 回归清单

## 11. 什么时候需要独立 worktree

建议这样判断：

- 只是你自己开多个窗口查看或少量修改：可不强制 worktree
- 需要让多个 AI 同时写代码：建议独立 worktree
- 会同时改不同模块、不同文件：建议独立 worktree
- 会改公共文件、路由、类型、菜单：尽量回到主线窗口统一处理

## 12. 最推荐你的实际推进顺序

如果按“稳、质量高、而且快”的目标，我建议你这样推进：

1. 串行做完步骤 1~6
2. 并行做：客户中心 + 文件基础 + 测试整理
3. 客户稳定后，并行做：行政书士 + 税理士 + 文件关联
4. 业务状态稳定后，并行做：财务 + 工作台 + 权限日志补齐
5. 最后统一做：联调、初始化数据、试运行、部署准备

这个顺序比完全串行更快，也比一开始全开更稳。

## 13. 一句话总结

**你一个人也完全可以并行推进，但前提是先把公共基础做稳；后面按“客户 -> 行政/税务 -> 财务/工作台 -> 收口联调”的顺序分批并行，速度和稳定性会更平衡。**
