# 历史签证数据导入 — 验收场景与操作说明（P1-S3e）

> **文档定位**：在 `docs/23_P1历史签证数据导入口径冻結.md`（S3a）与当前实现（S3b 预览、S3c 写入、S3d 工具页）基础上，收口 **操作步骤、模板示例、错误码说明、推荐分批方式** 与 **验收场景**。  
> **口径变更**：须先修订 S3a 冻結文档，再改 migration / API / 校验逻辑；本文随实现调整时，应与 `backend/src/modules/visa-case/import/visa-case-import.constants.ts` 中的码表保持一致。

## 1. 非自动全量迁移声明（必读）

本工具 **不提供** 从旧系统或历史表格 **无人值守、一次性全量自动迁移** 能力，与统一执行计划中 P1-S3 的定位一致：

- **不新建客户主档**：仅匹配已存在的 `customers`（`customer_id` 或 `customer_code`）；无法在导入中批量创建客户或修改主档标识字段。
- **人工校验为主**：须通过管理后台上传 CSV → 全量预览 → 勾选子集 → 子集二次预览通过 → 确认写入；操作员对勾选范围与行级结果负责。
- **分批写入**：鼓励按客户群、时间段或业务批次拆分多文件、多批次提交；每批成功后系统登记内容 SHA-256，避免同一字节流重复落库。
- **单环境**：不支持跨环境一键同步；生产数据须在目标环境内执行导入与审计对账。

### 1.1 幂等键（S3a 方案 A）与重复跑批

- 已实现 **方案 A**：列 `visa_cases.import_reference` 对应 CSV 的 `legacy_case_ref`；非空时在 **同一服务上下文客户** 下唯一（见迁移 `1775900000000-AddVisaCaseImportReference.ts`）。
- 库内已存在 `(customer_id, import_reference)` 时，预览对该 `CASE` 行标记 **DUPLICATE_SKIPPED**，提交时跳过创建但可为同批从属行解析 `visa_case_id`。
- 同一内容 SHA 已成功导入时，再次 commit 返回 **409 / `CSV_ALREADY_IMPORTED`**（见 §7.1）。

### 1.2 写入与回滚策略（S3c）

- **非整批事务**：按行调用既有案件 / 家属 / 路径 / 日志服务写入；**单行 `FAILED` 不触发整批数据库回滚**，同批中已成功行保留（与 §9 场景 11 一致）。
- 操作员须根据下载的 JSON 报告核对失败行，必要时修正 CSV 后另开一批补写。

## 2. 权限与接口

| 项目 | 说明 |
|------|------|
| 权限 | `visaCase:import`（预览与提交均需；默认仅管理者，扩展见 S3a §5） |
| 预览 | `POST /visa-cases/import/preview`，`multipart/form-data` 字段 `file`（UTF-8 CSV） |
| 提交 | `POST /visa-cases/import/commit`，字段同上；须与已成功子集预览的 **同一文件字节内容** 一致方可通过服务端校验链路 |
| 批次一覧（只读） | `GET /visa-cases/import/batches`，`visaCase:import`；query `page` / `pageSize`；返回 `importBatchId`、`contentSha256`、`createdBy`、`createdAt`、`summary` 等，与 `visa_case_import_batches` 及 §3.5 JSON 对账 |
| 批次詳細（只读） | `GET /visa-cases/import/batches/:id`（UUID），`visaCase:import`；单条审计载荷与上表字段一致 |
| 单文件大小 | 上限 **5MB**（与 Multer 配置一致） |

## 3. 前端操作步骤（S3d）

1. 进入签证案件 CSV 导入页（需 `visaCase:import`）。
2. 上传 UTF-8 CSV；系统自动调用 **全量预览**，展示 `contentSha256`、行数、`canProceed` 及各数据行状态。
3. 表格中 **错误行（ERROR）不可勾选**；默认可提交行为 OK、WARNING、DUPLICATE_SKIPPED。
4. 点击「提交所选」时，前端根据勾选行 **拼接子集 CSV**（保留表头 + 选中数据行），再次调用 **预览**；仅当子集 `canProceed === true` 时，才弹出确认框并调用 **commit**。
5. 提交成功后可在结果弹窗 **下载 JSON 报告**（含 `importBatchId`、逐行 `outcome`），用于与 `audit_logs` 对账。
6. 可将已成功行 **取消勾选**，用同一原始文件继续下一批（子集 SHA 与全量不同，不触发「同内容已导入」冲突）。

**注意（子集自洽）**：`FAMILY_MEMBER`、`legacy_case_ref` 非空的 `FILE_PATH`、`CASE_LOG` 行，依赖同一 CSV（或同一子集）内存在匹配的 `CASE` 行（相同服务上下文客户 + 相同 `legacy_case_ref`）。仅勾选从属行而不含对应 `CASE` 会导致子集预览失败或提交阶段案件 ID 无法解析。

### 3.5 审计与数据库对账（S3a §6）

- **JSON 报告**：提交成功响应与可下载报告中的 `importBatchId` 对应表 `visa_case_import_batches.id`；响应中的 `createdBy`、`createdAt`（ISO8601）分别对应 `created_by`、`created_at`，便于与批次表及审计日志人工对账。
- **`audit_logs`**：筛选 `action_type = 'IMPORT'` 且 `target_type = 'VISA_CASE_IMPORT'`，`target_id` 等于上述 `importBatchId`；`user_id` 应与 `visa_case_import_batches.created_by` 一致；`after_value` 中的 `contentSha256`、文件名与计数应与 `visa_case_import_batches` 同行数据一致。
- **时间**：`audit_logs.occurred_at` 与 `visa_case_import_batches.created_at` 为同一成功提交链路内写入，可用于排查时序问题。

## 4. CSV 格式约定

- **编码**：UTF-8（建议带 BOM 亦可，解析会去除 BOM）。
- **换行**：`\n` / `\r\n` 均可；全空行跳过。
- **表头**：第一行非空行为表头；列名 **不区分大小写**（内部会规范为小写）。
- **必填列（全表）**：`record_type`。
- **服务上下文客户（每行）**：`customer_id`（UUID）与 `customer_code` **至少填一个**；客户须存在且为 `ACTIVE`。
- **`record_type` 取值**：`CASE` | `FAMILY_MEMBER` | `FILE_PATH` | `CASE_LOG`（大小写不敏感）。

### 4.1 各记录类型常用列

| record_type | 说明 | 关键列 |
|-------------|------|--------|
| `CASE` | 创建签证案件（`import_reference` ← `legacy_case_ref`） | `legacy_case_ref`（可选但强烈建议，用于幂等）；`is_family_case`；家族签时 `family_link_mode`、`internal_primary_*` 或 `external_primary_*`（含可选 `external_primary_relation_to_applicant`，与 `FamilyRelation` 一致）；`case_status`、`case_type`、`expire_date`（`YYYY-MM-DD`）、`next_follow_up_at`（可解析的日期时间字符串）、`material_status`、`fee_status`、`memo`、`assigned_to`（用户 UUID） |
| `FAMILY_MEMBER` | 案件家属 | **`legacy_case_ref` 必填**；`member_customer_id` 或 `member_customer_code`；`member_role`；`is_primary`（`true`/`false`/`1`/`0` 等）；`display_name_snapshot` |
| `FILE_PATH` | 资料路径台账 | `file_path`；`path_type`（枚举，空则按 `OTHER`）；`legacy_case_ref` 空表示客户级路径，非空表示案件级且须在文件内存在对应 CASE；`display_name`；`path_remark` 或 `remark` |
| `CASE_LOG` | 案件日志 | **`legacy_case_ref` 必填**；`log_type`；`log_content` 或 `content`；可选 `submitted_items`、`missing_items`、`next_action`、`log_next_follow_up_at` |

### 4.2 日期与时间

- **日期**：`YYYY-MM-DD`（如 `2026-04-04`）。
- **日期时间**：`next_follow_up_at`、`log_next_follow_up_at` 等使用 `Date` 可解析字符串（实现为 `new Date(text)` 校验）。

### 4.3 布尔列

`is_family_case`、`is_primary`：`true` / `false` / `1` / `0` / `yes` / `no`（不区分大小写）；留空对 `is_family_case` 视为非家族案件。

### 4.4 幂等与重复

- **文件内**：同一服务客户下 `legacy_case_ref` 在多条 `CASE` 行中重复 → **整表阻断**（`DUPLICATE_LEGACY_REF_IN_FILE`）。
- **库内**：`CASE` 行带 `legacy_case_ref` 且 `(customer_id, import_reference)` 已存在 → 该行预览为 **DUPLICATE_SKIPPED**，提交时跳过创建但可回填 `visa_case_id` 供同批后续从属行使用。
- **同内容重复提交**：整文件内容 SHA-256 已在 `visa_case_import_batches` 登记 → **409**，码 `CSV_ALREADY_IMPORTED`。

## 5. 模板示例（请替换为客户 UUID / customer_code）

下列示例中 `00000000-0000-4000-8000-000000000001` 等请改为真实数据；列可按需增减，未使用的列可省略。

### 5.1 最小单案件（无家族签）

```csv
record_type,customer_code,legacy_case_ref,case_status,is_family_case,case_type,expire_date
CASE,DEMO-CUST,LEG-2024-0001,IN_PROGRESS,false,技人国,2026-12-31
```

### 5.2 家族签 INTERNAL + 家属 + 路径 + 日志（同一 `legacy_case_ref`）

下列为 **单一宽表头** 下多行示例；未用到的列留空，列顺序与表头一一对应。

```csv
record_type,customer_code,legacy_case_ref,is_family_case,family_link_mode,internal_primary_customer_code,case_status,case_type,expire_date,member_customer_code,member_role,is_primary,display_name_snapshot,file_path,path_type,display_name,log_type,log_content,log_next_follow_up_at
CASE,SVC01,FAM-001,true,INTERNAL,PRIMARY01,IN_PROGRESS,家族滞在,2026-12-31,,,,,,,,,,
FAMILY_MEMBER,SVC01,FAM-001,,,,,,,SPOUSE01,SPOUSE,false,配偶者表示名,,,,,,
FILE_PATH,SVC01,FAM-001,,,,,,,,,,,//nas/visa/FAM-001,CASE_DOCUMENT,申請書類,,,
CASE_LOG,SVC01,FAM-001,,,,,,,,,,,,,,FOLLOW_UP,初回ヒアリング済み,2026-04-10T10:00:00.000Z
```

说明：宽表头须覆盖本批会用到的全部列，且 **每行列数须与表头一致**（空列保留逗号）；**禁止** 在数据区插入第二行表头。路径中含逗号或引号时请用 CSV 双引号字段包裹，字段内 `"` 写作 `""`。

**写入顺序**：同一 `legacy_case_ref` 的 `CASE` 行必须出现在同批 CSV 中其 `FAMILY_MEMBER` / 带 `legacy_case_ref` 的路径与日志行 **之前**，以便提交时解析 `visa_case_id`。

## 6. 预览层错误码与含义（`VisaCaseImportErrorCode`）

以下为当前实现中使用的码；接口返回的 `message` 可能为日文，以下中文为释义。

| 错误码 | 典型含义 |
|--------|----------|
| `EMPTY_FILE` | 文件为空或无有效表头 |
| `MISSING_HEADER_ROW` | 常量预留；当前实现以空表头走 `EMPTY_FILE` 等路径为主 |
| `MISSING_RECORD_TYPE_COLUMN` | 缺少必填列 `record_type` |
| `INVALID_RECORD_TYPE` | `record_type` 不是四种之一 |
| `MISSING_SERVICE_CUSTOMER` | 未提供 `customer_id` 与 `customer_code` |
| `CUSTOMER_NOT_FOUND` | UUID 客户不存在 |
| `CUSTOMER_CODE_AMBIGUOUS` | `customer_code` 匹配多于一条 |
| `CUSTOMER_INACTIVE` | 客户非 ACTIVE |
| `INVALID_UUID` | `customer_id`、`member_customer_id`、`internal_primary_customer_id`、`assigned_to` 等 UUID 格式无效 |
| `DUPLICATE_LEGACY_REF_IN_FILE` | 同一客户下 `legacy_case_ref` 在文件内重复（文件级阻断或行级标记） |
| `INTERNAL_REQUIRES_PRIMARY` | INTERNAL 家族签无法解析主申请人 |
| `EXTERNAL_REQUIRES_NAME` | EXTERNAL 家族签缺少 `external_primary_name` |
| `INVALID_ENUM` | 枚举无效（含 `legacy_case_ref` 超长等部分场景） |
| `INVALID_DATE` | 日期/时间格式无效 |
| `INVALID_BOOLEAN` | 布尔列无法解析 |
| `LEGACY_REF_REQUIRED` | 家属行或日志行缺少 `legacy_case_ref` |
| `ORPHAN_FAMILY_ROW` | 家属行在文件内找不到对应 CASE 组 |
| `ORPHAN_FILE_PATH_ROW` | 带 `legacy_case_ref` 的路径行找不到对应 CASE |
| `ORPHAN_LOG_ROW` | 日志行找不到对应 CASE |
| `LOG_TYPE_REQUIRED` | 日志 `log_type` 无效或空 |
| `LOG_CONTENT_REQUIRED` | `log_content` 与 `content` 均为空 |
| `FILE_PATH_REQUIRED` | `file_path` 为空 |
| `MEMBER_CUSTOMER_REQUIRED` | 家属未提供 `member_customer_id` / `member_customer_code` |
| `DISPLAY_NAME_REQUIRED` | 家属缺少 `display_name_snapshot` |

### 6.1 警告码（不单独阻断 `canProceed`）

| 警告码 | 含义 |
|--------|------|
| `FILE_PATH_DUPLICATE_IN_FILE` | 同一客户 + 案件键 + `file_path` 在文件内重复 |

含 WARNING 的行仍可使 `canProceed === true`，由操作员决定是否勾选提交。

## 7. 提交层结果（`VisaCaseImportCommitOutcome`）

| outcome | 含义 |
|---------|------|
| `CASE_CREATED` | 新案件已创建 |
| `MEMBER_ADDED` | 家属已添加 |
| `FILE_PATH_CREATED` | 路径已创建 |
| `CASE_LOG_CREATED` | 案件日志已创建 |
| `SKIPPED_DUPLICATE` | 案件行因既有 `import_reference` 跳过，或创建时撞唯一约束后合流 |
| `FAILED` | 该行失败（预览 ERROR、或运行时异常）；**不回滚** 同批已成功行 |

### 7.1 提交层冲突码

| 错误码 | HTTP | 含义 |
|--------|------|------|
| `CSV_ALREADY_IMPORTED` | 409 | 相同内容 SHA-256 已成功导入过 |

预览 `canProceed === false` 时提交返回 **400**，不会写入批次表。

## 8. 推荐分批与文件组织

| 建议项 | 说明 |
|--------|------|
| 单文件体积 | ≤ **5MB**；过大应拆文件 |
| 行数 | 无硬编码上限；建议每批 **几十～二百行** 量级便于屏幕核对，复杂家族案可更小 |
| 拆分维度 | 按客户群体、担当、旧系统导出批次、时间片拆分，每文件保持 `legacy_case_ref` 在所选子集中自洽 |
| 幂等 | 对需可重跑的模板务必填写稳定 `legacy_case_ref`；避免依赖「无 ref 多次导入」产生重复案件 |
| 审计 | 每批成功后保留下载的 JSON 与 `import_batch_id`，与审计日志对账 |

## 9. 验收场景清单

| # | 场景 | 预期 |
|---|------|------|
| 1 | 空文件 / 仅空白 | `EMPTY_FILE` 或等价阻断，`canProceed = false` |
| 2 | 缺少 `record_type` 列 | `MISSING_RECORD_TYPE_COLUMN`，无数据行结果 |
| 3 | `customer_code` 不存在 | 行级 `CUSTOMER_NOT_FOUND` |
| 4 | `customer_code` 重复多条 | `CUSTOMER_CODE_AMBIGUOUS` |
| 5 | 停用客户 | `CUSTOMER_INACTIVE` |
| 6 | 同一客户两条 `CASE` 使用相同 `legacy_case_ref` | 文件级 `DUPLICATE_LEGACY_REF_IN_FILE`，`canProceed = false` |
| 7 | 库内已存在 `(customer_id, import_reference)` | 预览 `DUPLICATE_SKIPPED`；提交 `SKIPPED_DUPLICATE` 且可解析 `visa_case_id` |
| 8 | `FAMILY_MEMBER` 无对应 `CASE` 行 | `ORPHAN_FAMILY_ROW` |
| 9 | 子集仅勾选家属、不含 CASE | 子集预览失败或提交 `FAILED`（案件 ID 未解析） |
| 10 | 全量预览含 ERROR 行，仅勾选 OK/WARNING/DUPLICATE 子集 | 子集 `canProceed` 可为 true，提交仅处理勾选行 |
| 11 | 同批部分运行时失败 | 失败行 `FAILED`，其余行仍成功；批次仍写入，`failedRowCount` 增加 |
| 12 | 同一子集字节流再次 commit | 第二次 **409** / `CSV_ALREADY_IMPORTED` |
| 13 | 成功批次后下载 JSON | 含 `importBatchId`、`contentSha256`、`createdBy`、`createdAt`、`summary`、`rows[]` |
| 14 | 无 `visaCase:import` | 接口 403；前端提示无权限 |
