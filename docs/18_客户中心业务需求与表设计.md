# 客户中心业务需求与表设计

> 文档定位：基于当前仓库代码、现有项目文档与已冻结业务口径整理。  
> 适用范围：一期（P0）当前版本的客户中心。  
> 目标：明确“目前已经在做什么、依赖什么表、和其他模块如何关联”。

---

## 1. 模块定位

客户中心是一期的核心主入口，承担以下职责：

1. 统一维护客户主档，避免个人信息、法人信息、业务信息分散在多个模块。
2. 作为行政案件、税务合同、文件、财务等模块的统一关联入口。
3. 提供客户详情页，让业务人员可以从一个页面查看客户基本情况和关联业务。
4. 对个人客户补充在留资格、家族成员、主客户关联与到期提醒信息。
5. 通过客户备注记录日常跟进过程，保留可追溯的沟通和备忘痕迹。

当前版本延续“客户中心化”原则：大部分业务表都通过 `customer_id` 与客户主档关联。

## 2. 当前业务范围

### 2.1 已实现范围

当前客户中心已落地的业务能力包括：

1. 客户列表分页查询。
2. 客户新建。
3. 客户编辑。
4. 客户逻辑删除与恢复。
5. 客户详情查看。
6. 客户备注的新增、分页、编辑、删除。
7. 个人客户在留期限提醒列表。
8. 客户详情下挂行政案件列表。
9. 客户详情下挂税务合同列表。
10. 客户详情下挂文件面板。
11. 客户与内部员工分工关系的只读展示。

### 2.2 当前暂未完整闭环的范围

以下内容已有规划或局部占位，但当前客户中心内尚未形成完整闭环：

1. 客户详情内财务 Tab 目前仍为占位，尚未完整展示请款、收款、预收款明细。
2. `customer_staff_relations` 已有表结构与详情展示，但当前客户中心前端尚未提供独立维护入口。
3. 项目文档中曾建议单独提供 `/customers/{id}/overview` 聚合接口，但当前实现主要通过客户详情页分 Tab 加载关联模块数据。

## 3. 业务目标

### 3.1 核心目标

1. 建立统一客户主档。
2. 支持个人客户与法人客户双类型建档。
3. 让同一客户可同时归属于行政、税务或双业务服务线。
4. 让业务人员快速查看客户当前状态、负责人和关联业务。
5. 保证客户相关重要操作具备权限控制和审计能力。

### 3.2 管理目标

1. 降低跨模块重复录入。
2. 通过客户详情页集中查看关联业务。
3. 通过在留提醒提前识别即将到期的个人客户。
4. 通过客户备注沉淀跟进记录，减少信息散落在聊天工具或口头沟通中。

## 4. 当前业务口径

### 4.1 客户类型

客户分为两类：

| 枚举值 | 说明 |
| --- | --- |
| `PERSONAL` | 个人客户 |
| `COMPANY` | 法人客户 |

### 4.2 服务类型

客户可归属以下服务线：

| 枚举值 | 说明 |
| --- | --- |
| `ADMIN` | 行政书士业务 |
| `TAX` | 税理士业务 |
| `BOTH` | 同时存在双业务 |

### 4.3 客户状态

| 枚举值 | 说明 |
| --- | --- |
| `ACTIVE` | 在用 |
| `INACTIVE` | 停用 |

### 4.4 客户编码规则

当前服务端会在创建客户时自动生成客户编码：

1. 法人客户前缀为 `C`，例如 `C00001`。
2. 个人客户前缀为 `P`，例如 `P00001`。
3. 客户编码全局唯一。

### 4.5 个人客户补充口径

个人客户除基础信息外，当前版本还支持以下附加信息：

1. 国籍。
2. 在留资格。
3. 在留到期日。
4. 是否为家族成员。
5. 家族关系。
6. 主客户关联。
7. 提前提醒天数。

当前已冻结的家族关系枚举如下：

| 枚举值 | 说明 |
| --- | --- |
| `SPOUSE` | 配偶 |
| `CHILD` | 子女 |
| `PARENT` | 父母 |
| `OTHER` | 其他 |

### 4.6 在留提醒口径

当前版本已实现个人客户在留到期提醒：

1. 查询范围为未来 90 天内到期，包含已过期客户。
2. 按到期日升序排列。
3. 返回剩余天数与提醒等级。

提醒等级如下：

| 枚举值 | 说明 |
| --- | --- |
| `EXPIRED` | 已过期 |
| `URGENT` | 紧急 |
| `HIGH` | 高优先级 |
| `NORMAL` | 正常提醒 |

### 4.7 客户备注口径

客户备注当前支持以下分类：

| 枚举值 | 说明 |
| --- | --- |
| `FOLLOW_UP` | 跟进 |
| `MEMO` | 备忘 |
| `GENERAL` | 通用备注 |

### 4.8 客户与员工关系口径

客户与内部员工可建立角色分工关系：

| 枚举值 | 说明 |
| --- | --- |
| `PRIMARY` | 主担当 |
| `SECONDARY` | 次担当 |
| `SUPPORT` | 协作支持 |

## 5. 当前功能需求

### 5.1 客户列表

客户列表页需要满足以下需求：

1. 分页展示客户基础信息。
2. 支持按关键字搜索客户名称、客户编码、电话、邮箱。
3. 支持按客户类型筛选。
4. 支持按服务类型筛选。
5. 支持按客户状态筛选。
6. 支持按负责人筛选。
7. 支持按创建时间、更新时间等白名单字段排序。
8. 支持从列表直接进入详情页。
9. 支持从列表直接发起编辑和删除操作。

列表展示字段以当前实现为准，主要包括：

1. 客户编码。
2. 客户类型。
3. 客户名称。
4. 电话。
5. 服务类型。
6. 负责人。
7. 状态。
8. 创建时间。

### 5.2 客户新建与编辑

客户建档和编辑需要满足以下要求：

1. 必填字段至少包含客户类型、客户名称、服务类型。
2. 客户编码由系统自动生成，不允许前端手工输入。
3. 电话、邮箱、地址、负责人为可选字段。
4. 法人客户可维护法人编号、决算月、代表者姓名。
5. 个人客户可维护国籍、在留资格、在留到期日等附属信息。
6. 若个人客户被标记为家族成员，则需补充家族关系。
7. 支持主客户关联，用于建立家族成员与主客户之间的关系。
8. 客户类型变更时，系统需同步切换公司信息或个人信息子档案。

### 5.3 客户详情

客户详情页是当前客户中心的主要业务入口，需要满足：

1. 展示客户共享基础信息。
2. 根据客户类型展示公司信息或个人信息。
3. 展示负责人和客户状态。
4. 展示个人客户在留提醒相关派生信息，如剩余天数与提醒等级。
5. 展示客户与员工的分工关系。
6. 通过分 Tab 方式查看备注、行政案件、税务合同、文件等关联数据。

当前详情页 Tab 结构如下：

1. 基本信息。
2. 客户备注。
3. 行政案件。
4. 税务合同。
5. 财务信息。
6. 文件资料。

### 5.4 客户备注

客户备注需要满足以下业务要求：

1. 备注必须隶属于某个客户。
2. 支持新增备注。
3. 支持分页查看备注时间线。
4. 支持按备注类型筛选。
5. 支持编辑备注内容和类型。
6. 支持逻辑删除备注。
7. 记录备注创建人，便于后续追踪。
8. 备注内容长度上限为 5000 字符。

### 5.5 在留期限提醒

在留提醒页当前属于客户中心的专项能力，需要满足：

1. 面向个人客户的在留到期风险识别。
2. 统一列出未来 90 天内到期的客户。
3. 展示客户名称、家族关系、到期日、剩余天数、提醒等级。
4. 支持从提醒记录跳转到客户详情页。

### 5.6 与其他业务模块的关联要求

当前客户中心不是孤立模块，而是其他业务模块的聚合入口，需要满足：

1. 一个客户可以关联多个行政案件。
2. 一个客户可以关联多个税务合同。
3. 一个客户可以关联多个文件。
4. 一个客户可以关联财务数据，如请款、收款、预收款。
5. 客户详情页应逐步形成跨模块查看入口，而不是要求用户分别到各模块重复搜索。

## 6. 权限与可见性要求

### 6.1 当前接口权限

客户中心当前接口权限点包括：

| 权限编码 | 说明 |
| --- | --- |
| `customer:list` | 查看客户列表 |
| `customer:detail` | 查看客户详情 |
| `customer:create` | 新建客户 |
| `customer:edit` | 编辑客户 |
| `customer:delete` | 删除客户 |

备注接口沿用客户详情、编辑、删除权限。

### 6.2 当前数据可见性口径

根据已冻结业务口径，一期默认采用较宽的数据可见性：

1. 业务员工可以查看全部客户，不做“仅本人负责客户”过滤。
2. 财务中心菜单不对业务员工开放。
3. 客户详情中的财务数据仅允许逐步展示摘要，不直接开放全部财务明细。

## 8. 核心表详细设计

### 8.1 `customers`

客户主档表，是客户中心的核心主表。

| 字段 | 类型 | 约束/索引 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK | 主键 |
| `created_at` | timestamptz |  | 创建时间 |
| `updated_at` | timestamptz |  | 更新时间 |
| `deleted_at` | timestamptz | 软删除 | 逻辑删除时间 |
| `customer_code` | varchar(50) | 唯一 | 客户编码 |
| `customer_type` | varchar(20) |  | `PERSONAL` / `COMPANY` |
| `customer_name` | varchar(200) | 普通索引 | 客户名称 |
| `phone` | varchar(50) |  | 电话 |
| `email` | varchar(120) |  | 邮箱 |
| `address` | varchar(500) |  | 地址 |
| `service_type` | varchar(20) | 普通索引 | `ADMIN` / `TAX` / `BOTH` |
| `owner_user_id` | uuid | 普通索引，FK -> `users.id` | 负责人 |
| `status` | varchar(20) |  | `ACTIVE` / `INACTIVE` |
| `created_by` | uuid |  | 创建人 |
| `updated_by` | uuid |  | 更新人 |

设计说明：

1. 客户主档使用软删除，以保留审计能力和恢复能力。
2. `owner_user_id` 用于列表筛选、详情展示和责任归属。
3. `customer_code` 采用业务编码，不能与技术主键混用。

### 8.2 `company_info`

法人客户附属信息表，与 `customers` 为一对一关系。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK | 主键 |
| `customer_id` | uuid | 唯一，FK -> `customers.id` | 关联客户 |
| `corporation_number` | varchar(50) |  | 法人编号 |
| `fiscal_month` | smallint |  | 决算月，1-12 |
| `representative_name` | varchar(120) |  | 代表者姓名 |
| `created_at` | timestamptz |  | 创建时间 |
| `updated_at` | timestamptz |  | 更新时间 |

设计说明：

1. 仅当客户类型为法人时使用。
2. `customer_id` 唯一，保证一个客户只有一条法人附属信息。

### 8.3 `person_info`

个人客户附属信息表，与 `customers` 为一对一关系。

| 字段 | 类型 | 约束/索引 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK | 主键 |
| `customer_id` | uuid | 唯一，FK -> `customers.id` | 关联客户 |
| `nationality` | varchar(80) |  | 国籍 |
| `residence_status` | varchar(100) |  | 在留资格 |
| `residence_expire_date` | date | 条件索引 | 在留到期日 |
| `is_family_member` | boolean | 默认 `false` | 是否家族成员 |
| `family_relation` | varchar(30) |  | 家族关系 |
| `primary_customer_id` | uuid | FK -> `customers.id` | 主客户 ID |
| `remind_days_before` | int |  | 提前提醒天数 |
| `created_at` | timestamptz |  | 创建时间 |
| `updated_at` | timestamptz |  | 更新时间 |

设计说明：

1. 仅当客户类型为个人时使用。
2. `residence_expire_date` 建有条件索引，支撑在留提醒查询。
3. `primary_customer_id` 用于家族成员挂到主客户。
4. `remind_days_before` 当前已入库，但业务提醒接口当前按统一 90 天窗口执行。

### 8.4 `notes`

客户备注表，用于客户跟进和备忘记录。

| 字段 | 类型 | 约束/索引 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK | 主键 |
| `created_at` | timestamptz |  | 创建时间 |
| `updated_at` | timestamptz |  | 更新时间 |
| `deleted_at` | timestamptz | 软删除 | 逻辑删除时间 |
| `customer_id` | uuid | 普通索引，FK -> `customers.id` | 所属客户 |
| `content` | text |  | 备注内容 |
| `note_type` | varchar(30) | 默认 `GENERAL` | 备注类型 |
| `created_by` | uuid | FK -> `users.id` | 创建人 |

设计说明：

1. 备注采用软删除，避免跟进历史直接丢失。
2. 当前备注更新时间会在前端时间线中显示。
3. 备注是客户详情页中的高频操作数据。

### 8.5 `customer_staff_relations`

客户与内部员工分工关系表。

| 字段 | 类型 | 约束/索引 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | PK | 主键 |
| `customer_id` | uuid | 普通索引，FK -> `customers.id` | 客户 |
| `user_id` | uuid | 普通索引，FK -> `users.id` | 员工 |
| `relation_type` | varchar(30) | 默认 `PRIMARY` | 关系类型 |
| `created_at` | timestamptz |  | 创建时间 |

设计说明：

1. `(customer_id, user_id)` 建有唯一索引，避免同一员工重复挂到同一客户。
2. 当前详情页只读展示该表数据，后续可补维护入口。

## 9. 关联关系设计

### 9.1 一对一关系

1. `customers` -> `company_info`
2. `customers` -> `person_info`

业务规则：

1. 法人客户通常只挂 `company_info`。
2. 个人客户通常只挂 `person_info`。
3. 客户类型切换时，附属档案需要跟随切换。

### 9.2 一对多关系

1. `customers` -> `notes`
2. `customers` -> `customer_staff_relations`
3. `customers` -> `admin_cases`
4. `customers` -> `tax_contracts`
5. `customers` -> `files`
6. `customers` -> `invoices`
7. `customers` -> `payments`

### 9.3 自关联关系

`person_info.primary_customer_id -> customers.id`

用途：

1. 用于表达家族成员挂靠的主客户。
2. 便于在个人客户详情中跳转查看主客户档案。

## 10. 索引与查询设计建议

当前客户中心已体现出以下查询需求，表设计需持续围绕这些场景：

1. 按客户名称查询。
2. 按客户编码查询。
3. 按服务类型筛选。
4. 按负责人筛选。
5. 按在留到期日范围扫描个人客户。
6. 按客户 ID 查询备注、案件、合同、文件等关联记录。

因此，当前需要重点保留或持续强化以下索引：

1. `customers.customer_code` 唯一索引。
2. `customers.customer_name` 普通索引。
3. `customers.service_type` 普通索引。
4. `customers.owner_user_id` 普通索引。
5. `person_info.residence_expire_date` 条件索引。
6. `notes.customer_id` 普通索引。
7. `customer_staff_relations.customer_id`、`user_id` 及联合唯一索引。

## 11. 当前接口与表的映射关系

| 接口 | 主要读写表 | 说明 |

## 12. 当前版本建议的验收点

如果以“客户中心当前版本可交付”为目标，建议至少验证以下内容：

1. 能创建个人客户与法人客户两类档案。
2. 创建客户后能自动生成正确的客户编码。
3. 客户列表可以按关键字、客户类型、服务类型、状态筛选。
4. 客户详情能够正确展示附属信息。
5. 个人客户可展示在留期限与提醒等级。
6. 家族成员客户可以关联主客户。
7. 备注可新增、编辑、删除并保留创建人信息。
8. 客户详情可看到该客户下的行政案件、税务合同和文件入口。
9. 删除客户为逻辑删除，且支持恢复。

---

## 13. 后续补齐建议

基于当前实现状态，客户中心后续建议优先补齐以下内容：

1. 客户详情内财务摘要或财务明细展示闭环。
2. 客户与员工分工关系的维护入口。
3. 更完整的客户总览聚合接口，减少详情页多次分散请求。
4. 在留提醒规则与 `remind_days_before` 字段的真正联动。
5. 更细的数据权限控制，如按负责人或角色限制查看范围。

---

## 14. 一句话总结

当前客户中心已经形成“客户主档 + 附属信息 + 跟进备注 + 在留提醒 + 业务关联入口”的基础闭环，其核心数据库设计围绕 `customers` 主表展开，使用 `company_info`、`person_info`、`notes`、`customer_staff_relations` 承载补充信息，并通过 `customer_id` 向行政、税务、文件、财务模块扩展。
