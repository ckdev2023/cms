## 1. 背景与目标

### 1.1 背景

- P0 已落地 `visa_cases`、`visa_case_family_members`、`customer_file_paths`，以及复用 `notes` 的案件日志（`visa_case_id IS NOT NULL`），见 `docs/21_签证客户中心P0验收与Rollout说明.md`。
- 统一执行计划中 **P1-S3** 明确：**不纳入 P0 自动全量迁移**，以 **人工校验 + 分批写入** 为主。
- 批量写入必须 **复用既有创建/更新案件、家属、路径（及若范围内则日志）的服务层**，避免旁路 SQL（计划 P1-S3c）。

### 1.2 S3a 目标

将下列口径一次冻結，避免 S3b/S3c 各自解读：

- 哪些表允许被导入工具写入；
- 行数据如何解析到系统内客户与主申请人；
- 与已有案件冲突时跳过、更新还是报错；
- 谁可以执行导入、系统必须留下哪些审计痕迹。

## 2. 导入实体范围（IN / OUT）

### 2.1 允许写入（IN）

| 实体 | 表 / 条件 | 说明 |
|------|-----------|------|
| **签证案件** | `visa_cases` | 创建新案件或（在符合 §4 的前提下）更新已选定目标案件。 |
| **案件级家属** | `visa_case_family_members` | 与案件绑定的成员增删改须满足库内唯一约束（每案单一主申请人、`visa_case_id + customer_id` 不重复）。 |
| **资料路径台账** | `customer_file_paths` | 仅路径元数据；不触发 `files` 上传。`customer_id` 必填；`visa_case_id` 可空（客户级）或非空（案件级）。 |
| **案件日志（可选）** | `notes`（`visa_case_id IS NOT NULL`） | **可选纳入**：模板与预览层用列开关控制是否生成日志行。导入的客户备注（`visa_case_id IS NULL`）**不在** P1-S3 范围内。 |

### 2.2 明确禁止或未授权（OUT）

| 类别 | 说明 |
|------|------|
| **客户主档** | 不得通过本工具 **新建** `customers` / `person_info` / `company_info`；不得修改客户主档关键标识字段（如 `customer_code`）。匹配阶段 **只读** 客户表。 |
| **客户备注** | 不得批量写入 `notes` 且 `visa_case_id IS NULL`（保持与客户备注 API 边界一致）。 |
| **上传附件** | 不得写入 `files` 或触发对象存储上传。 |
| **行政案件** | 不涉及 `admin_cases` 及其子表。 |
| **材料 checklist 实例** | P1-S1 材料项实例（如 `visa_case_material_items` 等）**默认不纳入** P1-S3 首批导入范围；若未来扩展须先修订本文与 `docs/22_材料チェックリスト口径冻結.md`。 |
| **物理删除案件** | 不得批量物理删除 `visa_cases`；与 P0「有日志或路径的案件不做物理删除」原则一致。 |

## 3. 客户与主申请人匹配规则

### 3.1 服务上下文客户（`visa_cases.customer_id`）

表示 **当前被服务的系统内客户**（客户详情挂载、权限校验上下文），必须解析为已存在客户：

| 优先级 | 字段 | 规则 |
|--------|------|------|
| **首选** | 系统 `customer_id`（UUID） | 须存在且通常 `status = ACTIVE`；删除或停用客户上的新案件导入应判为 **错误行**（具体错误码由 S3b 定义）。 |
| **备选** | `customer_code`（唯一） | 全表唯一匹配；若匹配 0 或多于 1 条 → **错误行**，不得在预览中静默新建客户。 |

### 3.2 内部主申请人模式（`family_link_mode = INTERNAL`）

- 必须能解析 **`internal_primary_customer_id`**：允许直接给 UUID，或通过 **主申请人的 `customer_code`** 映射到同一 `customers` 主档。
- 解析结果须与 P0 规则一致：主申请人必须是系统内客户；**不在导入流程中创建「外部主申请人客户」**。

### 3.3 外部主申请人模式（`family_link_mode = EXTERNAL`）

- **不** 要求 `internal_primary_customer_id`；使用 `visa_cases` 上既有快照字段：`external_primary_name`、`external_primary_case_type`、`external_primary_expire_date`（可空按业务）。
- **可选列** `external_primary_relation_to_applicant`：表示外部主申与 **本案系统内申请人（服务上下文客户）** 的家属关系，取值与主档 `FamilyRelation`（`SPOUSE` / `CHILD` / `PARENT` / `OTHER`）一致；列为空或省略时对应库字段为 `NULL`。若列有值但无法解析为上述枚举，预览/本地校验按 `INVALID_ENUM` 拒绝该行。
- 不在 `customers` 表为外部主申请人建档。

### 3.4 家属成员行

- 每个家属必须解析到 **已存在** 的 `customer_id`（UUID 或 `customer_code`），写入 `visa_case_family_members.customer_id`。
- `member_role`、`is_primary`、`display_name_snapshot` 须符合既有枚举与「一案一主申请人」约束；违反约束的行的处理见 §4（预览阶段报错或整行拒绝）。

### 3.5 案件日志行（若纳入 IN）

- `notes.customer_id`：与 **服务上下文客户**（§3.1）一致，或与既有 API 约定一致（通常与案件 `customer_id` 一致）。
- `notes.visa_case_id`：指向本次导入创建或绑定的目标案件。
- `log_type`：必填（与 `VisaCaseLogType` 一致）；其余结构化字段可为空。

## 4. 与既有数据的冲突与幂等策略

### 4.1 现状

- `visa_cases` **没有** 与旧系统对齐的全局业务唯一键；同一 `customer_id` 下允许多条案件记录。
- 若不做幂等设计，**重复执行同一文件会产生重复案件**。

### 4.2 行级业务外键（冻結）

- 导入模板 **须** 支持可选列 **`legacy_case_ref`**（字符串，建议长度 ≤ 100）：表示旧系统或表格中的稳定案件引用号，在同一 **服务上下文客户** 下语义唯一（由事务所填写规范保证）。
- **实现阶段（S3b/S3c）** 二选一落地（在 S3b 技术方案中选定并在 S3e 验收中说明）：
  - **方案 A（推荐）**：新增可空字段 `visa_cases.import_reference`（名称以最终实现为准），并建立 **`UNIQUE (customer_id, import_reference)`**（`import_reference IS NOT NULL` 时生效的部分唯一索引亦可），用于幂等与冲突检测。
  - **方案 B**：独立 **映射表**（如 `visa_case_import_keys`）保存 `(customer_id, legacy_case_ref) → visa_case_id`，不修改 `visa_cases` 列。

未落地 A/B 前，**不得** 声称行级幂等已具备；仅可依赖 §4.4 的批次与人工策略。

### 4.3 冲突场景与默认行为（冻結）

| 场景 | 默认行为 |
|------|----------|
| 新行：`customer_id` + `legacy_case_ref` 在映射/DB 中 **不存在** | **创建** 新 `visa_cases` 及从属行。 |
| 新行：`legacy_case_ref` 已绑定已有案件 | **默认跳过** 该案行，并在结果报告中标记 **DUPLICATE_SKIPPED**；**禁止** 静默再插一条重复案件。 |
| 操作员在 UI **显式选择「更新已有案件」** 且指定 `visa_case_id` | 允许 **更新** 案件标量字段（S3c 定义白名单），家属/路径/日志按 **追加或替换策略** 在 S3c 文档中单列（避免混用）。 |
| 同一 CSV 内 **重复** `(customer_id, legacy_case_ref)` | **预览失败** 或仅保留首行（二选一，**须在 S3b 固定**并在模板说明中写明）。 |
| `customer_file_paths` 重复路径 | 不强制 DB 唯一；**预览中警告** 重复 `(customer_id, file_path, visa_case_id)`，由操作员勾选是否仍写入。 |

### 4.4 批次与重复跑批（幂等）

- 每一次 **已确认的写入** 必须生成 **`import_batch_id`**（UUID），并写入批次级审计（§6）。
- **同一文件内容重复提交**（相同内容哈希或相同 `import_batch_id` 重放）：**拒绝** 第二次整批自动写入，或返回「已处理」**仅只读报告**（S3c 选定一种并在验收中覆盖）。

### 4.5 与 P0 业务约束对齐

- 家属：遵守 `visa_case_family_members` 部分唯一索引（每案一个 `is_primary = true`）与 `(visa_case_id, customer_id)` 唯一。
- 有日志或路径的案件：**不** 做物理删除；导入工具 **不** 提供批量硬删。

## 5. 操作权限

### 5.1 冻結结论

- 导入属于 **高风险批量写**，**不得** 仅依赖「能登录后台」即默认可用。
- **新增独立权限码**：`visaCase:import`（命名与 `permission-codes.ts` 保持一致即可）。
- **默认角色**：仅 **管理者** 持有；若事务所授权高级业务员工，须在 `seed` 与权限矩阵中显式勾选，并在变更记录中说明。

### 5.2 与现有子权限的关系

- 执行写入时，服务端除校验 `visaCase:import` 外，仍须校验实际触及资源的操作等价权限，或 **明确规定**：持有 `visaCase:import` 即视为在同一请求批次内授权创建/更新案件、家属、路径及（若开启）案件日志，**以避免权限绕过**。推荐实现：**批次入口只验 `visaCase:import`，内部使用系统已信任的 service 层且不绕过 Guard**（具体以 S3c 实现为准，但不得出现「无签证编辑权却能导入改案」的漏洞）。

### 5.3 只读预览

- **解析与预览 API**（dry-run）：至少需 `visaCase:import` 或 **`visaCase:detail` + `visaCase:import`（预览只读）** 之一组合；冻結推荐：**预览与提交均要求 `visaCase:import`**，以降低信息泄露面（S3b 可微调，须在 S3e 写明）。

## 6. 审计要求

### 6.1 批次级审计（必填）

每一批 **确认写入** 必须在 `audit_logs`（或项目约定的统一审计模块）留下 **至少一条** 记录，建议字段含义如下：

| 字段 | 建议内容 |
|------|----------|
| `userId` | 操作者 |
| `actionType` | 若现有枚举无专用值，可用 `CREATE` 或扩展 `IMPORT`（实现时二选一并在常量中冻結） |
| `targetType` | `SYSTEM` 或扩展 `VISA_CASE_IMPORT`（实现时二选一） |
| `targetId` | `import_batch_id` |
| `afterValue`（或等价 JSON） | 含：`import_batch_id`、文件名/内容哈希、总行数、成功/跳过/失败计数、可选存储路径（若文件落盘） |
| `ipAddress` / `deviceInfo` | 与现有 `AuditLogInterceptor` 一致则复用 |

**实现冻結（与 `audit_logs` 表及 `LogService.createAuditLog` 一致）**：

- `actionType`：`IMPORT`（`AuditActionType.IMPORT`）
- `targetType`：`VISA_CASE_IMPORT`（`AuditTargetType.VISA_CASE_IMPORT`）
- `targetId`：成功提交后生成的批次主键 UUID（即下文 `visa_case_import_batches.id` / API `importBatchId`）
- `afterValue`：JSON，至少含 `importBatchId`、`contentSha256`、`fileName`（可空）及与 `visa_case_import_batches.summary` 一致的汇总计数字段（`rowCount`、各类成功/跳过/失败计数等）
- `occurredAt`：由列默认值写入，表示该条审计记录落库时间（与批次表 `created_at` 同一事务内先后写入，可对账）

### 6.2 明细审计

- **不强制** 为每一行案件再写一条 `audit_logs`（避免洪泛），但 **若** 现有 `visa-case` 写操作已带 `@AuditAction`，导入走同一 service 时 **可自然产生**  per-entity 记录；此行为视为加分项而非 S3a 硬门槛。

### 6.3 与人工作业追溯

- 前端须保留 **可下载的结果报告**（成功/跳过/失败行及原因码），与 `import_batch_id` 关联，便于与 `audit_logs` 对账。

### 6.4 批次登记表 `visa_case_import_batches`（与 §4.4、`audit_logs` 对账）

除 §6.1 的 `audit_logs` 外，每次 **确认写入成功** 须在表 `visa_case_import_batches` 登记一行，用于 **同内容 SHA 幂等**（§4.4）及与审计、前端 JSON 报告对账。列语义冻結如下：

| 列名（DB snake_case） | 语义 | 与 §6.1 / API 的对应关系 |
|----------------------|------|-------------------------|
| `id` | 批次主键 UUID | 即 `import_batch_id` / API 字段 `importBatchId`；与 `audit_logs.target_id` 一致 |
| `content_sha256` | 本次提交 CSV 原始字节的 SHA-256（十六进制小写，长度 64） | 与 `afterValue.contentSha256` 一致；**全表唯一**，重复字节流不得第二行 |
| `created_by` | 操作者用户 UUID | 与 `audit_logs.user_id` 一致 |
| `created_at` | 批次行写入时间（`timestamptz`） | 与同一批 `audit_logs.occurred_at` 可对账（先后写入、时间戳接近） |
| `summary` | `jsonb`，建议含 `fileName`、总行数、各类 outcome 计数 | 与 `afterValue` 中展开后的汇总字段一致，便于 SQL/报表直接查批次 |

**（2026-04 修订 · 性能索引）**：迁移 `1776500000000-AddVisaCaseImportBatchesCreatedAtIndex` 在 `visa_case_import_batches.created_at` 上增加 **降序 B-Tree 索引**，用于管理端/工具侧 **按提交时间倒序分页** 拉取批次列表；不改变 §6.4 列语义与幂等契约。总览见 `docs/21` §2.4。

## 7. 明确不在 P1-S3 首批范围的事项

- 自动根据在留卡 OCR 或邮箱匹配客户。
- 修改 `person_info.primary_customer_id` 与客户主档层家族关系（与 P0「两套关系并存、不自动同步」一致）。
- 导入 `MaterialStatus` 以外的 P1 材料 checklist 逐项状态。
- 跨环境一键同步（仅单环境内导入）。
