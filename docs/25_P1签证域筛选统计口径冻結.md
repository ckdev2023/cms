# 签证域筛选、客户派生风险与统计 KPI 口径冻結（P1-S4a）

> **文档定位**：P1-S4（签证域筛选与统计）的 **S4a 冻結**。定义跨客户案件列表筛选维度、客户列表 **派生风险** 规则、只读统计 KPI、权限默认复用方式及性能边界。  
> **提醒桶与优先级** 与 P0 一致，见 `docs/21_签证客户中心P0验收与Rollout说明.md` §9；本文件将同一套优先级映射到「派生风险」与统计口径，避免 S4b–S4g 各自解读。

---

## 1. 目标与不在范围

### 1.1 目标

- 为 **`GET /visa-cases`（或等价）** 提供统一的查询维度冻結清单。
- 为 **客户列表扩展查询** 提供只读 **派生风险** 标签的计算规则（**不落库**，不修改 `customers.status` 语义）。
- 为 **只读统计 API** 提供 KPI 清单与与提醒桶的对齐关系。
- 默认 **复用 P0 已存在权限**；不引入「仅本人案件」过滤（属 P2-S2）。

### 1.2 明确不在 P1-S4 范围

- 替换旧在留提醒页或强制跳转新入口（P1-S5）。
- 材料 checklist 实例级筛选（属 P1-S1/S2）。
- 实时大屏级秒级刷新、跨租户聚合、导出超大结果集（若需另立非功能需求）。

| 入口 | 策略 |
|------|------|
| **全局签证案件列表** | 新增独立路由（例如 `/visa-cases`），与「客户详情内案件 Tab」并存；菜单挂载在签证/客户相关业务分组下，需 `visaCase:list`。 |
| **客户详情** | 保持现有客户上下文案件列表 API；不强制与全局列表同一 UI，但 **筛选字段语义** 应对齐本文 §3。 |
| **统计视图** | 可与全局案件列表 **同页区块** 或 **独立子路由**；只读，需 `visaCase:list`（或与列表一致的查看权限）。 |

## 3. 案件侧筛选维度（冻結）

以下维度为 P1-S4 **应支持** 的查询条件（具体字段名以 Query DTO 为准，语义以本文为准）。

| 维度 | 说明 | 备注 |
|------|------|------|
| **服务上下文客户** | `customer_id` 精确或客户姓名/编码搜索（若列表需展示客户列） | 与 `visa_cases.customer_id` 一致 |
| **案件状态** | `case_status` 多选 | 枚举见 `VisaCaseStatus` |
| **负责人** | `assigned_to`（用户 ID）可选多选或单选 | 空值表示未指定负责人 |
| **材料摘要** | `material_status` 多选 | P0 手工维护字段，非 checklist 推导 |
| **费用状态** | `fee_status` 多选 | 可选 |
| **到期日区间** | `expire_date` from / to（含边界约定在 DTO 中固定） | **统计新提醒时以 `expire_date` 为准**；`external_primary_expire_date` **不参与** |
| **下次跟进区间** | `next_follow_up_at` 或「最新日志上的下次跟进」 | 列表筛选可与提醒服务取数逻辑对齐或可解释差异（须在 S4h 说明） |
| **家庭签** | `is_family_case`、`family_link_mode` | 可选 |
| **补件相关** | `case_status = SUPPLEMENT` **或** 布尔「最新日志含缺失/补件」 | 与 P0 补件桶条件一致时可合并为一个筛选勾选项 |
| **派生：提醒桶** | 按 §4 计算的 `VisaReminderType` 或子集筛选 | 仅派生字段，不落库 |
| **关键词** | `case_type` / `memo` 模糊 | 可选，注意索引与性能 §7 |

**默认排序建议（冻結）**：先按「派生风险优先级」升序（数值越小越紧急），再按 `expire_date` 升序、`updated_at` 降序；若实现采用单一 `ORDER BY`，须在 S4h 写明。

## 4. 客户列表派生风险（冻結）

### 4.1 语义

- **派生风险** 表示：在该客户名下 **至少一条** 符合条件的 `visa_cases` 记录时，在客户列表上展示的 **只读标签**（可多标签或取最高优先级一条，**冻結为下列之一，实现选定后写进 S4h**）：
  - **推荐**：展示 **最高优先级** 单一标签（与提醒页去重一致，列表更简洁）。
  - **可选**：展示多标签（需 UI 规范，避免溢出）。

下文按 **最高优先级** 定义「派生风险」枚举值。

### 4.2 枚举（与 P0 `VisaReminderType` 对齐）

| 值 | 含义（与 `docs/21` §9 一致） |
|----|------------------------------|
| `SUPPLEMENT` | 补件提醒：案件 `case_status = SUPPLEMENT`，或 **最新** 案件日志存在缺失材料/补件动作（与 P0 S14 一致） |
| `TODAY_FOLLOW_UP` | 今日待跟进：`next_follow_up_at` 为今日（案件字段或最新日志，按 P0 实现口径） |
| `EXPIRING_7_DAYS` | 7 天内到期：`expire_date` 落在 [今天, 今天+7 天]，**或已过期**（已过期视为最高紧急度归此桶） |
| `EXPIRING_2_MONTHS` | 2 个月内到期：`expire_date` 落在 (今天+7 天, 今天+2 个月] |
| （无） | 无任何案件命中上述条件则不展示风险标签 |

### 4.3 同一客户多案件去重（冻結）

- 对客户 C，遍历其关联案件，按 `docs/21` §9 **去重优先级**：  
  **补件 > 今日待跟进 > 7 天内到期 > 2 个月内到期**。
- 客户列表仅展示 **优先级最高** 的一档；**不** 用 `external_primary_expire_date` 参与计算。
- `customers.status` 仍为 `ACTIVE/INACTIVE` 主档语义；派生风险 **不改变** 客户状态字段。

### 4.4 客户列表筛选（冻結）

- 支持按上述派生风险 **过滤客户**（例如「仅显示存在 SUPPLEMENT 的客户」）：语义为 EXISTS 子查询 / JOIN，**非** 持久化列。

## 5. 统计 KPI（冻結，只读）

以下 KPI 由 **聚合查询** 输出，权限与案件列表只读一致；数值应与 `/visa-reminders` 或案件域服务 **可解释对齐**（允许实现上复用同一 SQL 片段，差异须在 S4h 记录）。

| KPI | 定义 |
|-----|------|
| **按 `case_status` 计数** | 各状态案件数（可排除 `CANCELLED` 是否计入在 S4b 固定） |
| **按派生提醒桶计数** | 对 **案件** 按 §3/§4 规则去重后归入四桶 + 「无命中」可选 |
| **7 天窗口内到期件数** | `expire_date` 在 7 天窗口内的案件数（含已过期若与 P0 一致） |
| **今日待跟进件数** | 满足今日跟进条件的案件数 |
| **补件相关件数** | 满足补件桶条件的案件数 |
| **未指定负责人件数** | `assigned_to IS NULL`（或空串，按 schema 固定） |

**不在 P1-S4 KPI 冻結内**：财务金额汇总、材料 checklist 完成率（待 P1-S1/S2）。

## 7. 性能与数据边界（冻結）

| 项 | 要求 |
|----|------|
| **分页** | 列表 API 必须分页；默认 page size 上限 **100**（可在 DTO 中定义为 50～100）。 |
| **索引** | 依赖现有 `visa_cases` 上 `customer_id`、`expire_date`、`case_status`、`assigned_to`、`deleted_at` 等索引；新增筛选若导致全表扫，须补充迁移与说明。 |
| **N+1** | 列表带客户展示字段时，**批量预取**客户主档，禁止逐行查询。 |
| **派生风险** | 客户列表批量计算时，优先 **单次 SQL**（子查询/窗口函数）或有限次查询；禁止每客户单独扫描全表。 |
| **统计 API** | 可缓存短 TTL（可选），非必须；不得返回无上限数组。 |

## 9. S4b 实现契约：`GET /visa-cases`（跨客户分页列表）

> 后端已实现；前端全局案件页（S4e）应与本节参数名与语义对齐。权限：**`visaCase:list`**。

### 9.1 分页

| 参数 | 说明 |
|------|------|
| `page` | 页码，默认 `1` |
| `pageSize` | 每页条数，默认 `20`，**上限 100** |

继承通用 `PaginationDto` 的 `keyword`：**案件**维度模糊匹配，对 `case_type`、`memo` 做 ILIKE（**不是**客户关键字；客户关键字见下）。

### 9.2 筛选参数（与 §3 维度对应）

| 查询参数 | 类型 | 说明 |
|----------|------|------|
| `customerId` | UUID | 服务上下文客户精确筛选 |
| `customerKeyword` | string | 客户 `customer_name` / `customer_code` ILIKE |
| `caseStatuses` | 重复 key 或逗号分隔 | `VisaCaseStatus` 多选 |
| `assignedToIds` | 重复 key 或逗号分隔 | 负责人 UUID 多选 |
| `unassignedOnly` | `true`/`false` | 仅 `assigned_to IS NULL`；**若与 `assignedToIds` 同时传，以本项优先** |
| `materialStatuses` | 重复 key 或逗号分隔 | `MaterialStatus` 多选 |
| `feeStatuses` | 重复 key 或逗号分隔 | `VisaCaseFeeStatus` 多选 |
| `expireDateFrom` / `expireDateTo` | `YYYY-MM-DD` | 到期日闭区间 |
| `nextFollowUpAtFrom` / `nextFollowUpAtTo` | ISO 日期时间 | **仅** `visa_cases.next_follow_up_at`；**不含**「最新案件日志上的下次跟进」。与 `/visa-reminders` 的「今日待跟进」若存在边界差异，在 **S4h** 中说明。 |
| `isFamilyCase` | boolean | 是否家族签 |
| `familyLinkMode` | `INTERNAL` / `EXTERNAL` | 家族签模式 |
| `supplementRelated` | `true` | `case_status = SUPPLEMENT` **或** 最新日志命中补件规则（与提醒补件桶一致） |
| `reminderBucket` | `VisaReminderType` | 按 **去重后的主桶** 筛选；自动排除 `COMPLETED`、`CANCELLED`（与提醒候选集一致） |

### 9.3 默认排序（与 §3 建议一致）

1. 派生提醒桶优先级：补件 > 今日待跟进 > 7 天内到期（含已过期）> 2 个月内到期 > 其他  
2. `expire_date` ASC，NULLS LAST  
3. `updated_at` DESC  

列表项在 join `customers` 后附带只读 **`customerName`、`customerCode`**，避免前端再 N+1 拉客户主档。

### 9.4 索引与性能（补充 §7）

迁移 **`1776100000000-AddVisaCaseListFilterIndexes`**：在 `visa_cases` 上对 `case_status`、`fee_status`、`material_status` 增加 **未软删行** 部分索引，支撑多选状态类筛选。

## 12. P1-S4h 验收场景与对账说明（S4h）

> **定位**：P1-S4（S4b–S4g）交付后的 **验收清单** 与 **实现口径对账**，与 `docs/21` 职责边界、权限矩阵一致；具体 Query 名以 `QueryGlobalVisaCaseListDto`、`QueryCustomerDto`、`QueryVisaCaseStatsDto` 为准。

### 12.0 子任务与交付物对照

| 子任务 | 验收对象 | 通过标准（摘要） |
|--------|----------|------------------|
| **S4b** | `GET /visa-cases` | 分页、§9.2 筛选、§9.3 排序、附带 `customerName`/`customerCode`、无客户维度 N+1；需 `visaCase:list` |
| **S4c** | `GET /visa-cases/stats` | 输出与 §5 / §12.3 一致；支持 `assignedTo` 收窄；需 `visaCase:list` |
| **S4d** | 客户列表扩展 | `visaReminderBucket` EXISTS 筛选；`visaDerivedRisk` 单标签；不改 `customers.status` |
| **S4e** | 前端全局案件页 | 路由 `/visa-cases`；筛选与 §9.2 对齐；跳转详情权限符合矩阵 |
| **S4f** | 前端统计区块 | 对接 S4c；加载/空态；负责人收窄与 S4c 一致（若提供） |
| **S4g** | 客户列表 UI | 派生风险列 + 桶筛选；与提醒页标签一致 |

### 12.1 权限与入口

| # | 场景 | 期望 |
|---|------|------|
| P1 | 用户仅有 `customer:list`，**无** `visaCase:list` | 客户列表可用；**后端仍会** 计算并返回 `visaDerivedRisk`，且 `visaReminderBucket` 筛选在 `GET /customers` 上生效（当前实现不额外要求 `visaCase:list`）；全局菜单/路由 **`/visa-cases`** 不可访问或 403 |
| P2 | 用户有 `visaCase:list` | 可访问 `GET /visa-cases`、`GET /visa-cases/stats` 与前端 `/visa-cases`；统计与表格加载成功 |
| P3 | 用户有 `visaCase:list` 但无 `visaCase:edit` | 全局案件页只读；编辑动作 403 或前端隐藏 |
| P4 | 财务人员（种子：只读签证） | 与 `docs/21` §4.1 一致：可看列表与统计，验收不依赖写权限 |

**说明**：若产品要求「无 `visaCase:list` 则不得看见客户列表上的签证派生信息」，属权限模型变更，须先改 `CustomerController`/DTO 再更新本节。

### 12.2 全局案件列表 `GET /visa-cases`

| # | 场景 | 期望 |
|---|------|------|
| G1 | 无筛选 + 默认分页 | 返回分页结构；单条含 `customerName` / `customerCode`（或等价字段），**无**对客户主档的 N+1 |
| G2 | `customerId` 精确筛选 | 仅该服务上下文客户名下案件 |
| G3 | `customerKeyword` | 客户姓名或 `customer_code` ILIKE 命中 |
| G4 | `caseStatuses` 多选 | `IN` 语义，与状态枚举一致 |
| G5 | `assignedToIds` 多选 | 负责人 OR；`unassignedOnly=true` 时 **优先** 仅 `assigned_to IS NULL`（与 DTO 注释一致） |
| G6 | `materialStatuses` / `feeStatuses` | 多选 `IN` |
| G7 | `expireDateFrom` / `expireDateTo` | 闭区间过滤 `expire_date` |
| G8 | `nextFollowUpAtFrom` / `nextFollowUpAtTo` | **仅**过滤 `visa_cases.next_follow_up_at`，不含日志表字段 |
| G9 | `isFamilyCase` / `familyLinkMode` | 与冻結语义一致 |
| G10 | `supplementRelated=true` | `case_status = SUPPLEMENT` **或** 最新案件日志命中补件规则（与 `findSupplementLogCaseIds` 一致） |
| G11 | `reminderBucket` | 按 **去重后的主桶** 筛选；**排除** `COMPLETED` / `CANCELLED` 与提醒候选集一致 |
| G12 | `pageSize` 上限 | 请求超过 **100** 时校验拒绝或钳制为上限（与 DTO 一致） |
| G13 | 排序 | 与 §9.3 一致：桶优先级 → `expire_date` ASC NULLS LAST → `updated_at` DESC |
| G14 | `customerKeyword` 与继承分页 `keyword` | `customerKeyword` 仅匹配客户主档；`keyword`（`PaginationDto`）按 §9.1 对案件 `case_type`/`memo` 模糊；**互不替代** |
| G15 | 多条件组合 | 各筛选条件为 **AND** 关系（在 SQL 中同时满足） |

### 12.3 只读统计 `GET /visa-cases/stats`

| # | 场景 | 期望 |
|---|------|------|
| S1 | 默认（无 `assignedTo`） | 返回 `caseStatusCounts`（**含**已完成/取消等全量状态分组）、`reminderBuckets`（四桶 + `noBucket`）、`expiringWithin7DaysWindow`、`todayFollowUpCount`、`supplementRelatedCount`、`unassignedCount` |
| S2 | `assignedTo=<用户 UUID>` | 开放案件子集与按状态计数均 **仅** 该负责人；`unassignedCount` **恒为 0** |
| S3 | 与提醒页对账 | 在同一数据集、同一负责人条件下，`reminderBuckets` 四分项与 `GET /visa-reminders` 返回的 `summary` **一致**（单测 `visa-case.service.spec.stats` 已固定此契约） |
| S4 | `caseStatusCounts` 与开放桶 | `caseStatusCounts` 统计 **全部** 非软删案件；`reminderBuckets` / `noBucket` 仅在 **未完结且未取消** 子集上计算，二者数值 **不应** 强行相加对平 |

### 12.4 客户列表扩展（派生风险 + 筛选）

| # | 场景 | 期望 |
|---|------|------|
| C1 | 不传 `visaReminderBucket` | 列表行为与 P0 一致，仅多 **只读列** `visaDerivedRisk`（可能为 `null`） |
| C2 | 客户名下 **多案件** | `visaDerivedRisk` 取 `docs/21` §9 优先级 **最高** 的一档（与 `buildOpenCasePrimaryBucketRankCaseSql` / `mapMinRankToVisaReminderType` 一致） |
| C3 | `visaReminderBucket=SUPPLEMENT` 等 | EXISTS 语义：至少一案落入该桶（与全局列表 `reminderBucket` 规则一致，含补件日志集） |
| C4 | 与 `keyword` / `customerType` 等旧筛选项组合 | **AND** 关系；不破坏原有筛选 |
| C5 | `customers.status` | 仍为 `ACTIVE/INACTIVE` 主档语义；派生风险 **不写库** |
| C6 | 导出/打印（若有） | `visaDerivedRisk` 等派生字段仅展示，**不**回写客户主档 |

### 12.5 与 `/visa-reminders`、文档 §9 的边界对账（重要）

| 项 | 实现口径（当前） |
|----|------------------|
| **今日待跟进** | 仅当 **`visa_cases.next_follow_up_at`** 的**日历日**等于当日；**不**读取「最新案件日志」上的 `next_follow_up_at`。全局列表的 `nextFollowUpAtFrom/To`、统计 `todayFollowUpCount`、客户 EXISTS 筛选与此一致。 |
| **补件** | `case_status = SUPPLEMENT` **或** 最新一条非软删案件日志：`log_type = SUPPLEMENT` **或** `missing_items` 非空。 |
| **7 天内到期 / 已过期** | `expire_date` 相对基准日的日历天数差 **≤ 7**（含已过期）；与 `resolveReminderBucket`、派生 SQL 中日期间隔一致。 |
| **2 个月内到期** | 天数差 **∈ (7, 60]**（与 P0 两个月窗口一致）。 |
| **`external_primary_expire_date`** | **不参与** 任一桶、派生风险与统计。 |

若产品文档（如 `docs/21` §9）表述为「今日待跟进来自案件字段 **或** 最新日志」，则以 **本节实现口径** 为验收依据；若要统一为「含最新日志」，须单独立项改 `VisaCaseReminderService.resolveReminderBucket` 与客户派生 SQL 后再修订本文与 `docs/21`。

### 12.9 Phase C（C4）提醒桶横向对账索引

> **用途**：将「签证提醒列表 `/visa-reminders`」「域统计 `GET /visa-cases/stats`」「全局列表 `reminderBucket`」「客户列表 `visaDerivedRisk` / `visaReminderBucket`」「工作台四分桶」放在同一矩阵下对照，避免各面各自解读优先级或候选集。  
> **结论（2026-04 对账）**：当前代码路径下 **四分桶 + `noBucket` 与单案去重规则一致**，**未发现需单独开 PR 的语义缺口**；与 `docs/21` §9 若存在「今日跟进是否含最新日志」表述差异，以 **§12.5 本节实现口径** 为验收依据（属已知边界而非遗漏实现）。

| 表面 / API | 单案主桶规则 | 主要实现位置 | 自动化锚点（示例） |
|------------|--------------|--------------|-------------------|
| `/visa-reminders` 列表与 `summary` | `resolveReminderBucket` | `VisaCaseReminderService` | `visa-case.service.spec.stats`（stats 与 summary 逐项相等） |
| `GET /visa-cases/stats` 的 `reminderBuckets` | 同上，对开放案件集 `getMany` 后内存累计 | `getVisaDomainStats` → `aggregateOpenCaseSegmentStats` | 同上；`visa-case.service.spec.stats` |
| `GET /visa-cases` 的 `reminderBucket` 筛选 | SQL 与主桶优先级一致（补件 / 今日 / 7 日含过期 / 2 月窗） | `applyGlobalReminderBucketFilter` | `visa-case-global-list-stats.parity.spec.ts` |
| 客户 `visaDerivedRisk` 聚合与 `visaReminderBucket` EXISTS | SQL `MIN(CASE…)` 与 `resolveReminderBucket` 同级 | `customer-visa-derived-risk.query.ts` | `customer-visa-derived-risk.apply-exists.spec.ts`；`customer-visa-derived-risk.query.spec.ts` |
