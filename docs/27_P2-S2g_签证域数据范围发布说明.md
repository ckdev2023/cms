# P2-S2g：签证域数据范围（dataScope）发布说明

> **文档定位**：配合 `docs/21_签证客户中心P0验收与Rollout说明.md` **§18**（P2-S2a 口径）与 **§18.9**（P2-S2g 内嵌收口）。本文 **复述 §18.9 的发布要点** 并补充 **单文件验收勾选项**、**实现路径索引**，便于运维分发。  
> **冲突处理**：若与 `docs/21` §18.9 表述不一致，**以 `docs/21` §18.9 为准**。  
> **不替代**：全局 RBAC 设计见 `docs/07_权限矩阵与角色设计.md`；本节仅覆盖签证域 **行级数据范围** 与 Query 参数 `dataScope`。

---

## 1. 产品默认行为（与老用户影响）

### 1.1 API 缺省

- **Query 未传 `dataScope`**（或传空）：服务端按 **`all`（全部）** 解析，**不按负责人收窄**。
- 与 P0/P1 已上线的「宽口径列表 / 提醒 / 统计 / 工作台」默认语义一致，**不因 P2-S2 上线而静默变窄**。

### 1.2 前端 URL 与控件

- 路由未带 `?dataScope=` 时，前端在请求前将缺省理解为 **`all`**，再与用户 **授权上限** 取交集（`clamp`）。
- 若用户 **没有任何** `visaCase:dataScopeMine` / `visaCase:dataScopeTeam` / `visaCase:dataScopeAll` 三类权限，则 **授权上限视为 `all`**（与后端 `VisaCaseDataScopePermissionService.getMaxAllowedVisaDataScope` 一致），行为与 **未引入 dataScope 权限前** 相同。

### 1.3 给老用户的一句话

> **未改角色权限时**：签证案件列表、提醒、统计、工作台、客户列表派生风险等与 **`dataScope` 引入前** 一样，默认仍是 **全件可见**（在已具备 `visaCase:list` / `visaReminder:list` 等 **能力** 的前提下）。

---

## 2. 管理者与「豁免」的真实含义

### 2.1 何谓「豁免」

- **不是**「管理员自动拥有所有写接口」。
- **是**：在 **已具备对应能力（Capability）** 的前提下，**数据范围上限** 按权限码计算为 **`all`**，从而允许 Query 使用 `dataScope=all` 且行级校验允许访问全部案件行。

### 2.2 触发「上限为 all」的条件（实现口径）

满足 **任一** 即视为用户在签证域 **最宽数据范围为 `all`**：

| 条件 | 说明 |
|------|------|
| 权限集合含 `*` | 超级管理员常用 |
| 权限集合含 `visaCase:*` | 模块通配，等同持有该模块下全部能力 + 范围上限 all |
| 显式持有 `visaCase:dataScopeAll` | 仅收窄范围权限时的「全件范围」授权 |

**未** 持有上述任一，但 **也未** 持有任一 `dataScopeMine` / `dataScopeTeam` / `dataScopeAll` 时：仍按 **§1.1** 视为上限 **`all`**（向后兼容）。

### 2.3 明确不豁免的内容（硬规则）

以下 **绝不** 因管理者或 `dataScope=all` 而绕过（与 `docs/21` §18.1、§18.6 一致）：

- 缺少 `visaCase:edit` 却修改案件；
- 缺少 `visaCaseLog:create` 却写案件日志；
- 缺少 `customerFilePath:*` 却改路径台账；
- 无 `visaCase:list` / 各接口声明的读门槛却访问列表或详情。

**结论**：**管理者 = RBAC 上通常持有 `*` 或完整签证权限**；实现上 **没有** 单独的 `isAdmin` 标志绕过业务权限码。

## 3. 收窄范围时的角色配置建议

当需要 **限制** 某角色只能看本人或团队案件时：

1. **移除** 该角色上的 `visaCase:dataScopeAll`（若曾显式授予）。
2. **按需授予** `visaCase:dataScopeTeam` 或 **`visaCase:dataScopeMine`**（二者取该角色应达到的最宽档；具体由权限集合计算最大值，见实现）。
3. 确认该角色仍具备业务所需的 `visaCase:list`、`visaCase:detail` 等 **能力**。

**注意**：种子数据中 **业务员工 / 财务** 等角色若已包含 `visaCase:dataScopeAll`，则其 **上限仍为全件**；仅当从角色中 **删除** 全件范围权限并改配 `Mine`/`Team` 后，前端分段控件与 API 才会限制在窄范围。

---

## 4. `team` 档位与团队表（运维提示）

- **`team`** 依赖 `team_users` 等多对多数据；若用户 **尚无任何团队归属**，当前实现按 `docs/21` §18.4 **过渡策略**：解析结果与 **`all` 等价**（避免误报空库）。
- 配置团队与成员后，`team` 将收窄为 **团队成员 `assigned_to` 并集**（且始终包含当前用户本人），见 `VisaCaseDataScopeService.resolve`。

## 5. 发布沟通与验收勾选项

| # | 建议动作 |
|---|----------|
| R1 | 对内说明：**默认未传 `dataScope` = 全件**，与旧版一致 |
| R2 | 说明：**`*` / `visaCase:*` / `visaCase:dataScopeAll`** 与 **上限 all** 的关系；**不**替代写权限 |
| R3 | 计划收窄权限前，列出受影响角色与测试账号，在预发用 `mine`/`team` 各验一条列表、详情、写操作 |
| R4 | 验证 **403**：故意请求 `dataScope=all` 但角色仅有 `dataScopeMine` 时应拒绝 |
| R5 | 验证 **行级**：详情/改案在 scope 外时 **读 404 / 写 403**（与当前 P2-S2d 策略一致，避免泄漏存在性） |
| F1a | **登记册**：同一账号在 `mine` / `team` / `all`（及管理者宽权限下的 `all`）下，`GET /visa-cases` 的 `total` 与 `GET /visa-cases/stats` 各 `caseStatus` 计数之和在**相同 Query 筛选**下一致；自动化见 `visa-case-f1-data-scope-list-stats.parity.spec.ts`（另含开放集与 `GROUP BY` 双链上 scope 注入断言） |
| F1b | **提醒与客户列表**：`GET /visa-reminders` 与 `stats` 的 `dataScope` 解析一致（`visa-case-f1-reminder-stats-data-scope.spec.ts`）；客户列表 EXISTS 与 QB 共用 `buildVisaCaseDataScopeExistsFragment`（`visa-case-scope-qb-exists.parity.spec.ts`、`customer-visa-derived-risk.apply-exists.spec.ts`）；手测时用同一 scope 切换 URL 后刷新提醒与客户派生列 |

## 7. 实现与本文不一致时的文档—代码绑定（Phase F）

当代码行为与 **本文** 或 **`docs/21` §18.9** 冲突时，按下列方式绑定交付，避免「代码已改、对外说明仍旧」：

1. **同一 PR**：优先在修改查询/权限/默认 `dataScope` 语义的 PR 内，同步修订本文与（若涉及总表）`docs/21` §18 相关小节，并在 PR 描述中写明「对账文档：`docs/27` / `docs/21` §x」。
2. **拆分 PR**：若必须先合代码、后补文档，须 **成对开 PR**：代码 PR 描述中注明 `Docs-follow-up: #<issue 或 PR 号>`；文档 PR 标题或描述中 **回链** 代码 PR，并在合并顺序上保证文档不长期落后于生产行为。
3. **冲突裁决**：正文 **§首段** 已声明与 `docs/21` §18.9 冲突时以 §18.9 为准；修订 §18.9 时须同步更新本文重复表述的段落。
4. **测例索引**：改动 `visa-case-data-scope.query.ts`、`VisaCaseDataScopeService.resolve` 过渡策略或 Guard 口径时，须同步更新 §6 所列 Jest 文件并通过 `npm run test --prefix backend -- <spec 路径>` 或全量 `npm run verify`。

## 8. 数据范围查询性能与索引回归（Phase F）

迁移 **`1776300000000-AddVisaDataScopePerfIndexes`** 为 `mine` / `team` 下案件列表、客户 EXISTS、补件相关子查询提供部分索引，名称如下（`down` 时按相反顺序删除）：

- `IDX_visa_cases_customer_assigned_open`：`visa_cases (customer_id, assigned_to)`，开放案件。
- `IDX_visa_cases_assigned_to_case_status_not_deleted`：`assigned_to` + `case_status`。
- `IDX_notes_visa_case_created_desc_active`：`notes (visa_case_id, created_at DESC)`，活跃补件日志路径。

**回归说明（发版前抽样）**

1. 在 **接近生产的脱敏库** 上确认迁移已执行：`SELECT indexname FROM pg_indexes WHERE indexname LIKE 'IDX_visa_cases_%' OR indexname LIKE 'IDX_notes_visa%';`
2. 对典型请求在预发打开 **SQL 日志**（TypeORM `logging: true` 或 Pg 慢查询），对下面两类语句各抽 1～2 条执行 `EXPLAIN (ANALYZE, BUFFERS)`（仅只读评估）：
   - 带 `dataScope=mine` 的 `GET /visa-cases` 列表主查询；
   - 客户列表带 `visaReminderBucket` 且 `dataScope=team` 时的主查询（含 EXISTS）。
3. **期望倾向**（非硬编码计划）：开放案件与客户 EXISTS 路径上，能观察到对上述索引的 **Index Scan / Index Only Scan / Bitmap Index Scan**，而非对大表的纯 `Seq Scan`；若计划退化，先核对数据量、统计信息与 `WHERE` 是否与索引谓词一致，再考虑新迁移或查询调整。
4. 修改 `visa-case-data-scope.query.ts` 中 **范围谓词** 时，须对照本节与迁移内注释复核索引 `WHERE` 子句是否仍匹配。
