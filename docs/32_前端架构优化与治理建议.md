# 前端架构优化与治理建议（Vue 3 + TS + Element Plus + Pinia）

本文基于当前仓库 `frontend/src` 的实现现状，给出一份可落地的前端架构优化与治理建议，目标是降低长期维护成本、提升一致性与安全性，并为后续功能增长预留清晰的演进路径。

## 1. 背景与目标

### 1.1 当前技术栈

- 框架：Vue 3 + TypeScript
- UI：Element Plus
- 状态：Pinia
- 路由：Vue Router 4
- 请求：Axios（统一封装在 `src/utils/request.ts`）
- 工程质量：ESLint + JSDoc 门禁 + Vitest

### 1.2 本文目标

- 让“状态、路由、请求、权限”形成稳定的单一事实来源（Single Source of Truth）
- 降低跨模块耦合（尤其是 request 层对 UI/路由的耦合）
- 让业务复杂度增长时依然能保持清晰的模块边界与依赖方向
- 兼顾当前交付节奏：以渐进式改造为主，避免推倒重来

## 2. 现状结构概览（目录职责）

`frontend/src` 当前主要结构与职责如下：

- `api/`：按业务域划分的 REST 调用函数（直接依赖 `utils/request`）
- `views/`：页面容器（多为“组合式 + 轻 Store”）
- `components/`：通用 UI 组件（如 `ProTable`、`PageList` 等）
- `composables/`：组合式逻辑（部分页面复杂逻辑拆分质量较高，如签证工作台）
- `stores/`：Pinia 全局状态（当前数量少，比较克制）
- `router/`：路由表、守卫、权限工具
- `constants/`：权限码、枚举、标签映射、feature flags 等
- `types/`：按域拆分的前端共享类型
- `utils/`：请求封装、通用工具、以及少量“强业务工具”

整体上属于企业后台常见的合理结构，具备良好的可维护基础。

## 3. 关键结论：主要风险点

### 3.1 鉴权与 token 处理存在“多点散落”

当前 `access_token` 的读取、清理、401 跳转等逻辑分布在多个位置：

- `src/stores/user.ts`
- `src/utils/request.ts`
- `src/router/guards.ts`
- `src/api/file.ts`（预览/下载 URL 或 header 拼接）

风险：

- 未来引入 refresh token、多端登录、跨 Tab 同步时容易出现“局部修复导致行为不一致”
- 401 触发时可能产生重复跳转/重复清理，甚至发生互相覆盖

建议：统一到“认证域单一入口”，把 token 与 session 行为收敛成一个模块（见 §5.1）。

### 3.2 request 层强耦合 UI 与 Router，限制扩展能力

`src/utils/request.ts` 在响应拦截器中直接做：

- `ElMessage.error(...)`
- `router.push('/login' | '/403')`

风险：

- 无法优雅支持“静默请求 / 表单就地提示 / 批量任务 / 可重试策略 / 不同页面不同提示策略”
- request 层变成“业务中枢”，会不断吸纳更复杂的分支

建议：将“错误展示/跳转策略”变成可配置的策略（见 §5.2）。

### 3.3 `utils/` 正在承载强业务域逻辑，长期会引发边界混乱

例如签证导入 CSV 解析、口径对齐逻辑等放在 `utils/` 下是可运行的，但从架构语义上更像 `features/visa/import` 的领域模块。

风险：

- `utils/` 被当作“啥都能放”，逐渐失去“通用、可复用、无副作用”的约束
- 业务逻辑被隐藏在“工具层”里，新同学难以定位

建议：渐进式把强业务工具迁移到 feature/domain 层（见 §6）。

### 3.4 菜单与路由存在“重复源”，可能出现漂移

当前路由表在 `router/routes.ts`，菜单在 `layouts/main-layout-menu.config.ts` 单独维护（含权限、文案 key、path）。现在规模可控，但后续页面增多会出现“改了路由忘了改菜单”。

建议：不一定强制自动生成菜单，但应建立一致性约束或校验（见 §6.3）。

### 3.5 列表页 server-state 模式不完全统一

你已经有 `useProTable`（数据加载与分页状态）以及 `ProTable`（表格 UI），但部分页面仍手写 loading/pagination/query，导致模式不统一，难以统一优化。

建议：强化“列表页标准范式”，并给出可复用的错误/加载态表达（见 §6.4）。

## 4. 目标架构原则（推荐的依赖方向）

### 4.1 分层原则（推荐）

- `views/`：页面容器，只做页面编排、路由交互、组合式调用与轻量 UI 状态
- `features/<domain>/`：业务域模块（页面相关组件、组合式、领域逻辑、adapter）
- `api/`：纯 API 函数（只关心请求入参/响应类型，不关心 UI 与路由）
- `stores/`：全局共享状态（认证、布局、跨页共享），避免把所有 server-state 都塞进 store
- `utils/`：纯工具/基础设施（尽量无 UI、无 router、副作用可控）

### 4.2 依赖方向（推荐）

- `views`/`features` 可以依赖 `api`、`stores`、`utils`、`constants`、`types`
- `api` 只依赖 `utils/request`、`types`
- `utils/request` 不直接依赖 `router`、不直接依赖 `element-plus`（通过策略/回调解耦）

## 5. 优先级最高的治理：认证与请求层收敛

### 5.1 建议建立“认证域单一入口”

目标：全项目只通过一个模块读写 token，并统一处理退出/失效/跨 Tab 同步。

建议落地方式（不引入新依赖的前提下）：

- 在 `stores/user.ts` 或新增 `utils/auth-session.ts` 中封装：
  - `getAccessToken()` / `setAccessToken()` / `clearAccessToken()`
  - `onAuthInvalidated(reason)`：统一处理失效（清理状态、跳转、提示）
- 路由守卫只做“是否有 token”与“是否已加载 userInfo”的流程编排，不直接管理 token key
- request 层遇到 401 时只触发 `onAuthInvalidated('401')`，不自己做跳转与消息
- 增加 `window.addEventListener('storage', ...)`：当 token 被其他 Tab 清理时同步登出态

### 5.2 建议把 request 错误处理改为“策略可配置”

目标：允许调用方选择提示策略，并让 request 层保持可扩展与可测试。

建议落地方式（示例）：

- `request(config, options?)`
  - `options.toast?: boolean`（默认 true）
  - `options.redirectOnAuth?: boolean`（默认 true，由上层决定是否跳转）
  - `options.silent?: boolean`（等价于 toast=false + 不跳转）
- response 拦截器只做：
  - 标准响应解包（`code !== 0` 变成统一 Error）
  - 统一错误类型归一化（例如 `ApiError`，包含 `status/code/message`）
- 由页面/feature 层决定：
  - 弹什么消息
  - 是否跳转
  - 是否在表单字段旁就地展示

## 6. 渐进式模块化建议（不推倒重来）

### 6.1 引入 `features/`（推荐结构）

当某个域的页面与逻辑开始变复杂时，将其从“散落在 views/composables/utils/constants”逐步迁移到 feature 目录：

```
src/
  features/
    visa/
      workbench/
        useVisaWorkbench.ts
        derived.ts
        load.ts
        routing.ts
      import/
        csv/
          parse.ts
          validate.ts
          types.ts
        components/
          ...
      types.ts
      index.ts
```

迁移原则：

- 先迁“强业务逻辑、稳定的纯函数”（例如导入解析与校验）
- 再迁“页面特有组合式”（避免破坏公共 composables 的语义）
- `utils/` 保持“通用、无业务口径”的约束

### 6.2 将“口径冻结”落点与代码边界对齐

仓库已有大量冻结口径文档（如导入、材料 checklist 等）。建议：

- 文档口径对应的代码尽量集中在 `features/<domain>/...`，避免散落
- 在模块内通过 `types.ts` 或 `contract.ts` 统一导出“口径级常量/枚举/映射”

### 6.3 菜单与路由一致性治理

不强制自动生成菜单，但建议做到至少一种约束：

- 方案 A：菜单项不直接写 path 字符串，而引用路由 `name` 或集中常量（降低漂移）
- 方案 B：新增一个轻量单测/校验（Vitest）：
  - 校验菜单 path 必须存在于路由表
  - 校验菜单的 `titleKey` 在 i18n messages 中存在

### 6.4 列表页标准范式（UI + 数据装载）

建议确立统一范式：

- UI：统一用 `ProTable` + `PageList`
- 数据：统一用 `useProTable(fetchFn)` 管分页、loading、查询
- 错误：统一使用 `pickApiErrorMessage`（或未来的 `ApiError`）决定提示策略

收益：

- 列表页交互一致（分页、重置、loading）
- 日后要加“请求取消、缓存、并发控制、搜索条件持久化”只需改组合式

## 7. 安全与稳定性建议

### 7.1 避免 token 出现在 URL

`api/file.ts` 目前存在将 token 拼到 preview URL query 的实现方式。这类 URL 可能出现在日志、截图、分享、或 Referer 中，存在泄露风险。

更稳妥的方向：

- 后端支持带 `Authorization` 的预览（iframe/pdf 等策略需配合）
- 或使用短期签名 URL（后端签发一次性 token）

### 7.2 统一错误归一化，支持观测与回放

建议逐步把错误从“字符串 + toast”演进为：

- 结构化错误对象（包含 `status`、`code`、`requestId`、`message`）
- 页面决定如何展示
- 未来可接入监控/审计（与后端 requestId 对齐）

### 7.3 轻量红蓝对抗分析（前端视角）

本项目定位为内部管理后台，红蓝对抗不追求“重型攻防”，但仍建议以“红方场景 → 蓝方控制 → 可观测与止血”做一次轻量闭环。总体原则与 [docs/05_红蓝对抗与安全设计.md](./05_红蓝对抗与安全设计.md) 保持一致：重点防误操作、越权和数据丢失，并确保出问题能追溯与恢复。

#### 7.3.1 需要重点保护的资产（前端能直接影响的部分）

- 会话凭证：access token、未来可能的 refresh token / cookie 会话
- 业务敏感数据：客户资料、财务记录、文件元数据、操作日志详情等页面可见信息
- 关键操作能力：删除/作废/冲正、文件上传/删除、权限配置与账号管理
- 文件访问链路：预览/下载 URL、文件名、文件类型与可能的外链引用

#### 7.3.2 红方典型攻击/破坏路径与蓝方对策（面向前端）

- XSS 获取会话与越权操作
  - 路径：页面渲染未转义内容（`v-html`、富文本、服务端返回的 HTML 片段）、第三方组件漏洞、DOM 注入导致执行脚本
  - 蓝方：减少/审计 `v-html` 使用；富文本输出做白名单净化；敏感操作增加二次确认与后端权限校验；避免把 token 放 localStorage（长期）或降低 token 权限/有效期；补充 CSP（若部署环境可控）
  - 观测与止血：前端错误上报 + 后端审计日志联动；一旦怀疑 XSS，可快速使现有 token 失效并强制重新登录

- token 泄露导致会话劫持
  - 路径：token 出现在 URL（query、hash）、控制台日志/埋点、截图分享、Referer 泄露、浏览器扩展读取 localStorage
  - 蓝方：禁止 token 进入 URL（预览/下载走 Authorization 或短期签名）；严禁日志打印 token；中长期迁移 HttpOnly cookie；缩短 token TTL 并配合服务端撤销策略
  - 观测与止血：服务端对异常 IP/UA 的 token 使用做告警与封禁；提供一键登出/强制下线

- 前端“隐藏按钮/路由”被绕过导致越权
  - 路径：仅靠菜单隐藏或 `v-permission` 隐藏按钮（攻击者可手工调用接口或直接访问路由）
  - 蓝方：明确“前端权限仅用于体验，真正鉴权在后端”；路由守卫只做用户体验层拦截；所有写接口后端必须校验权限与对象归属；关键页面在加载详情时也要依赖后端返回（不要只靠前端判断）

- 打开重定向与钓鱼（登录回跳参数被滥用）
  - 路径：登录页 `redirect` 参数若不做限制，可能被构造成外链跳转
  - 蓝方：限制回跳为站内相对路径（以 `/` 开头且不含协议/域名），并对不合法值降级到首页

- 文件链路风险（上传/预览/下载）
  - 路径：上传可执行脚本/伪装类型；下载文件名注入；预览 iframe 引入不可信内容；预览 URL 泄露
  - 蓝方：前端仅做体验校验（大小/扩展名），后端做 MIME/白名单与存储隔离；下载文件名进行安全处理；预览走受控域名与正确的 `Content-Disposition`；避免 token query

- CSV/Excel 注入与“导入导出”链路二次伤害
  - 路径：导出 CSV 中以 `=`, `+`, `-`, `@` 开头的单元格在 Excel 中被当公式执行；导入 CSV 的字段被误当公式或含恶意 payload
  - 蓝方：导出时对可疑前缀做转义（如前置 `'`）；导入预览严格展示原始内容并提示风险；后端同样需要防护

- 供应链/依赖漏洞与配置泄露
  - 路径：依赖包漏洞、锁文件漂移；构建产物携带 sourcemap 暴露内部路径/接口；环境变量误暴露
  - 蓝方：依赖升级节奏与审计（最小化新增依赖）；生产环境按策略控制 sourcemap；避免把敏感信息写入 `VITE_` 环境变量

#### 7.3.3 蓝方最低落地清单（前端侧）

- 权限：前端只负责展示与引导，后端必须做最终权限校验；前端路由拦截与按钮隐藏必须与后端权限码保持一致
- 会话：token 与 401/登出行为收敛为单一入口；禁止 token 出现在 URL；跨 Tab 同步登出
- 输出：审计/减少 `v-html`；导出 CSV 做公式注入防护；任何用户可控内容不拼接为 HTML
- 关键操作：删除/作废/冲正/上传等必须二次确认 + 防重复提交 + 后端幂等/审计
- 观测：错误上报（前端）与审计日志（后端）对齐 requestId，便于回放与追责

## 8. 分阶段实施路线（推荐）

### P0（低风险、高收益，优先做）

- token key 与 session 行为收敛：统一读写、统一失效处理、跨 Tab 同步
- request 层解耦：从“拦截器里直接 toast + router.push”改为“错误归一化 + 上层策略”

### P1（提高可维护性）

- 引入 `features/visa`（从导入 CSV 与工作台开始）
- 列表页逐步改用 `useProTable`（按模块逐页迁移）
- 增加菜单与路由一致性校验（单测或脚本）

### P2（安全与长期治理，需要后端协同）

- token 从 localStorage 迁移到 HttpOnly Cookie（配合 CSRF 方案）
- 请求层增加可观测性字段（requestId、trace）

## 9. 不做清单（避免过度设计）

以下事项不建议在当前阶段一次性引入：

- 大规模引入新的状态/请求库（例如全量替换为 React Query/SWR 之类的体系）
- 一次性重命名或重排所有目录（会制造巨大 diff 与合并成本）
- 把所有 server-state 都塞进 Pinia（容易造成 store 膨胀与耦合升级）

## 10. 结语

当前架构基础良好，主要问题集中在“认证/请求层的单一事实来源”与“业务模块边界的长期治理”。按本文路线以渐进式推进，可以在不打断交付的前提下，明显提升一致性、安全性与可维护性。
