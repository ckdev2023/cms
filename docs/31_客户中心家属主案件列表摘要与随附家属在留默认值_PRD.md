# 客户中心：家属列表主案件摘要回退 + 随附家属在留默认值 — PRD

> 状态：待评审 / 待排期  
> 关联冻结口径：`docs/17_业务口径冻结确认表.md`（§1.11 主展示案件选取）、`docs/21_签证客户中心P0验收与Rollout说明.md`（签证域边界）、`docs/27_P2-S2g_签证域数据范围发布说明.md`（`dataScope`）  
> 背景：家属子客户 `person_info.primary_customer_id` 已正确关联主档，但列表上 `listPrimaryVisaCase` / 派生提醒桶依赖 `visa_cases.customer_id = 当前客户`，导致家属行「主案件*」全空，一线误判为「无案件」；随附家属创建未带在留字段，重复录入成本高。

---

## 1. 问题陈述

1. **列表可读性与跟案效率**  
   家族申请场景下，**活件通常挂在主申（内部主客户）对应的 `visa_cases` 行**；家属为独立 `customers` 记录，案件 `customer_id` 多为主申而非家属本人。当前列表「主案件类型 / 状态 / 到期 / 下次跟进 / 负责人」及「提醒桶（派生）」均按**本人客户 ID** 关联案件聚合，家属行长期为空，与事务所「扫列表知跟哪张案子」的工作习惯不一致，易漏跟或退回 Excel。

2. **主档在留录入成本**  
   随附家属批量建档仅写入姓名、关系、护照、电话及主档家族关联，**在留资格 / 在留期限**为空。实务上家属与主申在留**可能不同**，但亦存在「先填同一套作初值再改」的强烈需求；完全空白导致必填心智成本高。

---

## 2. 目标

1. 在**不混淆「案件申请人」与「主档家属」**的前提下，使客户列表对**符合条件的家属客户**能**只读展示**与其主客户一致的「主展示案件」摘要（与 `docs/17` §1.11 选取规则同源），并正确反映 **签证数据范围 `dataScope`**。  
2. 在**新建随附家属**（及可选：**编辑时补空**）场景，提供**可选**的「从主客户复制在留资格 + 在留期限」作为**初值**，保存前可改；**不**做「主客户变更自动同步全家」的隐式联动。

---

## 3. 非目标（本 PRD 不包含）

- 护照上传 OCR / MRZ 自动解析（可另立 PRD）。  
- 修改 `visa_cases` 与 `customers` 的核心关系模型（案件申请人仍以 `visa_cases.customer_id` 为准）。  
- 家属客户自动成为 `visa_case_family_members` 成员（仍走现有案件向导 / 详情维护流程）。  
- 列表筛选、排序、导出是否跟随「回退摘要」——**第一期默认不改变**现有筛选语义（见 §7），仅做**展示层**增强，除非评审明确放开。

---

## 4. 用户故事

1. 作为**前台受付担当**，我希望在客户列表中打开筛选后，**家属行也能看到主申那条主展示案件的关键信息**，以便我不用先猜「这人是不是挂在张先生案子里」。  
2. 作为**案件担当**，我希望家属行上的案件摘要与主申行**同源规则**（同一 `dataScope`、同一 §1.11 排序），避免我看见无权限或错误的案件。  
3. 作为**案件担当**，我希望一眼能区分「**本人名下的案件摘要**」与「**来自主客户的案件摘要（只读）**」」，避免误以为家属是本案 `customer_id` 申请人。  
4. 作为**受付担当**，我在主客户表单用随附家属保存张太太、张小孩时，可勾选**沿用主客户当前在留资格与在留期限**，减少重复录入，且仍可在各人档案中修改。  
5. 作为**管理者**，我希望任何「看见主客户案件摘要」的行为都遵守现有 **RBAC 与签证 `dataScope`**，不扩大可见范围。  
6. 作为**新人**，当家属行展示的是回退摘要时，界面有简短说明或标签，降低培训成本。

---

## 5. 功能需求

### 5.1 名词与数据来源

- **本人主展示案件**：对 `customer_id = 当前客户 ID` 的 `visa_cases`，在**当前用户 `dataScope` 可见集合**内，按 `docs/17` §1.11 规则选出的唯一摘要（与现 `listPrimaryVisaCase` 一致）。  
- **回退主展示案件**：当本人主展示案件为 `null` 时，若满足 §5.2 条件，则改为选取 **`person_info.primary_customer_id` 指向的主客户** 的本人主展示案件（同一 §1.11 + 同一 `dataScope`）。  
- **有效列表摘要**：`本人主展示案件 ?? 回退主展示案件`（仅展示层逻辑；须在响应中可区分来源，见 §5.4）。

### 5.2 回退启用条件（必须同时满足）

1. 当前客户为 **个人客户**（`customer_type = PERSONAL`）。  
2. `person_info.is_family_member = true` 且 `person_info.primary_customer_id` 非空。  
3. 主客户存在且未删除；且主客户 **不等于** 当前客户（防止环）。  
4. **回退目标案件**的主展示行上，`visa_cases.customer_id` **必须等于该主客户 ID**（即案件申请人为主客户本人）。若主展示案件实际挂在其他客户 ID 上，**不回退**（保持空或仅本人摘要，避免错误嫁接）。  
5. 当前用户对回退目标案件在 **`dataScope` 下可见**；不可见则**不回退**（视为 `null`，与「无权限」一致）。

### 5.3 提醒桶（派生）

- **第一期建议**：列表上的 **「提醒桶（派生）」仍以本人 `customer_id` 关联的开放案件计算**（与现 `visaDerivedRisk` 一致），**不因回退摘要而改写**。  
- **理由**：避免家属行与主申行在筛选「补件 / 7 日内到期」等条件时**重复命中**同一张活件；派生桶语义保持「本人名下待办」。  
- **文案**：若家属行存在回退摘要但派生桶为空，可通过列头说明或空态提示「提醒以本人名下案件为准；案件摘要来自主客户」——具体文案实现阶段定稿。

### 5.4 API / DTO 行为（逻辑契约）

在客户列表单项（及如需客户详情顶栏摘要时）增加**可区分来源**的元数据，例如（字段名实现阶段可调整，语义须保留）：

- `listPrimaryVisaCase`：仍为**案件摘要对象**（与现结构一致），内容为**有效列表摘要**。  
- `listPrimaryVisaCaseSource`: `'SELF' | 'PRIMARY_CUSTOMER_FALLBACK' | null`  
  - `SELF`：来自本人 `customer_id`。  
  - `PRIMARY_CUSTOMER_FALLBACK`：来自 §5.2 回退。  
  - `null`：无摘要。  
- 可选：`primaryCustomerIdForListFallback`: `uuid | null`（仅当 source 为回退时有值，便于前端展示「主客户：xxx」）。

**详情页**：若产品希望详情页「签证域入口」与列表一致，可复用同一服务；本 PRD **最低交付**为列表；详情为可选同期或二期。

### 5.5 前端展示

- 主案件各列展示 **有效列表摘要** 的字段（类型、状态、到期、跟进、负责人等），与现有一致。  
- 当 `listPrimaryVisaCaseSource === 'PRIMARY_CUSTOMER_FALLBACK'` 时：  
  - 在**主案件类型**或**首列有摘要的单元格**增加**次级标签**或 `el-tag`（如「主客户案件」/ 主客户简称），避免与本人案件混淆。  
  - Tooltip 或辅助说明：案件申请人为关联主客户，非当前客户本人。  
- 深链（跳转案件详情、材料、日志等）行为：**与现有一致**，使用摘要中的 `visaCaseId`；须校验用户仍具备目标案件读权限（现有守卫应已覆盖）。

### 5.6 随附家属：在留默认值

**触发场景**：`CustomerFormDialog` 中通过「随附家属」行 **新建** `POST /customers`（及可选：**首次编辑**且该行在留字段为空时的批量填充——二期或同期由评审决定）。

**交互**：

- 在主客户保存区域或随附家属卡片上增加**可选**控件：「新建家属时沿用主客户：在留资格、在留期限」（默认勾选或默认不勾选由评审选定，**建议默认勾选**以降低空档率）。  
- 若主客户当前无 `person_info.residence_status` 与 `residence_expire_date`（或均为空），控件禁用并提示先填主客户。  
- 写入规则：仅写入**各新建家属**的 `person_info` 对应字段；**不**写入 `nationality` 等未列明字段。  
- **不**建立任何「后续主客户变更自动同步家属」的监听；若需批量同步，须另 PRD + 显式操作。

---

## 6. 权限、数据范围与安全

- 回退摘要所选案件必须通过 **`visaCaseDataScope.resolve` 与列表同源** 的可见性判定；禁止因 `primary_customer_id` 关系绕过 `dataScope`。  
- 主客户对客户 A 可见，但案件对当前用户不可见时：A 的家属行**不得**展示该案摘要。  
- 审计：本 PRD **不强制**新增审计事件；若实现过程写入敏感可见性变更，按现有 `audit_logs` 策略评估。

---

## 7. 与列表筛选的关系（第一期锁定）

- **不改变**现有「主案件状态（摘要）」等筛选的 SQL 语义：筛选仍基于 **本人 `customer_id` 的主展示 EXISTS**（与 `applyCustomerListListPrimaryVisaCaseRowFilters` 一致）。  
- 家属客户不会因「仅存在回退摘要」而被筛入「有主案件状态 = X」**除非**本人名下确有案件。  
- 若未来需求「按主客户案件筛家属」，须单独立项并评估性能与语义。

---

## 8. 验收标准（抽样）

1. 主客户张先生存在可见范围内主展示案件；家属张小孩仅有 `primary_customer_id`、无本人 `visa_cases`：列表张小孩行 **展示与张先生一致**的案件摘要，且来源标记为 **主客户回退**；张先生行仍为 **本人**。  
2. 将当前用户对该案 `dataScope` 设为不可见：张小孩行摘要变为空（或与不回退一致），**不出现**越权案件。  
3. `primary_customer_id` 指向非法或已删主客户：不回退，无报错页，摘要为空。  
4. 随附家属保存时勾选沿用：新建家属的 `person_info` 在留两字段与保存瞬间主客户一致；保存后各自修改互不影响。  
5. `npm run verify`（或当期 CI 标准）通过；关键回退与 scope 组合有 **后端单元测试** 覆盖。
