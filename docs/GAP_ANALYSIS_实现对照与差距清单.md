# GAP_ANALYSIS 实现对照与差距清单

> **对照基线**：`docs/GAP_ANALYSIS.md`（客户中心业务定位与一期边界说明）  
> **对账代码快照**：仓库当前 `v2` 分支形态（含签证域 `visa_cases`、材料 checklist、签证工作台等）  
> **关联收口文档**：`docs/21_签证客户中心P0验收与Rollout说明.md`、`docs/22_材料チェックリスト口径冻結.md`

本文回答三个问题：`GAP_ANALYSIS` 描述的一期能力哪些已落地、哪些只做到一部分、哪些仍缺失；与官方 P0/P1 文档冲突处以 **21/22 号文档** 为准。

---

## 1. 总览结论

| 判断 | 说明 |
|------|------|
| **核心架构对齐** | 「客户主档 + 签证案件 + 案件级家属 + 案件日志 + 资料路径台账」与 GAP 第三～五章的结构描述 **一致**，且与 `docs/21` 职责划分一致。 |
| **一期「必须做」大部分已覆盖** | 主档、在留补充信息、案件基础、内外部主申家族签、案件侧结构化日志、签证域提醒与路径、材料 checklist（P1 能力已进入代码）均已可找到实现。 |
| **主要差距集中在「客户级体验」与「GAP 字面细节」** | 客户备注未升级为全结构化跟进日志；主档无微信/LINE 字段；客户列表未按 GAP 理想列展示案件明细；**基于 `person_info` 的「90 天内到期统一列表页」** 与旧在留提醒入口已弱化/移除，主路径改为 **案件级** 提醒（与 GAP 文末「升级到案件级提醒」方向一致，但与 §五.5 字面流程不完全相同）。 |

## 2. 按 GAP 第六章「一期必须做」逐项对照

### 2.1 客户主档（个人 / 法人 · 基本信息 · 联系方式 · 负责人）

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 个人/法人、编号、姓名、电话、邮箱、地址、服务线、负责人、状态 | **已满足** | `Customer` + `PersonInfo` / `CompanyInfo`；`CreateCustomerDto` / `customer-profile.service` |
| 微信 / LINE | **未实现** | 实体与 DTO 中无独立字段；GAP 第二章痛点虽提及，第六章「联系方式」在实现上仅 **电话/邮箱** |

### 2.2 个人签证补充信息

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 国籍、在留资格、到期日、家族关系、主客户关联 | **已满足** | `PersonInfo`：`nationality`、`residenceStatus`、`residenceExpireDate`、`isFamilyMember`、`familyRelation`、`primaryCustomerId` |

### 2.3 签证案件基础能力

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 业务类型、状态、到期、下次跟进、负责人 | **已满足** | `VisaCase`：`caseType`、`caseStatus`、`expireDate`、`nextFollowUpAt`、`assignedTo`；`visa-case` 模块 CRUD + 列表/统计 |

### 2.4 家属关系（内部/外部主申请人）

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 主申/配偶/子女等 + 内部主申 + 外部主申快照 | **已满足** | `FamilyLinkMode` INTERNAL/EXTERNAL；`internalPrimaryCustomerId` + `externalPrimaryName/CaseType/ExpireDate`；`visa_case_family_members` + 前端 Wizard/Dialog |

**细粒度差距**：GAP 场景三提到外部主申需记录「**与申请人关系**」。当前外部快照 **未单独建模「主申↔家属关系」字段**；家属与主申的关系仍主要通过 **客户主档** `person_info.familyRelation` + **案件成员** `VisaCaseMemberRole` 表达，若业务要求「外部主申行上显式关系码」，则属 **可增强项**。

### 2.5 跟进日志（时间、记录人、类型、内容、已提交/缺失/下一步/下次跟进）

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 案件级结构化日志 | **已满足** | `CreateVisaCaseLogDto` + `notes` 表扩展字段（`visa_case_id`、`log_type`、`submitted_items` 等） |
| 客户级备注同等结构化 | **部分缺失** | `CreateNoteDto` / `CustomerNotesTab` 仅 **内容 + noteType**；数据库 `Note` 虽可存扩展字段，但 **客户备注 API/UI 未暴露** 已提交/缺失/下一步/下次跟进 |

与 GAP「过程层」叙事相比：**高频结构化跟进**已落在 **案件日志**；若坚持「客户 Tab 一条备注就要带齐结构化字段」，则与当前产品拆分（`docs/21`：客户备注 vs 案件日志）不一致，需产品确认是否要做 **客户级结构化备注** 或统一引导写 **案件日志**。

### 2.6 提醒（到期 / 下次跟进 / 补件）

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 案件维度：补件、今日待跟进、7 日内到期、2 个月内到期 | **已满足** | `VisaReminderType`；`/visa-reminders`、`VisaWorkbenchView`、客户列表 `visaReminderBucket` + `visaDerivedRisk` |
| 个人在留：`person_info` 扫描、**90 天内统一列表** | **路径变更** | 详情页仍展示 `residenceExpireDate` 与 `alertLevel`（`customer-response.mapper` + `visa-alert.util`）；**独立的「在留提醒列表」前端页已移除**（`ResidenceReminderListView.vue` 删除），与 `docs/21`「不替代旧在留提醒页」的并列描述相比，实际 **主入口已统一到签证提醒/工作台** |

### 2.7 资料路径（客户/案件/复制）

| 要求 | 状态 | 实现要点 |
|------|------|----------|
| 客户档案路径、案件路径、复制路径 | **已满足** | `customer_file_paths`：`customerId` + 可选 `visaCaseId`；`FilePathType` 枚举；`CustomerFilePathsTab` |
| GAP 字面「主申请人路径 / 家属路径」独立类型 | **语义靠归类而非专用枚举** | 当前用 `CASE_DOCUMENT` / `PERSONAL_DOCUMENT` / `OTHER` 等 + `displayName`/`remark` 区分；**无名为 PRIMARY_SPOUSE_PATH 的硬编码类型** |
