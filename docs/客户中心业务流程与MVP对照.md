> **文档目的**：从「员工实际怎么用系统」角度描述当前仓库中的**客户中心**主路径与分支，并对照 `prd/01_第一阶段MVP_PRD_标准化办案底座.md` 中与客户中心相关的条款，给出满足度判断。

## 1. 系统边界与角色

| 角色 | 与「客户中心」的关系 |
|------|----------------------|
| 内部员工（行政/签证/税务等） | 通过后台菜单进入客户中心 Hub，维护客户主档、查看关联业务、在签证域内推进案件与材料。 |
| 客户本人 | **不在**当前客户中心范围内；MVP PRD 中的「客户门户 / 客户上传」在本系统中未作为客户中心的一部分实现。 |

结论：当前「客户中心」是**内部员工视角的客户主数据与业务聚合入口**，不是对客门户。

## 2. 信息架构：Hub 与详情两层

> 与 v2 流程图 [`客户中心业务流程_v2.0.drawio`](diagrams/客户中心业务流程_v2.0.drawio) 中「进门第一眼 → Hub → 详情摘要 → 域内子块」的层级一致；**入口、深链与备注/日志分工** 的冻结说明以 **`docs/21`** 为权威，本节仅映射到当前前端实现。

### 2.1 客户中心 Hub（`/customers` 子树）

- **布局**：`CustomerCenterLayout` 顶栏多 Tab，按权限显示不同子页（定义见 `frontend/src/layouts/customer-center-tabs.config.ts`）。
- **典型分组/Tab**（顺序以配置为准）：客户列表、签证工作台、签证提醒、全局案件登记册、历史导入、行政→签证补录、在留相关列表视图（与主档筛选联动）、行政案件列表等。
- **根路径行为**：当用户具备签证工作台 Tab 权限时，从侧栏进入 `/customers` 常会 **replace** 到工作台子路径（保留 query），避免误以为「客户列表」是唯一首页；从子路径切回「客户列表」Tab 时不会再次劫持。细则见 `frontend/src/utils/customer-center-root-redirect.ts` 与 `docs/21` §5.4 侧栏表述。

### 2.2 客户详情（`/customers/:id`）

- **独立路由**：详情不在 Hub 的 `keep-alive` 子树内，从列表、工作台、提醒、登记册等均可 `push` 进入；返回路径由 `ccFrom` / 历史 back / 列表根兜底（`CustomerDetailView.vue`、`@/utils/customer-detail-return-navigation`）。
- **主导航 + 次级一行（B3）**：顶栏为自定义两行 Tab——**第一行**为高频域：基本信息、备忘与跟进、**签证域**（多子块）、行政案件（均受对应 `show*` 权限裁剪）；**第二行「台账与工具」**收纳税务合同、财务、文件，与第一行并列展示、减轻首行拥挤（实现见 `CustomerDetailView.vue` + 隐藏 `el-tabs` 顶栏的 `customer-detail-tab-panels`）。路由 `?tab=` 仍使用 `tax` / `finance` / `files`，与 `VALID_DETAIL_TABS` 一致。
- **默认 Tab 策略**：无 `?tab=` 时，若存在进行中的主展示签证案件且功能开关满足，可默认落在签证域 Tab（`customerDetailPrefersVisaDomainTab`）。
- **详情内留痕提示（C1）**：卡片顶部 `CustomerDetailTraceabilityHint` 与各 Tab 内文案/链共同提示「客户备注 vs 案件日志」分工，**不改数据模型**（与 `docs/21` §1.4 一致）。

### 2.3 与 `docs/21` 对齐的 query 深链（详情页）

列表、工作台、摘要带等向详情投递的 query 由 **`docs/21`** 与各视图约定；常见键包括（消费后部分键由子组件从 URL 剥离）：

| Query 键 | 典型用途 |
|----------|----------|
| `tab` | 详情顶层 Tab，如 `visa-domain`、`notes`、`tax` 等 |
| `openVisaCaseId` | 进入签证域并聚焦指定案件（如打开编辑上下文） |
| `visaDomainBlock` | 直接展开签证域子块：`cases` / `family` / `paths` / `logs` / `materials` |
| `logVisaCaseId` | 案件日志子块默认选中案件 |
| `openVisaCaseLogForm` | 进入日志子块后自动打开新建表单 |
| `suggestedNextFollowUpAt` | 新建日志表单「下次跟进」建议值 |
| `materialsVisaCaseId` | 材料清单子块默认选中案件 |
| `openVisaCaseWizard` | 进入签证域并打开建案向导 |

深链拼装时应保留客户中心数据范围类 query（如 `dataScope`、`assignedTo`、`ccFrom` 等），见 `pickCustomerDetailDeepLinkPreserve` / `CustomerDetailContextStrip.vue`。

### 2.4 签证域在详情内的子块

签证域 Tab 内再分为：**案件、家属、资料路径、案件日志、材料清单** 等（`CustomerVisaDomainTab.vue`）。  
产品与数据分工以 **`docs/21`** 为准：客户备注为轻量备忘；**结构化跟进与交接以案件日志（`notes.visa_case_id`）为权威载体**。

## 3. 主业务流程（叙事顺序）

### 3.1 客户主数据生命周期

1. **发现/定位**：在客户列表关键字搜索、类型/服务线/状态/负责人等筛选；或从签证工作台、签证提醒、案件登记册跳转至某客户详情。
2. **新建**：列表发起新建 → `POST /customers` → 成功后通常进入详情或留在列表（以当前前端引导为准）。
3. **维护**：详情「基本信息」或列表行编辑 → `PUT /customers/:id`；个人/法人扩展字段随 DTO 一并更新。
4. **停用与恢复**：逻辑删除与恢复（软删除），权限点 `customer:delete` 等控制。

### 3.2 签证协同路径（与主档并行）

1. **建案主路径（已冻结）**：**新建客户 → 客户详情 → 签证域 Tab 内建案**（`docs/21` §1.3）。不在客户中心内用「合并向导」默认替代该顺序，除非未来修订文档单独排期。
2. **案件运营**：在签证域内维护案件字段、家属、资料路径台账、材料清单状态、案件日志与下次跟进时间等；列表/工作台可通过 **query 深链**（如 `openVisaCaseId`、`logVisaCaseId`、`visaDomainBlock`）打开详情并定位子块，消费后从 URL 剥离。
3. **提醒与主档在留**：**案件维度**提醒主路径为签证工作台与 `/customers/visa-reminders`（见 `docs/21` §1.5）。**主档在留**仅在客户详情与个人客户列表派生展示与筛选；**不再**提供已移除的独立在留列表路由/API，书签与替代入口见 **`docs/21` §1.5**「旧书签说明」。

### 3.3 非签证业务在客户中心的挂载

- **行政案件**：详情第一行 Tab 或 Hub 内行政案件列表 → `admin_cases.customer_id`。
- **税务合同**：详情第二行「台账与工具」内税务子 Tab → `tax_contracts.customer_id`。
- **文件**：详情第二行文件子 Tab → `files` 与业务类型关联。
- **财务**：详情第二行财务子 Tab，能力随权限与实现迭代；完整明细更多在财务中心模块（见 `docs/18` §2.2）。

### 3.4 沟通与留痕

| 形态 | 落点 | 说明 |
|------|------|------|
| 客户级备忘 | 客户备注 Tab，`notes.visa_case_id IS NULL` | 跟进/备忘/通用等类型，轻量时间线。 |
| 案件级结构化沟通 | 签证域 → 案件日志 | 缺失项、已交项、下一步、下次跟进等（`docs/21` §1.4）。 |
| 审计 | 登录日志、操作审计、文件访问等 | 跨模块，不仅限于客户中心。 |

## 5. 对照 `prd/01_第一阶段MVP_PRD_标准化办案底座.md`

### 5.1 PRD §5.2「客户中心（后台）」逐条

| PRD 要求 | 当前实现结论 | 说明 |
|----------|--------------|------|
| 个人客户/法人客户建档 | **满足** | `customer_type` + `person_info` / `company_info`。 |
| 客户标签、来源、负责人、协同人 | **部分满足** | **负责人**有（`owner_user_id`）；**客户标签、来源**未见一等公民字段；**协同人**有 `customer_staff_relations` 数据与详情只读展示，**客户中心内无独立维护入口**（`docs/18` §2.2）。 |
| 客户全景页：案件、文件、任务、收费、沟通记录 | **部分满足** | **案件**：签证案件（签证域）+ 行政案件 Tab + 税务合同 Tab。**文件**：有。**任务**：MVP 语义下的「通用案件任务中心」不在客户详情单页一统；行政案件自有任务流，与 PRD「任务列表」级中枢不完全等同。**收费**：财务 Tab/模块有能力，与 PRD「收费状态页」的完整产品形态需单独对账。**沟通**：备注 + 签证案件日志，非 PRD设想的「单一沟通记录列表」统一模型。 |

### 5.2 与 PRD 其他条款的关联（客户中心视角）

| PRD 区块 | 与客户中心关系 | 结论（摘要） |
|----------|----------------|--------------|
| §5.1 SaaS 基础（租户、试用、套餐） | 客户数据无租户隔离字段 | **不满足 SaaS MVP**；与客户中心功能是否「好用」是两层问题。 |
| §5.3–5.4 统一案件主表 + 模板化阶段任务 | 当前为签证案件 / 行政案件等**并列域** | **不等同** PRD 的通用 `cases` 引擎；客户中心是聚合入口而非统一案件抽象。 |
| §5.5–5.7 资料项版本、今日待办看板等 | 材料清单、工作台 KPI 等**偏签证域实现** | **签证路径较强**；是否覆盖 PRD 所列全部业务包与看板项需按业务类型逐项验收。 |
| §5.8 收费状态 | 财务模块 + 详情 Tab | **部分满足** PRD「运营态收费跟踪」，非复杂会计核算。 |
| §5.9 审计与权限 | RBAC + 审计日志 | **基本满足** 内部后台诉求；缺租户级/客户门户级权限分层。 |

### 5.3 总判断（是否「满足」整份 MVP PRD）

- **若将 PRD 理解为「可对外售卖的 SaaS 第一阶段 MVP」**：与 `prd/04_当前系统对照MVP差距分析.md` 一致，整体为 **部分满足 / 未完全达标**，客户中心也不是对客门户。  
- **若将问题收窄为「内部事务所后台里，客户中心是否覆盖 PRD §5.2 描述的理想客户中枢」**：**部分满足**——建档与多业务挂载较强，**标签/来源/协同维护、统一任务与沟通模型、与通用案件引擎对齐**仍不足。
