## 1. 各模块状态枚举值定义

### 1.1 行政案件状态（AdminCaseStatus）

已实现于 `backend/src/common/constants/enums.ts`。

| 枚举值 | 中文 | 日文参考 | 说明 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿 | 下書き | 刚创建，信息未填写完整 |
| `ACCEPTED` | 受理中 | 受付中 | 已正式受理，开始处理 |
| `MATERIAL_PENDING` | 材料待补 | 資料待ち | 需要客户补充材料 |
| `SUBMITTED` | 已提交 | 提出済み | 已向入管等机关提交申请 |
| `APPROVED` | 已批准 | 許可済み | 机关审批通过 |
| `REJECTED` | 已驳回 | 不許可 | 机关审批不通过 |
| `COMPLETED` | 已完成 | 完了 | 案件全部处理完毕 |
| `CANCELLED` | 已取消 | 取消 | 客户取消或其他原因终止 |

**状态流转规则**：

```
DRAFT → ACCEPTED → MATERIAL_PENDING ⇄ ACCEPTED
                 → SUBMITTED → APPROVED → COMPLETED
                             → REJECTED → COMPLETED (归档)
任何非终态 → CANCELLED
```

- `MATERIAL_PENDING` 与 `ACCEPTED` 可来回切换（补材料后重新受理）
- `APPROVED` / `REJECTED` 后须进入 `COMPLETED` 归档
- `CANCELLED` 为终态，不可回退
- 终态：`COMPLETED`、`CANCELLED`

**结论**：✅ 冻结，与现有代码一致，不再变更。

### 1.4 月次资料状态（MaterialStatus）

### 1.5 请款状态（InvoiceStatus）

| 枚举值 | 中文 | 日文参考 | 说明 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿 | 下書き | 刚创建，可编辑 |
| `SENT` | 已发送 | 送付済み | 已发送给客户 |
| `PARTIAL` | 部分收款 | 一部入金 | 已收到部分款项 |
| `PAID` | 已收清 | 入金完了 | 全额收清 |
| `VOID` | 已作废 | 無効 | 作废不再生效 |

**状态流转规则**：

```
DRAFT → SENT → PARTIAL → PAID
             → PAID (一次性收清)
DRAFT → VOID
SENT  → VOID (需检查：已有收款则不可直接作废，须先冲正)
```

- `DRAFT` 阶段可自由编辑金额和明细
- `SENT` 后金额锁定，修改须作废并重开
- `PARTIAL` → `PAID` 由系统根据收款分配自动计算触发
- `VOID` 为终态；已有收款的请款单不可直接作废，须先冲正关联收款
- 不设 `待发送` 状态——`DRAFT` 即等同待发送，减少不必要状态

**结论**：✅ 冻结，与现有代码一致。

### 1.6 收款状态（PaymentStatus）

| 枚举值 | 中文 | 日文参考 | 说明 |
| --- | --- | --- | --- |
| `REGISTERED` | 已登记 | 登録済み | 收款已录入系统 |
| `VERIFIED` | 已核销 | 消込済み | 已与请款单核销完毕 |
| `REFUNDED` | 已退款 | 返金済み | 全额退还客户 |
| `REVERSED` | 已冲正 | 取消済み | 因错误而冲正（等同作废） |

**状态流转规则**：

```
REGISTERED → VERIFIED (分配到请款单完成核销)
REGISTERED → REVERSED (登记错误，冲正)
VERIFIED   → REVERSED (已核销后发现错误，冲正并回退请款状态)
REGISTERED → REFUNDED (未核销直接退款)
```

- `REFUNDED` 和 `REVERSED` 为终态
- 冲正操作必须记录原因，并自动回退关联请款单状态

**结论**：✅ 冻结。

### 1.7 预收款交易类型（DepositTransactionType）

预收款不设独立的「账户状态」枚举，通过 `deposit_accounts.balance` 余额 + `deposit_transactions` 流水记录来表示账户状态。

| 枚举值 | 中文 | 日文参考 | 说明 |
| --- | --- | --- | --- |
| `RECHARGE` | 充值 | チャージ | 客户预存入款 |
| `OFFSET` | 抵扣 | 充当 | 用预存款抵扣请款单 |
| `REFUND` | 退款 | 返金 | 将预存款退还客户 |
| `ADJUSTMENT` | 调整 | 調整 | 管理员手工调整余额（须备注原因） |

**决策**：不新增 `DepositAccountStatus` 枚举。账户状态逻辑如下：
- 余额 > 0 → 可用
- 余额 = 0 且有过交易 → 已结清
- 无交易记录 → 未开户（在 UI 上不显示）

**结论**：✅ 冻结。不新增预收款账户状态枚举。

### 1.11 客户列表主展示案件选取与多案件排序规则

> **效力**：落实 `docs/GAP_ANALYSIS_实现对照与差距清单.md` §5 第 4 条及 §3「页面组织」；实现客户列表「主展示案件」摘要列（list 子查询 / mapper）时 **须**遵守下列规则。

**适用范围**：同一客户下 **零条或多条** `visa_cases` 时，列表 **每客户最多一条**「主展示案件」摘要（类型、状态、到期、下次跟进、负责人等由列定义决定）。

**数据范围**：选取在 **该客户可见的签证案件集合** 内进行；客户是否出现在列表仍受 `VisaDataScope` 等既有规则约束。选取结果对 **同一列表结果集内的所有用户相同**（不按「是否负责人」分叉主展示行）。

**终态**：`VisaCaseStatus` 为 **`COMPLETED`** 或 **`CANCELLED`** 的视为已结案。

**候选集与排序**：

1. **候选集 A**：未结案（非 `COMPLETED` 且非 `CANCELLED`）的全部案件。
2. 若 **A 非空**：在 A 内排序，取第一条为「主展示案件」：
   - 第一键：`next_follow_up_at` **升序**，`NULL` 置后（**最先需要跟进**优先）；
   - 第二键：`expire_date` **升序**，`NULL` 置后（**最近到期**优先）；
   - 第三键：`updated_at` **降序**（最近业务更新优先）；
   - 第四键：`id` **降序**（稳定 tie-break）。
3. 若 **A 为空**：在 **全部** 案件中按 `updated_at` **降序**，再按 `id` **降序** 取一条作只读摘要；若无任何案件则该列 **空状态**。
4. **负责人是否为当前登录用户** **不参与** 上述选取键；若 UI 需高亮「我负责」，仅可为 **展示层** 样式，**不得**改变本条选取结果。

**结论**：✅ 冻结（2026-04-04 增补）。

### 1.12 护照号码（自然人主档存储与检索）

> **效力**：统一回答「护照号是否入库、落哪张表、是否唯一、隐私与能否搜」；与 `docs/客户需求.md` 中「护照号 / 护照信息」表述 **互引**。**当前仓库表结构尚未包含该列**，本节为 **产品+数据冻结口径**；落地实现（迁移、DTO、API、界面）须单独迭代并按本节验收。

#### 1.12.1 是否入库

| 决策项 | 结论 |
| --- | --- |
| 是否作为持久化字段入库 | **是**。客户中心需求将护照号列为自然人关键标识之一；与「材料是否已收/已扫描」为 **不同维度**（后者见 `docs/22_材料チェックリスト口径冻結.md` 及 checklist 模型），**不得**用 checklist 替代护照号主数据。 |
| 与当前代码的关系 | **尚未实现**：`customers`、`person_info`、签证案件成员实体 **均无** 护照号列；家属向导行若仅快照姓名等，**不**视为已满足本节「主档护照号」能力。 |

#### 1.12.2 存储落点（选定方案）

| 候选 | 结论 | 说明 |
| --- | --- | --- |
| `customers` 主表 | **不采用** | 客户含 **法人**；护照仅对 **自然人客户** 有意义，放主表会制造大量 `NULL` 与语义混杂。 |
| `person_info` | **✅ 采用** | 与自然人扩展 **1:1**；主申请人、已建档家属成员均通过 **客户主档** → `person_info` 持有护照号；列表/详情若展示护照，以 **该客户对应 `person_info`** 为权威来源。 |
| 仅签证侧扩展表（如案件/成员行） | **不作为主存储** | 可作 **未建档家属快照**、历史导入等 **补充** 场景演进；**同一自然人** 在有多案件时不应在各案件重复维护互不一致的「主护照号」。主数据仍以 **客户 + `person_info`** 为准。 |

**字段形态（实现时约束）**：`person_info` 新增可空列，建议 `varchar(64)`（存半角大写归一由应用层约定）；**禁止**依赖护照号作为 ORM 主键或外键。

#### 1.12.3 唯一性

| 决策项 | 结论 |
| --- | --- |
| 全局唯一约束 | **不设**。护照换发、录入误差、各国编号规则差异等均可能导致合理重复或历史多条。 |
| 库级 UNIQUE | **不建** `UNIQUE(passport_number)`。 |
| 可选体验 | 将来若需「疑似重复提示」，采用 **非阻断** 的查询提示即可，**不改变** 本节「不强制唯一」结论。 |

#### 1.12.4 隐私与可见性

| 决策项 | 结论 |
| --- | --- |
| 访问控制 | 与本文 **§5 员工数据可见性范围** 一致：一期 **不做字段级脱敏**；能访问该客户详情/API 的角色按既有 RBAC 看到护照号字段（与姓名、在留等同级）。 |
| 审计与导出 | 敏感操作沿用既有操作日志策略；若后续增加批量导出/打印，须在导出规范中 **单独登记** 护照号是否脱敏，**不在本节预设**。 |

#### 1.12.5 检索与列表

| 决策项 | 结论 |
| --- | --- |
| 主检索入口 | 客户列表/搜索仍以 **客户编号、姓名、联系方式** 等为主；护照号 **可作为** 辅助检索维度（实现时：优先 **精确匹配** 或 **前缀匹配**，避免重负载模糊扫描）。 |
| 签证工作台 | **不以** 护照号作为工作台默认筛选主键；若与列表共用查询参数，属增强项，须与性能基线（本文 §9）一并评估。 |

**结论**：✅ 冻结（2026-04-05 增补）。

## 2. 财务结算规则

### 2.1 请款规则

| 规则项 | 结论 |
| --- | --- |
| 请款单关联 | 一张请款单关联一个客户，可关联零或多个案件/合同 |
| 请款单明细 | 通过 `invoice_items` 支持多行明细，总额由系统汇总 |
| 金额精度 | `numeric(18,2)`，日元场景下小数位为 0（前端按币种控制输入） |
| 默认币种 | JPY（日元），一期不支持多币种 |
| 请款编号 | 系统自动生成，格式 `INV-YYYYMMDD-NNNN`，唯一且不可修改 |
| 金额修改 | `DRAFT` 状态可自由编辑；`SENT` 后不可修改，须作废重开 |
| 作废规则 | 须填写作废原因；已有关联收款的请款单不可直接作废，须先冲正全部关联收款 |
| 作废后重开 | 允许，重开时生成新请款编号，原单保留作废记录 |

### 2.2 收款规则

| 规则项 | 结论 |
| --- | --- |
| 收款与请款关系 | 多对多——一笔收款可分配到多张请款单，一张请款单可被多次收款 |
| 分配机制 | 通过 `payment_allocations` 表记录每笔分配金额 |
| 部分收款 | ✅ 支持。分配金额 < 请款总额时，请款状态自动变为 `PARTIAL` |
| 超额收款 | ❌ 不允许。单笔收款的分配总额不得超过收款金额；单张请款单的累计收款不得超过请款总额 |
| 超额部分处理 | 如客户多付，须单独登记一笔预收款充值（`RECHARGE`），不允许直接超额分配 |
| 收款编号 | 系统自动生成，格式 `PAY-YYYYMMDD-NNNN` |
| 冲正规则 | 须填写冲正原因；冲正后自动回退关联请款单状态（`PAID` → `PARTIAL` 或 `SENT`） |
| 请款状态联动 | 收款分配后系统自动计算：累计分配 = 总额 → `PAID`；0 < 累计 < 总额 → `PARTIAL`；累计 = 0 → `SENT` |

### 2.3 预收款规则

| 规则项 | 结论 |
| --- | --- |
| 账户模型 | 每个客户一个预收款账户（`deposit_accounts`），余额通过流水表汇总计算 |
| 余额计算 | `balance = SUM(RECHARGE) - SUM(OFFSET) - SUM(REFUND) ± SUM(ADJUSTMENT)` |
| 余额校验 | 抵扣和退款操作前必须校验余额充足，不允许余额为负 |
| 抵扣操作 | 选择目标请款单 → 输入抵扣金额 → 系统校验余额 → 生成 `OFFSET` 流水 + `payment_allocations` 记录 |
| 抵扣顺序 | 一期不做自动抵扣，由操作人手动选择目标请款单并指定金额 |
| 退款操作 | 须填写退款原因，生成 `REFUND` 流水，扣减余额 |
| 调整操作 | 仅管理员可执行，须填写调整原因，生成 `ADJUSTMENT` 流水 |
| 并发安全 | 预收款余额更新使用乐观锁（`@VersionColumn`），防止并发扣减 |

### 2.4 财务公共防护能力

| 能力 | 实现方式 | 适用范围 |
| --- | --- | --- |
| 幂等控制 | 请求头携带 `Idempotency-Key`，后端基于内存缓存去重（一期不引入 Redis） | 请款创建、收款登记、预收款操作 |
| 乐观锁 | TypeORM `@VersionColumn`，更新时校验版本号 | 请款状态变更、预收款余额变更 |
| 前端防连击 | 按钮点击后 loading + 禁用，使用 composable 封装 | 所有财务表单提交按钮 |
| 金额精度 | 后端使用 `numeric(18,2)`；前端使用字符串传输，不用浮点数运算 | 全部金额字段 |

**结论**：✅ 冻结。以上规则为一期财务模块的完整边界。

## 3. 文件存储最终方案

### 3.1 方案结论

**采用「系统上传 + 服务器本地目录存储」方案**，不采用「仅记录 NAS 共享路径」方案。

| 决策项 | 结论 |
| --- | --- |
| 存储方式 | 文件上传到后端服务器本地目录 |
| 元数据 | 写入 `files` 表（文件名、路径、大小、扩展名、上传人、关联业务） |
| 文件实体 | 存储在服务器指定目录，按 `/{business_type}/{YYYY}/{MM}/{uuid}.{ext}` 命名 |
| 上传方式 | 前端通过 API 上传（multipart/form-data） |
| 下载方式 | 前端通过 API 下载（后端流式返回 + 权限校验 + 日志记录） |
| 预览方式 | 图片：前端 `<img>` 直接展示；PDF：前端使用 iframe 或 pdf.js |
| 上传限制 | 单文件最大 50MB；允许类型：图片(jpg/png/gif/webp)、PDF、Excel(xlsx/xls)、Word(docx/doc)、文本(txt/csv) |
| 文件重名 | 允许同名文件（物理文件使用 UUID 命名，不会冲突；`file_name` 仅用于展示） |
| 版本控制 | 一期不做文件版本管理，相同业务对象可上传多个文件 |
| 删除策略 | 软删除（`deleted_at`），物理文件不立即清除，后续可定期清理 |

### 3.2 目录结构

```
/data/cms-files/
  ├── CUSTOMER/2026/03/
  ├── ADMIN/2026/03/
  ├── TAX/2026/03/
  ├── FINANCE/2026/03/
  └── INTERNAL/2026/03/
```

### 3.3 NAS 的位置

NAS 仅作为服务器本地目录的**备份目标**，不直接作为应用文件存储路径。备份策略在 F2 部署窗口制定。

**结论**：✅ 冻结。

## 6. 国际化需求

### 6.1 结论

**一期界面语言为日文（ja-JP），不做多语言切换功能。**

### 6.2 实现方式

| 项目 | 方案 |
| --- | --- |
| 界面文案 | 直接在模板中写日文，不使用 vue-i18n |
| 日期格式 | `YYYY年MM月DD日` 或 `YYYY/MM/DD`，使用 dayjs 格式化 |
| 金额格式 | 日元无小数，千分位分隔，前缀 `¥`，例：`¥1,234,567` |

| 前端 locale | Element Plus 设置为 `ja` locale |
| S0-γ2 布局 | **不需要**预留 vue-i18n 骨架 |

### 6.3 理由

- 系统面向日本事务所员工，默认用日文即可
- 用户数量少（<10人），无多语言切换需求
- 直接写日文比引入 i18n 框架成本更低、维护更简单
- 如二期需要中文/英文，届时再引入 vue-i18n 做抽取

**结论**：✅ 冻结。
